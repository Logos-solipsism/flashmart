2. **再走第 2–8 章**：每章对应简历上的一条 bullet，内部严格按六类问题排：
   - 维度① 这东西是什么 · 大致怎么用 · 为什么用它
   - 维度② 什么背景 · 基于项目背景为什么偏偏这么选型
   - 维度③ 具体的解决流程（能画出来）
   - 维度④ 各种特殊情况下的兜底策略
   - 维度⑤ 真正的需求 · 实际产出成果
   - 维度⑥ 同类问题的一套方法论
3. **每个问题都有两档答案**：
   - **【新手版】**（用最白的话写的 2~3 句）：面试时先把这句说出口，保证对方听懂、保证自己不出错；

## 第 2 章 · bullet ①：Redis + Lua 原子扣减库存与一人一单

### 2.0 这句话里他会盯的词
**原子**（原子到什么程度？为什么非要原子？）、**一人一单**（在哪儿判断的？数据库还管不管？）、**唯一索引兜底**（兜谁的底？冲突了订单怎么办？）、**超卖**（你怎么知道没超卖？）。

### 维度① 它是什么 · 怎么用 · 为什么用

**Q1：Lua 脚本是什么？你在哪儿用的、怎么用的？**
【新手版】Lua 是一段能在 Redis 服务器内部直接跑的小脚本。我用它把「查一下这个人买过没 + 查一下还有没有库存 + 扣掉一份库存」这三步写成一段脚本，交给 Redis 一口气跑完。这样中间不会被别的请求插进来，所以不会超卖。
A：Lua 脚本是通过 EVAL 提交给 Redis 单线程执行的脚本，Redis 在跑脚本的整个过程中不会穿插执行其他命令，所以脚本内部的"读—判断—写"天然是一个原子操作。我把它包在 Spring 的 DefaultRedisScript 里，用 StringRedisTemplate.execute 调用，脚本文件放在 resources/lua/seckill_stock.lua（见 SeckillStockService 里静态加载的 SECKILL_SCRIPT），入参是 KEYS[1] 等于 seckill:stock:{活动id}、KEYS[2] 等于 seckill:bought:{活动id}、ARGV[1] 是 userId、ARGV[2] 是每人限购数。

**Q2：为什么必须原子？拆成三条命令会怎样？**
【新手版】会出两种事。第一，库存只剩 1 件，两个人同时查到"还有 1 件"，然后都扣，就变成 -1，也就是超卖。第二，同一个人两个请求同时查到"他没买过"，然后都放行，就落下两单。
A：拆开就有两个竞态窗口。① 超卖：两个请求都执行 GET stock 读到 1，都判断大于 0 通过，再各自 DECR，库存变成 -1，**卖出的东西比货多**。② 一人一单失效：两个请求都 HGET bought userId 读到 0，都判断"未购买过"，都执行 HINCRBY，同一个用户落下两单。这两件事的本质都是**"判断"和"执行"之间被别人插了一脚**，Lua 的价值就是把它们压进一个不可分割的执行单元。

**Q3：脚本内部具体怎么判断的？**
【新手版】先看库存还在不在：取不到就直接返回"未预热"；是 0 或负数就返回"抢光了"。再看这个人买过几件：只要"已买数量 + 1"超过限购数，就返回"超限购"。两个都过了，才把库存减 1、把这个人已买数量加 1。
A：四步，全部在脚本里完成：① GET KEYS[1]，返回 nil 说明活动库存还没预热，返回 -3；② stock 小于等于 0 返回 -1（售罄）；③ HGET KEYS[2] ARGV[1]（取不到按 0 算），bought 加 1 大于 limitPerUser 返回 -2（超限购）；④ 全过则 DECR KEYS[1] 加 HINCRBY KEYS[2] ARGV[1] 1，返回 stock 减 1（扣减后的剩余库存）。Java 侧把这四个返回值映射成常量 NOT_PREPARED 等于 -3、SOLD_OUT 等于 -1、OVER_LIMIT 等于 -2，非负数就是成功。

**Q4：一人一单的记录为什么用 Hash，不用 String 或者 Set？**
【新手版】因为我存的是"这个人买了几件"，而不是"买过没买过"。Hash 的每个字段是「用户id → 已买几件」，能加能减还能数；String 一个 key 只能记一个人，几万人抢就几万个 key；Set 只能记"买过"，记不了"买了几件"。当前业务只开放每人 1 件，但存数量的写法本身就是为限购 N 件准备的。
A：因为**我存的是数量，不是布尔值**。Lua 里判断的是"bought 加 1 会不会超过 limitPerUser"，Hash 的 field 是 userId、value 是已购数量，天然表达"这个人在这个活动里买了几件"，HINCRBY 还能原子自增自减（下单失败时我用 HINCRBY -1 把机会还回去，而且只在当前值大于 0 时才减，避免并发重试把已购数量减成负数）。如果用 String，key 得是 seckill:bought:{activityId}:{userId}，一次活动几万个用户就是几万个 key，Redis 的 key 空间和过期管理都更难；用 Set 只能表达"买过还是没买过"的布尔语义，表达不了数量，也做不了回退。

   **一处要说清楚的取舍**：Redis 这一侧的能力是"每人限购 N 件"，但**当前版本在创建活动时把限购数固定成 1**（传大于 1 会被商家接口直接拒绝）。原因是订单表的唯一索引是 `(user_id, activity_id)`，它只允许同一用户在同一活动下有一条订单——如果放开 N 大于 1，第 2 单会被唯一索引拦下，而抢购接口早就返回"抢到了"，用户会一直轮询到 QUEUING、也拿不到失败提示。**这种静默失败比直接拒绝更难查**，所以我选择在入口处挡住，而不是留一个看起来能用、实际会卡住的功能。

▸ **追问 1：Hash 这样存，一个活动就一个 key，会不会变成大 key？**
【新手版】会，而且我知道它的量级。一个字段大约几十字节，十万人的活动也就几 MB，在 Redis 单 key 的承受范围内；真正的隐患是活动结束后这个 Hash 一直没人清。
A：会，而且我知道量级：field 是 userId 字符串、value 是小整数，单字段几十字节，十万量级的活动大约几 MB，还在单 key 的合理范围。真正的风险有两个：一是**热 key**——同一活动所有请求都打在这一个 Hash 上，Redis 单分片会成瓶颈，真要扛更高并发我会按 userId 取模把 Hash 拆成若干分片；二是**清理**——seckill:bought:{activityId} 现在没有 TTL，活动结束后要靠 reset 或人工清（SeckillStockService.reset 里会 delete(bought)），这是我记下的待改进项。

▸ **追问 2：为什么不用 Redisson 分布式锁把这段逻辑锁起来？**
【新手版】锁能解决问题，但代价更大：多一次网络往返、锁粒度难把握、锁超时和业务耗时还可能对不上。Lua 是在 Redis 内部一次执行完，不用"抢占—加锁—释放"这一圈，更省也更快。
A：三个原因。① **往返次数**：锁方案至少是"加锁 + 读 + 写 + 解锁"四次交互，Lua 是一次 EVAL，热门接口上这个差距会被放大；② **原子性边界**：锁保证的是"临界区互斥"，但临界区一旦包含业务逻辑（比如查活动状态），锁的持有时长就不可控，还要处理锁续期；Lua 的临界区就是脚本本身，只有几条命令；③ **范围**：真正的最终一致性我另外用数据库唯一索引加带条件的扣减 SQL 兜底，分布式锁在这一层并不能提供额外保障。所以这个项目**刻意没有引入 Redisson**（上一个项目用的是 Redisson 看门狗，这里是同题不同解）。

### 维度② 背景 · 为什么偏偏这么选

**Q5：为什么库存扣减要放 Redis，数据库不够用吗？**
【新手版】数据库也能扣，但每一单都是一次写事务，还要更新索引和写日志，几千人同时点会直接把连接池和行锁打满。Redis 在内存里做一次自减，快到不是一个量级。所以我把 Redis 当"扣减的真身"，数据库只做异步回写和最后的兜底。
A：不是"数据库不能扣"，而是"数据库不该承接口尖峰"。秒杀的特征是**极短时间内的瞬时并发**，如果用数据库扣库存，每次都是带行锁的 UPDATE 加事务提交加 redo 与 undo 写入，热点行的锁竞争会把连接池（我配的是 Hikari maximum-pool-size 等于 20）瞬间耗尽，请求排队雪崩。所以我把架构分成两层：**Redis 是扣减的真身**（seckill:stock:{activityId}，DECR 在内存里完成），**数据库是异步回写加最终兜底**（flash_activity.available_stock，由 MQ 消费者扣，SQL 里带 available_stock 大于 0 的条件）。

**Q6：为什么要预热？不预热会怎样？**
【新手版】因为活动一开始，流量是瞬间涌进来的。如果等第一个请求来了才去数据库读库存写进 Redis，那第一波请求全都在查库，等于白做缓存。所以我提前把库存写进 Redis，请求来了直接扣。
A：秒杀的流量特征是"开抢瞬间的垂直脉冲"，预热的意义是**把第一个请求要付的初始化成本提前付掉**。不预热的话，开抢那一瞬间所有请求都会走到"库存 key 不存在"的分支（脚本返回 -3），要么全部报"库存未就绪"，要么全部回源数据库，缓存等于不存在。我的做法是两条路都留了：商家创建活动时 ActivityService.create 直接调 prepareStock 预热；抢购链路里 SeckillService 每次进来也调一次 stockService.ensurePrepared(activityId, 数据库的 available_stock, 活动总库存) 兜底（防止服务重启后 Redis 被清空）。

**Q7：预热为什么要有幂等？**
【新手版】因为预热是"把库存写成一个固定值"。如果两个请求同时发现没预热、都去写，而其中一个人已经扣过库存了，那第二次写就会把已扣的库存**覆盖回去**，库存凭空多出来。所以我用一个短的 SETNX 锁，只让一个人写。
A：这是一个很容易被忽略的坑：预热的动作是覆盖写。并发场景下会出现"线程 A 已经扣了 1 件（库存 99），线程 B 这时才把自己的 SET 100 写进去"，库存被凭空加回来 1 件，**等价于超卖**。所以 ensurePrepared() 分两步：先看 seckill:stock:{activityId} 在不在，**在就直接返回**（快路径——抢购接口每个请求都会调它，每次都对初始化锁做一次 SETNX 是多余的写，而且锁 TTL 过期后会留出"用数据库库存覆盖 Redis 计数器"的窗口）；不在才用 setIfAbsent 抢一个 seckill:stock:init:{activityId} 的门闩（TTL 10 秒），抢到的线程把**数据库当前的 available_stock**（不是活动总库存）写进 seckill:stock:{activityId}，同时把活动总库存写进 seckill:total:{activityId}（都是 TTL 7 天），没抢到的直接返回。写 available_stock 这一点很关键：库存 key 一旦丢失（被误删、过期），按总库存重建会把已经卖出去的部分"补回来"，凭空多出库存——这比超卖还难查。10 秒的短 TTL 是刻意的——它只是"初始化窗口内的互斥"，不是长期的业务状态。

### 维度③ 具体流程（要能画）

**Q8：完整讲一遍抢购请求的链路。**
【新手版】请求进来先过限流，再查活动（走缓存），然后就是那段 Lua：查库存、查限购、扣库存，一次做完。扣成功就生成订单号、发一条消息，立刻返回"排队中"。前端拿着订单号轮询结果。
A：五步，主链路里**没有一次数据库写**：
① **滑动窗口限流**（AOP 切面，按用户 1 秒 5 次，超出直接 429）；
② **活动校验**：ActivityService.detailForSeckill 走逻辑过期缓存，依次校验"活动存在、状态在线、未开始、已结束"；
③ **库存预热（幂等）加 Lua 原子扣减**：ensurePrepared 之后执行 trySeckill，返回 -2 报"每人限购 N 件"、-1 报"手慢了"、-3 报"库存尚未就绪"；
④ **生成订单号**：OrderNoGenerator.next(userId)，格式是 FM 加 yyyyMMddHHmmss 加用户尾号 3 位加 6 位进程内自增序列，共 25 位（原来是 4 位随机数：实测两万次生成撞了 207 次，而 order_no 上有唯一索引，撞号就是下单直接失败，所以换成自增序列）；
⑤ **投递 MQ 后立刻返回**：topic_order_create，key 是 order: 加 orderNo，返回体只有 orderNo、state 等于 QUEUING 和提示语。前端拿 orderNo 轮询 /api/seckill/result/{orderNo}。

    ┌──────────┐   ①限流(AOP)    ┌───────────────┐  ②活动校验(逻辑过期缓存)

**Q9：数据库那层的唯一索引是怎么兜底的？**
【新手版】订单表上有个 (user_id, activity_id) 的唯一索引。就算 Redis 那边判断失误、同一个人落下两条，第二条一定会插入失败报主键冲突，我在代码里接住这个异常，把刚扣的数据库库存还回去，然后按"重复下单"处理——把 Redis 里预扣的库存和名额也一起还掉。
A：seckill_order 上有 UNIQUE KEY uk_user_activity (user_id, activity_id)。链路是：OrderCreateConsumer 调到 OrderService.createOrder，先 decreaseStock 扣数据库库存，再 insert 订单；如果插入抛 DuplicateKeyException（MyBatis-Plus 暴露成 Spring 的重复键异常），说明这个人已经在这个活动下过单了——此时 createOrder 里先 activityMapper.increaseStock(activityId) 把刚扣掉的数据库库存还回去，然后**返回 null** 表示"这是重复单，按幂等处理"；消费者拿到 null 之后执行 stockService.rollbackAll(activityId, userId)，把 Redis 里的库存加 1、把这个用户的已购数量减 1。

▸ **追问：为什么唯一索引是 (user_id, activity_id)，而不是把 status 也加进去？**
【新手版】因为我要表达的是"这个人在这个活动里永远只能有一条订单记录"，不管这条记录现在是什么状态。如果把状态加进去，那一个人超时一单、再抢一单，就会留下两条，一人一单就名存实亡了。
A：(user_id, activity_id) 表达的是**业务不变量**——"一个用户在一个活动里最多一条订单"，与订单当前处于什么状态无关。如果把 status 加进唯一键，一旦订单变成 TIMEOUT，唯一约束就不再对这条记录成立，用户可以再抢一单，数据库层的一人一单就失去了意义。代价我也清楚：用户名额被永久占用（即使他超时没付款），**这正是我想要的语义**——见维度④。

### 维度④ 特殊情况下的兜底策略

**Q10：超时关单之后，库存退回给谁？那个用户还能再抢吗？**
【新手版】关键在这里：关单**只把库存还回池子，不把那一个人的"已购名额"还给他**。也就是说货可以给别人抢，但这个人用过一次机会了，不能再抢。只有"订单根本没落库"这种他什么都没拿到的情况，我才把库存和名额一起还给他。
A：这是两件**故意设计成不一样**的事，代码里也是两个不同的方法：
- **超时关单** → OrderService.timeoutOrder 调的是 stockService.rollbackStock(activityId)，方法注释写得很直白："**故意不回滚已购记录的：名额已经用掉了，用户不付款就作废，库存退回池子里给其他人抢 —— 这正是真实秒杀的做法（限购机会只有一次）**"。所以关单之后这个人再抢，会被 Lua 的 -2 挡下，提示"每人限购 1 件，你已经抢到啦"。
- **下单失败**（消息消费时数据库库存不足、或者唯一索引拦下的重复单）→ OrderCreateConsumer 调的是 stockService.rollbackAll(activityId, userId)，**库存加 1 且把该用户的已购数量减 1**。因为这种场景用户什么都没拿到，订单根本没落库，把机会还回去才公平。

▸ **追问：为什么要有这个区别？直接都回滚不就完了？**
【新手版】如果关单也把名额还回去，那"超时"就变成了"免费重来"。恶意用户可以无限占库存、不付款、等系统自动还回来，再抢再占，用一个人把整个活动的库存锁死。
A：如果关单也回滚名额，**"超时"就等价于"无限次免费重试"**：恶意用户只要不断下单不付款，就能反复锁住库存再释放，用极低成本把活动的货全部占住（黄牛占位）。反过来，把"机会"和"货物"拆开处理，既保证了货不会被浪费（库存回到池子给别人抢），又保证了机会不被滥用（一人一次）。代价是**正常用户误超时之后也失去了资格**——这是业务上接受的取舍，我在文档里把它写成明确的设计决策而不是 bug。

**Q11：如果 Redis 里库存判断说"有货"，但数据库真的扣不动了怎么办？**
【新手版】数据库那条扣减 SQL 带了 available_stock 大于 0 这个条件，所以库存是负数它就直接不执行、返回影响 0 行。我把 0 行当成"库存真的没了"，抛异常，消费者在外面接住，把 Redis 预扣的库存和名额还回去，再让消息重试。
A：FlashActivityMapper.decreaseStock 的 SQL 是 UPDATE flash_activity SET available_stock 等于 available_stock 减 1，WHERE 里带 id 和 available_stock 大于 0，**返回受影响行数**。返回 0 就说明数据库这一层确实没库存了（Redis 和数据库短时不一致，比如 Redis 被清过、或者库存被商家改小过）。createOrder 收到 0 会抛 BizException("数据库库存已扣不动，本次下单失败")——**这句文案只描述数据库这一侧**，Redis 侧预扣的库存与名额由调用方（消费者）回滚；OrderCreateConsumer 的 catch 里调 rollbackOnce(msgId, event)：先用 seckill:rollback:{msgId} 的 SETNX 保证**同一条消息只回滚一次**（否则 MQ 重试会把库存反复加回去，凭空多出库存），再 rollbackAll 把 Redis 库存和名额还回去，然后 markFailed 加抛出异常交给 RocketMQ 阶梯重试。Redis 侧的回滚本身也带上限：rollback_stock.lua 只有"当前库存小于活动总库存（seckill:total:{activityId}）"时才加一。**这一层是"数据库永远不会扣成负数"的最后一道闸。**

**Q12：Redis 挂了、或者库存 key 被误删了会怎样？**
【新手版】Lua 脚本第一句就是取库存，取不到直接返回 -3，接口报"活动库存尚未就绪，请稍后重试"，不会往下走。同时抢购链路每次进来都会先尝试幂等预热，所以就算 key 被删了，下一个请求也能把它按**数据库当前的 available_stock**重新建起来（不会把已经卖出去的部分补回来）。
A：分两种：① **Redis 不可用**：trySeckill 里脚本执行会抛异常，这一层现在没有 catch，会冒到全局异常处理器返回"系统繁忙"——**这是刻意的**，抢购这种"扣了就必须算数"的动作，我宁可失败也不愿意在存储不可靠的时候放行（对比限流组件我选择了降级放行，因为限流是保护手段，见第 6 章）；② **key 被误删**：SeckillService 每次进入都先调 stockService.ensurePrepared(activityId, () -> activityService.currentDbStock(activityId), activity.totalStock())，**重建用的就是数据库当前的 available_stock**，不是活动总库存——因为按总库存重建会把已经卖出去的部分"补回来"，凭空多出库存，这比超卖还难查。ensurePrepared 还带一条快路径：库存 key 已经存在就直接返回，只有 key 不在时才抢 SETNX 门闩写入，所以正常抢购请求不会每次都多做一次 SETNX，也不会出现"锁 TTL 过期后用数据库库存覆盖已扣减计数器"的窗口。剩下的 Redis 与数据库短暂不一致，最终由数据库的扣减条件兜住（多卖的部分会在数据库这一层被拦下并回滚）。

### 维度⑤ 真正的需求 · 实际产出

**Q13：一人一单和限流，你到底压出了什么结果？**
【新手版】压测工具（bench/Bench.java，纯 JDK 写的，不依赖 JMeter）里有一个 oneuser 实验：用同一个账号在极短时间内并发打 20 次抢购接口，结果是**只成功 1 次**，其余全部被拦下。提示语就是"每人限购 1 件，你已经抢到啦"。
A：实验设计是这样的：先 reset 清掉该活动的订单（**物理删除**，不是逻辑删除，见 Q14）、重置库存和已购记录，然后用闭锁同时发起 20 次抢购请求。结果：**成功 1 次、限购 4 次、限流 429 共 15 次**（限流在限购之前生效，所以大部分请求根本没走到 Lua）。拦截分两类，我把它分开统计了：一类是被**限流**（每人 1 秒 5 次）在进入库存校验之前就 429 掉的，另一类是真的走到 Lua 里被 -2 限购挡下的——这两类的服务端返回原文我都单独打了一张表。除此之外还做了个补充验证：**按 1.2 秒间隔匀速再发 5 次**（绕开 1 秒限流窗口），结果是成功 0 次、限流 0 次、**全部被一人一单规则拦下**——这一步是为了证明"拦截来自限购本身，而不是被限流掩盖了"。

**Q14：怎么证明"没有超卖"？**
【新手版】压测工具的统计接口会把"总库存、数据库剩余库存、Redis 剩余库存、订单总数、各状态订单数"一起打出来。跑完拿这几个数一对：数据库剩余库存和 Redis 剩余库存对得上、订单数也没超过总库存，就说明没超卖。另外每次压测前都要把上一个活动的订单**物理删除**，不然唯一索引会把新订单全挡掉。
A：靠 BenchService.stats（/api/bench/stats/{activityId}）输出的一组对照数据：totalStock、dbAvailableStock、redisAvailableStock、orderCount、ordersByStatus、cacheLoadCount。判断口径是**订单数不超过总库存、且两边的剩余库存能对上**。最近一次实测是"活动 30 件库存 / 60 个不同用户并发抢"：**成功 30 次、落库 30 单、数据库剩余库存 0、Redis 剩余库存 0**——成功数、落库数与总库存三者相等，无超卖、库存非负。这个数字的口径要说清楚：本机 Windows + Docker 中间件、压测客户端与服务同机、闭环压测模型，测前先清空数据表并等 MQ 排空。这里有个很值得讲的实现细节：压测重置必须用 deleteByActivityPhysically 做**物理删除**，因为 MyBatis-Plus 配了逻辑删除（logic-delete-field 等于 deleted），逻辑删除只是把 deleted 置 1，**那条行仍然占着 uk_user_activity**，会导致同一个用户之后再也下不了单——这个坑我是踩出来的，mapper 上专门写了注释。

### 维度⑥ 方法论（这一段最容易被记住）

**Q15：高并发下"扣减类"的需求，你有一套通用的办法吗？**
【新手版】五步：第一，把判断和扣减合成一个原子动作（Lua）；第二，判断的时候一定要把条件写进执行语句里，比如扣库存必须带 available_stock 大于 0，而不是"先查再改"；第三，在真正的存储上加一道硬约束，比如唯一索引；第四，扣减的"真身"放在能扛住并发的地方（Redis），数据库做异步回写；第五，给"还回去"设计两条不同的路径——没拿到东西要全还，拿到了但作废只还货不还机会。
A：我的五条：① **原子化**：把"判断加执行"合并进一个不可分割的执行单元（Lua、单条带条件的 UPDATE、或者 CAS 操作），消灭"读—判断—写"之间的竞态窗口；② **条件前置**：库存判断必须长在 UPDATE 的 WHERE 里（available_stock 大于 0），而不是先 SELECT 再判断，这样数据库自身就是幂等且不会扣成负数的；③ **硬约束兜底**：不管前面多少层校验，最终都要有一条数据库级的不可绕过的约束（唯一索引、条件更新返回行数）；④ **分层承载**：高频扣减放 Redis，数据库只承接"已经过削峰的写入"，两者的差值由最终一致性机制收口；⑤ **回滚要分语义**：区分"用户什么都没拿到"和"用户拿到过但作废了"，前者全额回滚（库存加机会），后者只回滚资源（库存）。这五条不只适用于库存，同样适用于优惠券核销、额度占用、库存锁定这类"有限资源竞争"的场景。

### 本章追问链（问完第一句之后最可能被追的四句）
1. **"Lua 里面如果加了别的逻辑，会不会把 Redis 卡住？"** → 会，所以我的脚本只做 O(1) 的读和写，没有任何循环、没有大范围扫描；Redis 单线程跑脚本期间会阻塞其他命令，脚本越短越好。
2. **"那你怎么保证 Lua 脚本不会因为网络问题被重复执行？"** → EVAL 本身是单条命令，不存在"执行了一半"的情况；客户端重试可能让脚本跑两次，所以脚本最好是幂等的——我这段脚本不具备幂等性（重跑会多扣一次），这一点靠客户端超时重试策略和数据库唯一索引共同限制影响面，属于我知道的边界。
3. **"同一毫秒两个人抢最后一件，谁赢？"** → Redis 是单线程按到达顺序串行执行脚本，**先到先得**，后到的那个读到库存 0 返回 -1。不存在"两个人都赢"。
4. **"这套方案能扛多少 QPS？"** → 我没压出 Redis 单分片的极限（未实测）。能说的是瓶颈转移的位置：主链路只剩一次 EVAL 加一次异步发消息，数据库写被挪到了消费端按自己的速度消费；真正先到瓶颈的会是 Redis 单分片的热 key，处理办法是按 userId 分片 Hash。

### 一分钟口述稿（被要求"讲讲你的库存扣减"时照着说）
"我的抢购核心是把'判断限购 + 判断库存 + 扣库存'三步合成一次 Lua 原子执行。原因是如果拆成三条命令，并发下会出现两种事故：两个人同时读到库存 1 然后都扣，变成超卖；同一个人两个请求同时读到'没买过'然后都放行，落下两单。脚本里就是四步：取库存，取不到返回未预热；库存小于等于 0 返回售罄；用 Hash 取这个人的已购数量，加一超过限购就返回超限购；全过了才 DECR 库存、HINCRBY 已购数量。一人一单用 Hash 存 userId 到已购数量，所以我支持的不是死的一人一单，而是可配置的每人限购 N 件。Redis 只是第一道，数据库上还有 (user_id, activity_id) 唯一索引和带 available_stock 大于 0 的扣减 SQL 兜底。这里我特意做了一个设计区分：**超时关单只回滚库存、不回滚这个人的已购记录**——名额用掉了，不付款就作废，货退给池子里别人抢；只有订单根本没落库的下单失败，我才把库存和机会一起还回去。实测上，同一个用户并发抢，只成功 1 次，其余全部被'每人限购 1 件'拦下。另外补充一句：这个项目我**没有用分布式锁**，用的是 Lua 加乐观锁加唯一索引，因为锁的临界区在这里解决不了额外问题，反而多几次网络往返。"

## 第 3 章 · bullet ②：RocketMQ 异步下单削峰

### 3.0 这句话里他会盯的词
**异步解耦**（哪些是异步的？同步的还剩什么？）、**只保留资格校验与消息投递**（那用户到底买到了没有？）、**削峰**（削的是谁的峰？峰去哪儿了？）、**流量**（怎么知道真的削下去了？）。

### 维度① 它是什么 · 怎么用 · 为什么用

**Q1：这条链路里，什么是异步的，什么是同步的？**
【新手版】用户点"抢购"这个请求是同步的，但它只做四件事：限流、校验活动、扣 Redis 库存、发一条消息，做完立刻返回"排队中"。真正写订单、扣数据库库存这些慢活，是另一个程序（消费者）异步做完的。前端拿订单号轮询，看到订单了就说明落库了。
A：同步的是**抢购接口**本身（SeckillService.seckill）：限流，再活动校验（走缓存），再幂等预热加 Lua 原子扣减，再生成订单号，再 mqProducer.sendAsync 投递，最后返回 orderNo 加 state 等于 QUEUING。异步的是**所有数据库写**：订单落库、数据库库存扣减、投递延迟关单消息，都在 OrderCreateConsumer 里做。对外的一致性是"**最终一致加前端可观测**"：/api/seckill/result/{orderNo} 在订单还没落库时返回 QUEUING，落库后返回真实状态（PENDING_PAY、PAID、TIMEOUT）。

**Q2：为什么用消息队列，而不是直接同步写完数据库再返回？**
【新手版】同步写的话，用户得等"扣数据库库存 + 插订单 + 提交事务"全部完成才拿到响应。秒杀时这几千个事务同时在抢同一行库存，互相等锁，前端的等待时间会越来越长。异步发消息不一样：数据库只面对消息队列推过来的速度，队列先把洪峰**存下来**，消费端按自己能扛的节奏慢慢写——这就是削峰。
A：核心是**把"用户点击的并发"换成"消费端的并发"**。同步写时，瞬时并发直接打到数据库热点行上，行锁排队让响应时间非线性变长，而且 Tomcat 的工作线程（我配了 max 等于 200）会被这些等待全部占住，一个接口慢会拖慢整个服务。异步化之后：抢购线程的耗时只包含一次 Redis 脚本加一次异步发消息，写完就释放；数据库面对的是 RocketMQ 按消费能力推过来的**匀速流量**。用消息队列而不是线程池或 @Async，是因为我要的是三件事：**可靠**（进程重启消息还在 Broker 里）、**可重试**（消费失败按阶梯重试、超限进死信）、**可削峰**（洪峰存在 Broker 而不是堆在应用内存里）。

**Q3：异步之后，用户怎么知道自己到底抢到了没有？**
【新手版】接口立刻返回"抢到了！正在为你生成订单"加一个订单号，状态是 QUEUING。前端拿着这个订单号循环问服务端"好了没"，订单一旦落库，状态就变成待支付，前端跳转到支付页。
A：三段式：① **接口立即返回** orderNo 加 state 等于 QUEUING 加提示语；② **前端轮询** /api/seckill/result/{orderNo}，SeckillService.result 里订单为 null 就返回 QUEUING，查到订单就返回真实 status；③ **归属校验**：查到订单后还要比对 userId，不是自己的订单返回 403"无权查看该订单"（订单详情接口 GET /api/order/{orderNo} 后来也补上了同样的校验：非本人返回 403"无权查看该订单"，订单查不到返回 404"订单不存在或还在生成中，请稍后重试"）。另外订单 VO 里带 payDeadline（创建时间加超时秒数），前端据此显示支付倒计时。**异步不是把问题甩给用户，而是把"等待"变成一个用户看得见、可轮询的状态。**

### 维度② 背景 · 为什么偏偏这么选

**Q4：为什么这个场景必须削峰？不削会怎么样？**
【新手版】秒杀的特点就是"一秒钟几千个人抢一百件货"。如果不削峰，这几千个请求会同时去抢数据库同一行库存，全都堵在那儿等锁；应用线程也全被占住，连"已售罄"这种简单查询都返回不了。
A：因为秒杀的流量是**脉冲式**的：业务上一个活动的有效库存可能只有一百件，但开抢瞬间打进来的请求是几千甚至几万，其中 99% 注定要失败。如果不削峰，这些注定失败的请求会**真实地消耗数据库的锁和连接**：热点行的行锁排队、连接池（20 个连接）耗尽、Tomcat 工作线程（200 个）被占满，导致的结果是"该成功的也超时了"。削峰的本质是**让系统按自己的处理能力接收请求，而不是按用户的点击速度**。还有一个隐性收益：真正落到数据库的只有"通过了 Redis 扣减的请求"，也就是库存数量级（一百次），而不是请求数量级（几千次）——**削峰顺便把 99% 的无效写也过滤掉了**。

**Q5：为什么是 RocketMQ，不是 Kafka？**
【新手版】我需要的主要是"业务任务"而不是"海量数据流"。RocketMQ 自带延迟消息，我的超时关单直接用它，不用再写定时任务；还有死信队列和控制台，一条消息重试了几次、为什么失败都看得到。
A：我的场景是**业务事件的可靠投递**，不是大吞吐流处理，所以选型权重不在吞吐上：① **原生延迟消息**——超时关单直接复用（见第 7 章），Kafka 没有这个能力，得自己加调度层；② **死信队列加消息轨迹**——消费失败重试到上限进 %DLQ%cg_order_create，后台能看到一条消息的完整轨迹，这对"订单类"业务很重要；③ **重试语义贴合**——RocketMQ 的消费失败重试是"同一消费组内按阶梯间隔重投"，正好匹配"数据库偶发失败要再试一次"的诉求。Kafka 的优势是吞吐和流式生态，但那不是我这条链路的瓶颈。

### 维度③ 具体流程（要能画）

**Q6：抢购接口和消费者各自做了什么？**
【新手版】接口：限流、校验活动、扣 Redis 库存、生成订单号、发消息、返回，一共就这些。消费者：先查这条消息是不是处理过（幂等），然后扣数据库库存、插订单，成功后再发一条延迟 30 秒的关单消息；任何一步失败就把 Redis 里预扣的库存和名额还回去，然后让消息重试。
A：

    抢购接口（同步，毫秒级）
      POST /api/seckill/{activityId}
        → ① AOP 滑动窗口限流（用户维度 1s/5 次）
        → ② ActivityService.detailForSeckill（逻辑过期缓存）+ 状态/时间校验
        → ③ stockService.ensurePrepared（库存 key 不存在时才按数据库 available_stock 预热）+ trySeckill（Lua 原子扣减）
        → ④ OrderNoGenerator.next(userId) → orderNo
        → ⑤ sendAsync(topic_order_create, key="order:"+orderNo, OrderCreateEvent)
        → ⑥ 返回 {orderNo, state: QUEUING}

    OrderCreateConsumer（异步，topic_order_create / cg_order_create / consumeThreadMax=32）
        → TraceUtil.start(消息里的 traceId)       ← 跨进程续上同一条链路日志
        → idempotentRepository.tryAcquire(msgId)  ← msg_id 唯一索引，重复消息直接丢
        → 反序列化 OrderCreateEvent
        → OrderService.createOrder(...)  @Transactional
             ├─ decreaseStock(activityId)  WHERE available_stock > 0 ；0 行 → 抛异常
             ├─ orderMapper.insert(order)  status=PENDING_PAY, version=0
             └─ DuplicateKeyException → increaseStock 还库存 + 返回 null（重复单）
        → 若返回 null：rollbackOnce(msgId, event)（SETNX 保证每条消息只回滚一次；还库存 + 还名额）
        → 若成功：sendAsync(topic_order_timeout, delayLevel=nearestDelayLevel(30))
        → markSuccess(msgId)
        → 异常路径：rollbackOnce(msgId, event) + markFailed(msgId) + 抛出 → MQ 阶梯重试 → 到上限进死信（项目里没有死信消费者与重放接口，只能去 Dashboard 人工处理）

**Q7：消息里都带了什么？为什么这么设计？**
【新手版】消息里只放订单号、用户、活动、商品和成交价这些主键和必要字段，不放整张订单对象。消费端需要更多信息就自己去数据库查。这样以后业务字段改了，消息格式不用跟着升级。
A：MqEvents.OrderCreateEvent 里是 orderNo、userId、activityId、productId、flashPrice，注释里写明了设计意图："**只带业务主键（orderNo、activityId）和必要字段，消费端自己回查数据库，这样消息格式不会随业务字段变化而频繁升级。**" 另外发送侧做了两件事：keys 设为 order: 加 orderNo（便于在控制台按业务键查消息、也是幂等表里记录的 biz_key）；TraceUtil.HEADER 里带上当前 traceId，消费端 TraceUtil.start(...) 取出来继续用——**一次请求的 HTTP 日志和消费者日志能串成一条**。

**Q8：为什么发消息用异步发送（sendAsync）？**
【新手版】因为我在主链路上不想等 broker 的回执。发消息成功与否不影响"我已经扣到库存、拿到名额"这个事实，失败了我记错误日志，所以没必要让用户多等一个网络往返。
A：MqProducer.sendAsync 用的是 rocketMQTemplate.asyncSend 加 SendCallback，主线程不等 broker 回执，成功打 debug 日志、失败打 error 日志；**onException 里还有一层兜底：同步重发一次**（syncResend，同步发送会走 broker 客户端自带的 retry-times-when-send-failed 重试），同步重发也失败才打 error 日志；延迟消息那条分支还额外传了 3000ms 超时和 delayLevel。取舍是明确的：**主链路延迟优先，投递可靠性由"失败同步重发一次加日志"承担**。要诚实说边界——同步重发仍然失败时，"扣了 Redis 库存但消息没发出去"这个窗口只能靠日志暴露，没有自动补偿；工业级做法是落一张本地消息表，用定时任务扫"未发送"记录重投。这是我明确记下的改进项。

### 维度④ 特殊情况下的兜底策略

**Q9：消息丢了怎么办？**
【新手版】分三段看。发消息这一段：我用的是异步发送，失败会打错误日志，但确实存在"库存扣了、消息没发出去"的窗口，正确做法是落本地消息表用定时任务补发，这是我记下的待改进项。存消息这一段：消息写在 broker 磁盘上，服务重启也在。收消息这一段：数据库写成功才 ACK，失败就重试。所以真正会丢的窗口只在"Redis 扣减成功、消息没发出去"这一瞬间。
A：三段拆开：① **生产端**——asyncSend 的回调在失败时会**同步重发一次**（syncResend），同步重发也失败才 log.error 打日志，这是最终的暴露手段，仍然没有自动重投（本地消息表没做）；要彻底消掉这个窗口必须引入**本地消息表**（把"扣 Redis 库存"和"记录待发消息"放在同一处、由定时任务补偿），我把它列为下个版本第一件事。② **Broker 端**——消息持久化在 broker 磁盘上，应用进程重启不影响。③ **消费端**——业务成功才 markSuccess，失败 markFailed 后抛异常，交给 RocketMQ 阶梯重试。所以真正敞着的窗口是**"Redis 已经扣减、消息尚未投递成功"**这一瞬间，表现为"用户拿到 orderNo 但一直轮询到 QUEUING"。缓解手段是这一瞬间的错误日志加 orderNo 可以在日志里定位。

**Q10：消息重复消费怎么办？**
【新手版】RocketMQ 保证的是"至少送到一次"，所以消息一定会重复。我的防重做在消费端：用一张表存消息 ID 并加唯一索引，插入成功就是第一次处理；插入冲突就说明处理过——成功过就直接跳过，失败过的说明这是它的重试，放行再试一次。业务侧还有第二道：订单表的 (user_id, activity_id) 唯一索引。
A：MqIdempotentRepository.tryAcquire 靠 mq_consume_log 的 UNIQUE KEY uk_msg_id：insert 成功就是首次消费返回 true；抛 DuplicateKeyException 就回查这条记录，如果状态是 FAILED 就**放行**（说明这是它自己的重试）并把 retry_count 加 1 改回 CONSUMING，否则返回 false，消费者直接 return。**幂等有两层**：消息级（msg_id 唯一索引）和业务级（seckill_order 的 uk_user_activity）。第二层才是真正不可绕过的——即使幂等表被清、或者以后业务规则变了，业务不变量仍然成立。

**Q11：消息积压了怎么办？**
【新手版】先分清是"消息突然变多"还是"消费变慢"。能加机器就加消费实例，我的消费者是无状态的，加实例就能分摊；如果是某个下游慢（比如数据库抖了），就减慢重试节奏，别让线程干等。
A：判断依据是控制台的堆积量和消费 TPS。处理顺序：① **提并行度**——OrderCreateConsumer 已经配了 consumeThreadMax 等于 32，消费实例本身无状态，横向加实例即可分摊，必要时扩队列数；② **降级非核心**——topic_cache_evict 的缓存补偿消息可以延后处理，topic_order_create 必须优先保；③ **查下游**——如果积压是因为数据库慢（连接池打满、慢 SQL），那加消费实例反而会加剧，要先把下游救回来。这里的边界要说清楚：**积压的时候，"抢购接口还在正常收流量"这个事实本身是好事**——流量被存在 broker 里而不是丢掉；但如果积压时间超过了订单超时时间，就会出现"订单刚落库就被延迟消息关掉"的时序错乱，所以超时时间要显著大于可接受的积压时长。

**Q12：消费失败重试几次？重试完还失败呢？**
【新手版】消费端失败就把异常抛出去，让 RocketMQ 按阶梯间隔重试，越等越久；试到上限还失败，消息进死信队列，我能从死信里查出来，也能按订单号重新投一条。
A：消费端不自己写循环重试，**统一交给 RocketMQ 的阶梯重试**（间隔逐级拉长），到最大次数后进死信主题 %DLQ%cg_order_create（这是 RocketMQ 按消费组自动创建的，代码里连常量都没有定义——原来的 MqTopics.DLQ_ORDER_CREATE 已作为死代码删掉；项目里**没有死信消费者，也没有重放接口**，死信只能去 Dashboard 人工处理）。每一次尝试都会在 mq_consume_log 里留痕：status（CONSUMING、SUCCESS、FAILED）加 retry_count 加 error_msg，所以死信里的消息**不是黑盒**——能查到它试了几次、每次为什么失败。另外我在编码阶段就把"可恢复失败"和"不可恢复失败"分开了：数据库库存不足这种业务失败有专门的 rollbackAll 路径，只有真正的异常（连接超时、死锁）才抛出去重试。

### 维度⑤ 真正的需求 · 实际产出

**Q13：你说的"削峰"，有没有实际数字？**
【新手版】有两个实测数。第一，异步版的抢购接口**返回耗时 28ms**——用户点一下基本是"秒回"。第二，接口返回之后大约 **157ms** 订单落库，也就是前端轮询一两次就能看到待支付状态。也就是说：用户等待的时间和系统干活的时间被拆开了，28ms 是用户付出的，157ms 是系统自己消化洪峰用的。第三个数字是对照压测：同样是 50 并发 / 2000 请求，异步版 **176 req/s**，同步对照组 **39 req/s**，吞吐差约 4.5 倍。
A：实测口径：**异步抢购接口返回耗时 28ms**（用户感知的等待），**接口返回后约 157ms 订单落库为 PENDING_PAY**（异步链路的端到端完成时间）。这两个数要一起说才有意义：**用户只等 28ms，剩下的 157ms 从用户的等待里挪到了后台**。对比口径来自压测工具里的一对等价接口 POST /api/bench/seckill-async/{id} 和 POST /api/bench/seckill-sync/{id}——异步版是"Lua 扣减加发 MQ 立即返回"，同步版是"扣数据库库存加插订单后返回"，**两者只差"要不要等数据库写完"这一处**，其他条件（同一个活动、同一套 reset、同样的并发模型）完全一致。这个对比能成立的关键是接口设计：真实 /api/seckill 有一人一单和限流，同一账号只能成功一次，没法把并发打满，所以压测用**合成 userId** 走等价链路——这是我在 bench 服务注释里写明的取舍："跳过一人一单校验，其他逻辑与线上一致，所以耗时和吞吐的差异来自是否异步"。对照压测的数字（50 并发 / 2000 请求）：**异步 176 req/s、平均 280.66ms、P50 282ms、P90 307ms、P95 315ms、P99 329ms**；**同步对照组 39 req/s、平均 1259.62ms、P50 1261ms、P90 1359ms、P95 1394ms、P99 1462ms** → **吞吐约 4.5 倍、单请求平均耗时降约 78%、P99 降约 77%**。口径：本机 Windows + Docker 中间件，压测客户端与服务同机，闭环压测模型，测前清空数据表并等 MQ 排空。

▸ **追问：157ms 这个数字怎么测出来的？**
【新手版】压测工具里的超时、支付实验是这么做的：发一次抢购，拿到 orderNo，然后**每 200 毫秒轮询一次**结果接口，记录第一次不是 QUEUING 的时间和轮询次数。157ms 就是"抢购接口返回"到"订单落库"之间的间隔。
A：Bench.pollState(token, orderNo, timeoutMs, predicate)：以 200ms 为间隔轮询 /api/seckill/result/{orderNo}，直到 state 不再是 QUEUING（或超时），打印轮询次数和总耗时。所以这个数字的**精度上限是 200ms 的轮询粒度**，我会主动说明这一点：它是"大约 157ms 量级"的真实观测，不是高精度打点；如果要更精确，应该在消费端埋点（记录消息投递时刻与落库时刻的差值）。**知道自己数字的精度边界，比数字本身更加分。**

### 维度⑥ 方法论（这一段最容易被记住）

**Q14：什么样的逻辑该异步化？给我一套判断标准。**
【新手版】四条：耗时长而且我控制不了；用户不需要等它才能继续；成功失败是明确的、可以重试；失败了有地方能看出来。四条都符合就把它从主链路挪走，少一条就老老实实同步做。
A：四条标准：① **耗时不可控**（依赖外部服务、或者超过 200ms）；② **结果不影响本次响应**（用户不需要等它才能继续，比如"抢购资格"已经拿到、"订单落库"可以稍后）；③ **有明确的成功与失败状态且可重试**；④ **失败可观测**（有日志、有死信队列、有后台能查）。四条全中才异步。反过来，**结果必须立刻返回的（比如登录要签发 token）、失败了无法定责的、需要强一致读的，都不能异步**。再补一条我踩出来的经验：异步化的门槛不只是"慢"，还有**"异步之后用户能不能自己看到进度"**——有 orderNo 轮询接口，异步才成立；没有这个接口，异步就是把不确定性甩给用户。

### 本章追问链（问完第一句之后最可能被追的四句）
1. **"异步下单之后，如果用户一直不付款，库存不就一直占着？"** → 会，所以我给每个订单在创建成功的同时投了一条延迟消息，到点自动关单并回滚库存（第 7 章），不需要定时任务扫全表。
2. **"Redis 扣了库存但消息发失败了，用户岂不是白抢一次？"** → 是，这个窗口真实存在，我现在靠错误日志暴露，正确解法是本地消息表加定时补偿，这是我最优先的改进项。
3. **"为什么不干脆用线程池异步写订单？"** → 线程池的任务在内存里，重启就丢、失败不会自动重试、洪峰时还会把应用内存和线程吃光。我要的是"可靠加可重试加可堆积"，这三件事只有独立的 broker 能给。
4. **"削峰之后，数据库的写入速度就是消费速度，那消费端自己成为瓶颈怎么办？"** → 那就横向加消费实例（消费者无状态），或者提 consumeThreadMax；但要注意先确认瓶颈不在数据库，否则加消费实例只会把数据库压得更狠。

### 一分钟口述稿（被要求"讲讲异步下单"时照着说）
"我的抢购接口是同步的，但只做四件事：限流、校验活动（走缓存）、用 Lua 原子扣 Redis 库存、把一条消息投到 RocketMQ，然后立刻返回一个订单号，状态是 QUEUING。真正写订单、扣数据库库存这些动作，全部由消费者异步做——先查消息幂等表，再扣数据库库存、插订单，成功后投一条延迟 30 秒的关单消息；任何一步失败就把 Redis 预扣的库存和名额还回去（回滚用 SETNX 保证每条消息只回滚一次），再让消息重试。**为什么要这么拆**：秒杀的流量是脉冲，如果不削峰，几千个请求会去抢数据库同一行库存，行锁排队会把连接池和 Tomcat 线程全占满，连'已售罄'都返回不了；异步之后数据库只面对队列推过来的匀速流量，而且真正落到数据库的只有'通过 Redis 扣减'的那一百个请求，99% 的无效请求在 Redis 那一层就被挡掉了。选 RocketMQ 不选 Kafka，是因为我要的是业务事件的可靠投递——它自带延迟消息（我的超时关单直接用）、死信队列和消息轨迹。用户侧的体验是：接口 28 毫秒返回，前端拿 orderNo 轮询，实测大约 157 毫秒后订单落库变成待支付。边界我很清楚：异步发送失败会同步重发一次，再失败就只能靠日志暴露，没有自动补偿，应该用本地消息表来收口。"

## 第 4 章 · bullet ③：逻辑过期防击穿 + 空值缓存防穿透

### 4.0 这句话里他会盯的词
**逻辑过期**（什么是逻辑上的过期？跟真的过期有什么区别？）、**异步重建**（谁来重建？重建期间请求怎么办？）、**缓存击穿**（和穿透、雪崩有什么区别）、**缓存空值**（空值存多久？会不会把真的数据挡住？）。

### 维度① 它是什么 · 怎么用 · 为什么用

**Q1：缓存穿透、击穿、雪崩，分别是什么？**
【新手版】穿透是"查一个根本不存在的东西"，缓存没有、数据库也没有，于是每次都白跑一趟数据库。击穿是"一个热点 key 突然失效了"，一瞬间所有请求发现缓存没了，全都扑向数据库。雪崩是"大批 key 同时失效"，等于数据库在那一刻被全量请求打了一遍。
A：三者的成因和抓手完全不同：
- **穿透**：请求的数据**在数据库里也不存在**（比如查一个不存在的活动 id、被随机 id 攻击），缓存永远不会命中，每次都穿透到数据库。抓手是"把不存在这件事也缓存下来"（空值缓存）或布隆过滤器。
- **击穿**：数据**存在**，但那个热点 key（比如一个大促活动）在某个瞬间失效或被删，N 个并发请求同时发现 miss、同时回源。抓手是"只放一个请求回源"（互斥锁）或者"干脆不让它失效"（逻辑过期）。
- **雪崩**：**大量 key 同时过期**（比如统一设了同一个 TTL），或者缓存集群整体宕机，请求全量落到数据库。抓手是 TTL 打散、多级缓存、熔断降级。

**Q2：什么是"逻辑过期"？它和普通 TTL 有什么不一样？**
【新手版】普通 TTL 是 Redis 到点就把 key 删了，下一次请求发现没有就回源。逻辑过期是：key 的物理过期时间设得很长，同时在**值里面**存一个"逻辑过期时间"；到点之后 key 还在、旧值还能读出来，只是程序发现它"逻辑上过期了"，于是返回旧数据，另外派一个后台线程去重建。
A：实现上，缓存值被包了一层：外面是 expireAt（逻辑过期时间戳）和 data（真正的数据），物理 TTL 设成逻辑过期的 **3 倍**（writeWithLogicExpire 里 Duration.ofSeconds(logicTtlSeconds 乘 3)）。读取时先反序列化，取 expireAt 和 data；如果当前时间已经超过 expireAt，就**先把旧值返回给当前请求**，同时调 asyncRebuild 去重建。**核心差别**：普通 TTL 失效后缓存里什么都没有，请求只能阻塞等回源；逻辑过期失效后缓存里**永远有东西**，请求永远不阻塞。

**Q3：逻辑过期怎么做到"只有一个请求去重建"？**
【新手版】重建之前先抢一把锁——用 Redis 的 setIfAbsent（也就是 SETNX），只有抢到的那个线程去后台重建，没抢到的直接什么都不做，继续用旧值。
A：asyncRebuild 里用 setIfAbsent 抢一个 cache:rebuild:lock: 加 key 的锁（value 是 UUID、TTL 10 秒）：抢到锁的线程把重建任务提交给一个固定的守护线程池（Executors.newFixedThreadPool(4)，线程名 cache-rebuild），重建完在 finally 里删锁；没抢到锁的线程**直接 return**，因为它已经拿到旧值返回了，不需要做任何事。互斥的目的是**把重建的并发从 N 降到 1**，避免过期瞬间 N 个线程同时回源。

**Q4：空值缓存是怎么防穿透的？**
【新手版】数据库里查不到的时候，我不返回空就完了，而是在缓存里写一个特殊标记（内容是双下划线 NULL 双下划线），给它一个很短的过期时间（默认 30 秒）。下次再有人查同一个不存在的 id，直接命中这个标记，知道"数据库里确实没有"，就不再查库了。
A：RedisCacheClient 里定义 NULL_MARK 等于 "__NULL__"。读路径一进来先判：如果取到的值等于 __NULL__，**直接返回 null 且不回源**。回源函数返回 null 时（数据库里确实没有），写 SET key "__NULL__" EX nullValueTtlSeconds（由 flashmart.cache.null-value-ttl-seconds 配置，默认 30 秒）。短 TTL 是刻意的：既挡住了"同一批不存在的 id 反复打库"，又保证"刚创建的数据不会因为一个陈旧的空标记而长期查不到"。

### 维度② 背景 · 为什么偏偏这么选

**Q5：为什么用逻辑过期，不直接用互斥锁重建？**
【新手版】互斥锁的方案里，没抢到锁的请求要**等**别人重建完，热点 key 过期那一瞬间会有一批请求卡住；逻辑过期是"返回旧值加后台重建"，**所有请求都不等**。秒杀场景下，多等 200 毫秒可能就意味着用户看到的是转圈而不是活动页，所以我选不等。
A：两者的**可用性模型不同**：互斥锁是"**阻塞加强一致**"——没抢到锁的请求自旋或睡眠等重建，代价是过期瞬间一批请求的响应时间被拉长；逻辑过期是"**不阻塞加最终一致**"——所有请求立刻拿到旧值，代价是**短暂的数据陈旧窗口**（在重建完成前，用户看到的是老数据）。对这个项目里的"活动详情"来说，陈旧几十毫秒到几百毫秒完全可以接受（活动标题、价格、时间这些字段几乎不变），而**响应时间不可接受被拉长**，所以选逻辑过期。反过来说，如果是"账户余额"这种绝对不能读到旧值的数据，逻辑过期就是不合适的——**这是选型的边界，不是我漏想了。**

**Q6：那为什么还要额外加一个"完全未命中"的 SETNX 分支？**
【新手版】因为逻辑过期只管"key 还在、但逻辑上过期了"这一种情况。还有一种情况是 key **真的被删掉了**（比如商家改了活动，我把缓存删了），这时候缓存里什么都没有，旧值没得返回，所有并发请求就会一起打到数据库。所以我在"完全未命中"这条路上也加了 SETNX：只放一个线程回源，其他的等一小会儿重读缓存。
A：这是我在实现里补的一个重要分支。逻辑过期解决的是"**缓存还在但过期**"，而 CacheEvictService 删缓存、进程重启、key 被 Redis 淘汰，都是"**缓存真的没了**"——这时没有旧值可以兜，如果不加控制就是经典的冷启动击穿。所以 getWithLogicExpire 里"缓存为 null"的分支做法是：抢 cache:rebuild:lock:{key} 的 SETNX，抢到的线程**同步**回源并写入缓存（写的时候带上逻辑过期时间），finally 删锁；没抢到的 sleep 60 毫秒后重读缓存，读到就用，仍读不到才自己回源兜底。**60ms 的短暂等待加重读，是把"击穿"换成了"短暂排队"。**

**Q7：空值的 TTL 为什么是 30 秒这么短？**
【新手版】因为空值标记是一把双刃剑：它能挡住不存在的 id，但也会把"刚刚才创建出来的数据"挡住。30 秒是一个平衡——足够挡掉攻击流量，又不会让正常的新数据等太久。
A：权衡在于**防护强度和"数据可见性延迟"成反比**：TTL 越长，穿透防护越好，但"数据刚被创建、用户却查不到"的窗口越大。30 秒的取值来自场景判断：① 我的穿透风险主要来自**被刷不存在的活动 id**，这类流量是连续的，30 秒足以把同一批 id 收敛到一次回源；② 反过来，商家刚创建的活动通常是**紧接着就要上架被抢**的，30 秒的可见性延迟在业务节奏上可以接受。同时它由 flashmart.cache.null-value-ttl-seconds 配置，可以在不改代码的前提下按业务调整。另外要能说清一个细节：空值标记**只对"查不到的 key"生效**，它的 key 就是被查的那个数据的 key，不会影响别的数据。

### 维度③ 具体流程（要能画）

**Q8：完整讲一遍读缓存的流程。**
【新手版】先取缓存。取到空值标记就直接返回"没有"。什么都没取到，就抢锁回源，只放一个人去查库，其他人等一小会儿重读。取到了正常值，就看它的逻辑过期时间：没过期就直接用；过期了就**先把旧值返回**，后台再去重建。
A：

    getWithLogicExpire(key, type, logicTtl, loader)
      │
      ├─ ① GET key
      │    └─ == "__NULL__" ──────────▶ 返回 null（穿透已挡住）
      │
      ├─ ② == null（缓存真没了 → 冷启动击穿风险）
      │    ├─ SETNX cache:rebuild:lock:{key} 成功？
      │    │    ├─ 是 → countLoad(key) + loader.get()   ← 同步回源
      │    │    │      ├─ null → SET key "__NULL__" EX 30s → 返回 null
      │    │    │      ├─ 值   → writeWithLogicExpire → 返回值
      │    │    │      └─ finally: DEL lock
      │    │    └─ 否 → sleep 60ms → 重读 key
      │    │           ├─ "__NULL__" → null
      │    │           ├─ 有值且能反序列化 → 返回
      │    │           └─ 还是空 → countLoad + loader.get()（自己兜底回源）
      │
      └─ ③ 命中，解析 {expireAt, data}
           ├─ now > expireAt → asyncRebuild()   ← 先返回旧值，再异步重建
           │      └─ SETNX 抢到锁 → 提交 rebuildPool(4 线程守护池)
           │                        → 回源 + 重写缓存 → DEL lock
           │         SETNX 没抢到 → 直接 return（别的线程在重建，我用旧值就行）
           └─ now <= expireAt → 直接返回 data

**Q9：重建的线程池是怎么配的？为什么用守护线程？**
【新手版】固定 4 个线程的线程池，线程是守护线程，名字叫 cache-rebuild。守护线程的意思是：它不会阻止 JVM 退出，服务停机的时候不会因为还在重建缓存而卡住。重建是"尽力而为"的事，失败了也不影响这一次请求。
A：Executors.newFixedThreadPool(4, ...) 并把线程设成 daemon、命名 cache-rebuild。三个设计点：① **固定 4 个线程**——重建是低频动作（只在逻辑过期瞬间触发一次），4 个足够，同时天然形成背压：即使锁失效、真的并发提交了，也不会无限制创建线程；② **守护线程**——不阻塞 JVM 退出，避免优雅停机被重建任务拖住；③ **异常自吞**——asyncRebuild 的 finally 里删锁，异常被 catch 住只打 log.warn，因为重建失败**不影响本次请求**（本次已经返回旧值了），最坏情况是下一个请求再触发一次重建。

### 维度④ 特殊情况下的兜底策略

**Q10：重建失败了怎么办？**
【新手版】不影响这次请求，因为这次已经返回旧值了。锁会在 finally 里被删掉，所以下一个请求会再触发一次重建，相当于自动重试。最坏情况是缓存一直重建不成功、一直返回旧值——但至少请求不阻塞，数据库也没被打穿。
A：重建失败的处理链路：asyncRebuild 内部 catch 住 Exception 打 log.warn，finally 里 redis.delete(lockKey) 释放互斥锁。所以失败之后**锁不残留**，下一次逻辑过期判断会重新触发一次重建——形成"下一次请求自动重试"的软重试。要诚实说边界：**这个重试没有次数上限、也没有退避**，如果数据库持续不可用，会表现为"每次都触发一次重建、每次都失败"，日志会持续刷 warn（这是可观测的，不是静默失败）；更稳妥的做法是给重建加"失败 N 次后进入冷却期"，我没做，属于已知边界。此外还有一个兜底：**旧值仍在缓存里**（物理 TTL 是逻辑 TTL 的 3 倍），所以系统在"数据库长时间不可用"的情况下仍能降级为"读旧数据服务"，不会整体不可用。

**Q11：逻辑过期期间，用户会不会看到过期数据？**
【新手版】会，这是这个方案主动接受的代价。旧值会一直服务到重建完成，这个窗口通常是重建一次数据库查询的时间（毫秒到几十毫秒级）。对我的活动详情来说没关系——变的只是标题价格这些，而且活动的核心资源（库存）根本不在这个缓存里，是每次实时读 Redis 的。
A：会，而且是**设计上接受的**：逻辑过期本质是"**可用性优先、最终一致**"。两个缓解：① **窗口很短**——重建就是两次 selectById（活动和商品），本地库毫秒级；② **把强一致数据挪出缓存**——活动详情里最敏感的是**剩余库存**，我特意**不把它放进缓存的 VO**，而是在 ActivityService.detail 里每次实时调 currentStock(...) 读 Redis（seckill:stock:{activityId}），未预热时才回退数据库。所以"价格标题可能短暂陈旧，库存永远实时"。这是这套设计里我觉得最值得讲的一个决策：**同一条数据的不同字段，可以用不同的时效策略。**

**Q12：空值标记会不会把"本来有、但当时还没数据"的东西挡住？**
【新手版】会有一个最多 30 秒的窗口。但实际风险很小：活动 id 是自增主键，被查过并写了空标记的 id 不会被新活动复用；而"改了活动"这种动作走的是写路径，会主动把缓存删掉，标记也一起消失。
A：会，窗口上限就是空值 TTL（默认 30 秒）。但要说明这个风险的实际大小：① **主键不会复用**——活动 id 是自增主键，被查过并写了空标记的 id 不会被后面的新活动复用到，所以"同一个 id 从无到有"在自增主键下不会发生；② **真正会发生的是"改了状态"或"改了库存"**，而这类动作走的是写路径，ActivityService.update 里会**先更新数据库、再删缓存**（cacheEvictService.evictWithCompensation），删缓存时把这个 key 上的空标记一并删掉，所以标记不会残留；③ 兜底仍然是那个短 TTL。所以我的判断是：**在自增主键加写路径主动清缓存的组合下，这个窗口的影响可以忽略**，我也把它写成了明确的取舍而不是遗漏。

### 维度⑤ 真正的需求 · 实际产出

**Q13：缓存击穿你怎么验证的？数字是多少？**
【新手版】压测工具里有 cache-miss 实验：先读一次让缓存生效，然后让服务端把缓存删掉并把回源计数清零，再同时并发打 100 次详情接口。结果是：**100 个并发请求全部成功**，而**数据库只被回源了 1 次**，100 个请求的总耗时 **114ms**。修复之前是 100 次。
A：实验步骤（Bench.expCacheMiss）：① 预热读一次详情，确保缓存已写入；② 调 reset 让服务端**同时删掉详情缓存并把该 key 的回源计数清零**（计数 key 是 cache:loadcount: 加活动 key，由 RedisCacheClient.countLoad 在每次真实回源时加 1——**这个埋点是专门为了把结论变成可复现数字而加的**）；③ 用闭锁同时发起 **100 个并发请求**。结果：**100 个请求全部成功拿到详情，缓存回源次数等于 1，100 个请求的总耗时 114ms，修复前是 100**。另外逻辑过期这条路径也单独验证过：**逻辑过期瞬间 100 个并发请求全部成功，只触发 1 次异步重建，整个并发耗时 119ms**——注意这个 119ms 是"100 个并发请求全部拿到响应"的墙钟时间，说明请求**没有被重建阻塞**（如果用的是互斥锁方案，没抢到锁的请求要等重建完成，这个数字会明显变大）。

**Q14：缓存穿透呢？**
【新手版】cache-penetrate 实验：拿一个**不存在的活动 id**，连续并发查 200 次。结果是**累计只回源数据库 1 次**，因为这个 id 查不到之后就被写上了空值标记（30 秒 TTL），后面的 199 次全部命中标记直接返回。
A：Bench.expCachePenetrate 默认查询次数 200，先 resetCacheLoadCount 清零计数，再并发查 200 次不存在的活动。**累计回源次数等于 1**（期望不超过 1）。这个实验里有个很值得讲的细节：工具会先**探测一次**，如果发现 Redis 里已经有空值标记（上一次实验留下的，TTL 30 秒），就打印说明并等待标记过期后重来——**因为如果不处理这个，回源次数会是 0，就观察不到"第一次查询会回源 1 次"这个事实**。这个"等待 TTL 过期再测"的动作，体现的是"我要测的是机制，不是数字好看"。另外服务端返回也要同时看：200 次全部是 HTTP 200 加业务码非 0（业务上"活动不存在"），没有一次意外成功。

### 维度⑥ 方法论（这一段最容易被记住）

**Q15：缓存这一类问题，你有一套统一的思考方式吗？**
【新手版】我把它拆成"读不到"和"读得不对"两大类，再加"扛不住"一类。读不到：不存在的用空值缓存防穿透，热点失效的用逻辑过期或互斥锁防击穿，大批同时失效的打散 TTL 防雪崩。读得不对：用 Cache Aside 保证一致性。扛不住：多级缓存、限流、降级。
A：我的分类框架是**三个问题、五套手法**：
- **读不到（不存在）** → 缓存空值（短 TTL）或布隆过滤器；
- **读不到（热点刚失效）** → 逻辑过期（返回旧值加异步重建，不阻塞）或互斥锁（阻塞等待，强一致）；选哪个看**"陈旧和延迟"哪个更不可接受**；
- **读不到（大批同时失效）** → TTL 加随机扰动、多级缓存、缓存预热；
- **读得不对（一致性）** → Cache Aside 加延迟双删加补偿（第 5 章）；
- **整体扛不住（雪崩、宕机）** → 限流降级（第 6 章）、熔断、多级缓存、热点数据本地缓存。
贯穿所有手法的一条原则是：**先问"这份数据允许陈旧多久"**——允许陈旧的走逻辑过期，不允许陈旧的走互斥锁或干脆不缓存。这个问题的答案决定了选型，而不是反过来。

### 本章追问链（问完第一句之后最可能被追的四句）
1. **"物理 TTL 是逻辑 TTL 的 3 倍，为什么是 3 倍？"** → 保证"逻辑过期之后旧值还能存活足够久"来接住重建窗口。3 倍是个经验余量：逻辑过期 60 秒、物理 180 秒，即使重建连续失败几轮，旧值仍在。它不是算出来的精确值，如果要严谨，应该让它不小于"最长重建耗时加最大抖动"。
2. **"逻辑过期期间 Redis 内存里堆着过期数据，会不会把内存撑爆？"** → 会占用内存，所以物理 TTL 必须设——否则这些"永远逻辑过期"的 key 会永久驻留。我用 3 倍逻辑 TTL 控制上限，同时活动详情这种热点 key 的数量级本身很小（是活动数，不是用户数）。
3. **"为什么用 SETNX 锁而不是 Lua？这里不需要原子吗？"** → SETNX 本身就是原子的（SET key value NX EX）。这里不需要 Lua，因为临界区里没有"读—判断—写"的复合逻辑，只有"抢到就干、抢不到就走"，一个 SETNX 足够。
4. **"空值缓存被大量随机 id 打，Redis 里岂不是写了一堆垃圾 key？"** → 会有这个问题，这是空值缓存的已知副作用：攻击者用随机 id 打，每个 id 都会留下一个 30 秒的 key。缓解手段是 TTL 短（30 秒自动回收）加入口限流（穿透实验里那些请求也要先过限流）；更彻底的做法是布隆过滤器或者在网关层做 id 合法性校验。

### 一分钟口述稿（被要求"讲讲缓存击穿和穿透"时照着说）
"我处理的是两个不同的问题。**穿透**是查一个数据库里也不存在的东西，缓存永远不命中，每次都白跑一趟库——我的做法是**空值缓存**：回源查不到时，往缓存里写一个 __NULL__ 标记，TTL 30 秒，30 秒内同一批不存在的 id 只会回源一次，实测 200 次查询不存在的活动，累计只回源 1 次。**击穿**是热点 key 在某个瞬间失效，N 个并发同时扑向数据库——我用的是**逻辑过期**：缓存值里额外存一个 expireAt，物理 TTL 设成逻辑 TTL 的 3 倍，所以逻辑过期后 key 还在、旧值还读得到；读取时发现逻辑过期，就**先把旧值返回**，同时用 SETNX 抢锁、派一个后台线程去重建。这样重建期间所有请求都不阻塞。实测逻辑过期瞬间 100 个并发请求全部成功，只触发 1 次异步重建，整个并发耗时 119ms。另外我还补了一个容易漏的分支：如果缓存是**真被删了**（不是逻辑过期），旧值没得返回，那我就用 SETNX 只放一个线程同步回源、其他线程睡 60 毫秒重读——实测缓存被删后 100 个并发只回源 1 次，修复前是 100 次。最后一个设计我想强调：活动详情里**剩余库存这个字段我故意不放进缓存**，每次实时读 Redis，所以'标题价格可能短暂陈旧，库存永远实时'。"

## 第 5 章 · bullet ④：Cache Aside + MQ 补偿 + 延迟双删 + TTL

### 5.0 这句话里他会盯的词
**先更新数据库、再删除缓存**（为什么是这个顺序？反过来行不行？）、**删除失败投递 MQ 补偿**（怎么知道失败了？重试几次？）、**延迟双删**（延迟多久？为什么要再删一次？）、**TTL 兜底**（兜的是什么底）。

### 维度① 它是什么 · 怎么用 · 为什么用

**Q1：Cache Aside 是什么？**
【新手版】就是"缓存和数据库各管各的"：读的时候先查缓存，缓存没有就查数据库再写回缓存；写的时候**先更新数据库，然后把缓存删掉**，不是去改缓存。删掉之后下一个读请求自然会把最新数据重新装进缓存。
A：Cache Aside（旁路缓存）是使用最广的缓存一致性模式，读写路径分开：
- **读**：GET 缓存，命中就返回；未命中就查数据库，再写回缓存，再返回。
- **写**：**更新数据库，然后删除缓存**（不是更新缓存）。
我的实现里读路径是 RedisCacheClient.getWithLogicExpire（带逻辑过期），写路径在 ActivityService.update：先 activityMapper.updateById(activity)，再 cacheEvictService.evictWithCompensation(ActivityCacheKeys.detail(activityId))。**注意"删除"而不是"更新"是这个模式的关键。**

**Q2：为什么是"删除缓存"而不是"更新缓存"？**
【新手版】因为并发更新的时候，两个请求写缓存的先后顺序是没法保证的。A 先把新值写进去，B 后把自己的旧值写进去，缓存里就留下了一个旧值，而且它不会自己过期。删除就没这个问题——删掉之后谁来读谁回源，读到的必然是数据库当前的值。
A：**更新缓存的写法在并发下会产生"后写的旧值覆盖先写的新值"**：两个请求各自"更新库加更新缓存"，如果 A 的库更新在前、B 的库更新在后，但 B 的缓存写入恰好晚于 A（网络抖动、GC 停顿都可能造成），那么缓存里留下的是 B 那份。而且这个脏值**不会自己恢复**，要等 TTL 到期。删除缓存的写法天然规避了这个问题：删除是**幂等且无序**的操作——谁先删谁后删，结果都是"缓存里没有"，下一次读必然回源拿最新值。代价是**一次缓存 miss 和一次回源**，用一次数据库读换掉了脏数据的风险，我认为非常划算。

**Q3：为什么是"先更新数据库、再删缓存"，不能反过来？**
【新手版】反过来的话（先删缓存、再更新库），会出现这个窗口：你删了缓存，另一个请求进来发现缓存空了，回源读到的还是**数据库里的旧值**，把它写回缓存；然后你才更新数据库。结果数据库是新的、缓存是旧的，而且这个不一致会一直留着。先更新库再删缓存，那个窗口就小得多。
A：两种顺序的不一致窗口大小完全不同：
- **先删缓存、再更新库（不推荐）**：删缓存之后、更新库之前的窗口里，任何读请求都会**回源读到旧值并写回缓存**，然后库才更新成新值——结果是**缓存长期陈旧**（要等 TTL 才能恢复）。而且这个窗口不短（包含一次数据库更新的耗时）。
- **先更新库、再删缓存（Cache Aside 标准做法）**：不一致窗口是"更新库之后、删缓存之前的读请求读到了旧值"——但这个读请求要么在删缓存**之前**就把旧值写回缓存（那它随后就被删掉了），要么在删缓存**之后**才写回（这就是脏值，需要延迟双删处理）。窗口**明显更小**。
所以顺序不是随便定的：**先更新库、再删缓存，把"可能残留脏值"的窗口压缩到最小**，剩下的用延迟双删清掉。

### 维度② 背景 · 为什么偏偏这么选

**Q4：这个项目的缓存一致性需求到底是什么？**
【新手版】我的场景是"商家改活动"——改库存、改时间。这本身是**低频写、高频读**的场景，不是那种读写都很猛的业务。所以我需要的不是强一致，而是"改完别让用户一直看到老的活动信息"，也就是最终一致，而且不能因为一致性把读路径拖慢。
A：三个特征决定了方案：① **写少读多**——商家改活动的频率远低于买家看详情和抢购；② **读路径要快**——活动详情在抢购链路上被每次请求读一次，绝不能为了一致性加锁或加同步等待；③ **可以接受短暂不一致**——用户看到几秒前的活动标题、价格没有问题（但库存不能错，所以库存单独放 Redis 实时扣）。所以目标定为**最终一致**，并且**把一致性成本全部放在写路径上**（写的时候多删一次、多投一条消息），读路径保持纯粹的"读缓存"。

**Q5：那为什么还要补偿、双删、TTL 这三层，一层不够吗？**
【新手版】三层管的是三件不同的事。**补偿**管"删除动作本身失败了"——比如 Redis 网络抖了一下，删没删掉我不知道。**延迟双删**管"删除成功了，但并发读又把旧值写回来了"。**TTL** 管"前面全都失效了"——就算补偿也失败、脏值也写回来了，到点它自己会消失。三层各管一段，合起来才是最终一致。
A：三层负责的失败模式是正交的：
- **MQ 补偿** → 负责**"删除操作没成功"**：cacheClient.evict 返回 false 时，落一条 cache_sync_task（status 是 PENDING）并投 topic_cache_evict 让消费者重试；
- **延迟双删** → 负责**"删除成功了但脏值被并发读回了"**：更新库，再删缓存，延迟后再删一次，把那个回填的旧值清掉；
- **TTL 兜底** → 负责**"前两层都失败"**：缓存的物理 TTL（逻辑 TTL 的 3 倍）保证了脏值最终一定会消失。
**一句话总结：补偿保"删得掉"，双删保"删得干净"，TTL 保"最终会干净"。** 三个词在简历上是并列的，但它们不是三个同义反复。

**Q6：TTL 兜底听起来很弱，为什么不追加强一致？**
【新手版】因为我衡量过代价。强一致要么用分布式锁把读写串起来（读路径被拖慢，抢购接口是要抗并发的），要么用数据库事务加缓存同步提交（更复杂还更容易出错）。而我的数据是"活动标题、价格、时间"这类，陈旧几秒完全能接受。库存那种不能错的，我压根没放缓存。
A：这是**权衡后的主动选择**，理由有三：① **数据分级**——真正不能错的数据（库存、订单状态）根本不在这个缓存里；② **代价不对称**——强一致（分布式锁、订阅 binlog 同步）会把复杂度加到读路径上，而我的读路径是抢购主链路，它比"活动标题陈旧几秒"重要得多；③ **兜底是确定的**——TTL 让不一致有**上界**（物理 TTL），不是"可能永远脏"。所以我的表述是"**最终一致，且不一致时长有上界**"，而不是含糊的"保证了一致性"。

### 维度③ 具体流程（要能画）

**Q7：商家改活动，完整链路是什么？**
【新手版】先更新数据库，然后试着删一次缓存。删成功了，再投一条延迟消息，过一会儿把缓存再删一遍（清掉并发读可能写回来的旧值）。删失败了，就落一条待补偿记录、并投一条消息让消费者重试删；重试还是失败，记录标成失败，但缓存自己的 TTL 到点也会让它消失。
A：

    ActivityService.update(活动)  ── @Transactional
      │
      ├─ ① UPDATE flash_activity（totalStock / availableStock / startTime / endTime）
      │      注意：已售出数量保持不变，availableStock = max(0, 新总库存 - 已售)
      │
      └─ ② cacheEvictService.evictWithCompensation("activity:detail:{id}")
           │
           ├─ evict(key)：cacheClient.evict → redis.delete(key)
           │    │
           │    ├─ 成功 → return（继续走双删）
           │    └─ 失败 → 落 cache_sync_task(status=PENDING, retry_count=0，之后由消费者累加)
           │              + sendAsync(topic_cache_evict, reason="UPDATE")
           │
           └─ 延迟双删：sendAsync(topic_cache_evict, reason="DOUBLE_DELETE",
                                   delayLevel=nearestDelayLevel(delaySeconds))
                        delaySeconds = doubleDeleteDelaySeconds（配置项 double-delete-delay-seconds，默认 5）

    CacheEvictConsumer（topic_cache_evict / cg_cache_evict / consumeThreadMax=32）
      → tryAcquire(msgId) 幂等
      → cacheClient.evict(event.cacheKey())
           ├─ 失败 → markTask(FAILED) + markFailed(msgId) + 抛异常 → MQ 阶梯重试
           └─ 成功 → reason 为 UPDATE 时 markTask(SUCCESS)（回写条件是 status != SUCCESS，retry_count 在这里累加）
                     markSuccess(msgId)

**Q8：为什么删除失败要落一张表，直接投消息重试不行吗？**
【新手版】因为消息也是会丢的、重试也是会到上限的。落一张表之后，我就有了一个**可以查、可以告警、可以人工重放**的地方——"哪几个 key 现在还没删掉"这个问题有答案。表加消息，等于"可观测加重试"两件事都占上了。
A：cache_sync_task 表提供的是**持久化的待办清单**：cache_key、status（PENDING、SUCCESS、FAILED）、retry_count、error_msg。它的价值在于：① **可观测**——能直接查 status 为 PENDING 的记录看到积压量，这是告警和排查的入口；② **可人工介入**——消息重试到死信之后，运维可以按这张表重放；③ **状态可闭环**——消费者删除成功后会 markTask(key, SUCCESS)，更新条件是 status 不等于 SUCCESS：这样一条失败过的任务在重试成功后也能回到 SUCCESS，同时已经 SUCCESS 的任务不会被重复改写；而且每次回写都会把 retry_count 加一，所以"到底重试了几次"在表里是看得见的（这个字段以前恒为 0，是代码评审时发现的）。**消息是"执行手段"，表是"状态真相"**，这是我在上个项目里学到的分工方式。

**Q9：延迟双删的延迟时间是怎么定的？**
【新手版】代码里配的是 5 秒（double-delete-delay-seconds），投递时取 RocketMQ 最接近且不小于它的延迟档位——RocketMQ 只支持固定档位（1 秒、5 秒、10 秒……），5 秒正好是其中一档，所以实际生效的延迟就是 5 秒。这个时间的量级要**大于"一次读请求回源并把旧值写回缓存"的耗时**，才能覆盖住那个窗口。
A：两个层面：① **配置层**：flashmart.cache.double-delete-delay-seconds 配的是 5；之前的写法是毫秒配置 double-delete-delay-millis: 500，代码里还要用 max(1, 毫秒 除以 1000) 折算，配置值和实际生效值对不上（配 500 毫秒、实际 1 秒），所以直接改成秒配置，配多少就是多少；② **投递层**：RocketMQ 的延迟消息只支持固定档位（1s、5s、10s、30s、1m 等等，见 MqProducer.DELAY_LEVEL_SECONDS），nearestDelayLevel(5) 会选到第 2 档也就是 5 秒，正好落在档位上，不需要向上取整。所以**当前实际生效的延迟是 5 秒**。定这个时间的依据是：它必须**大于"最慢的一次读请求走完查库到写回缓存的时间"**，否则第二次删除还是会晚于脏值回填，等于白删。5 秒对一个本地库查询来说有充足余量；如果数据库慢到这个量级，这个值要相应放大。

### 维度④ 特殊情况下的兜底策略

**Q10：延迟双删其实是个概率手段，你怎么看？**
【新手版】对，它不能完全消除不一致，只能把窗口压得很小。真正严格的做法是**删除缓存时带上版本或时间戳**，回填时校验"我读到的数据是不是比缓存里的新"，或者干脆让缓存写入方别乱回填。我现在用的是"延迟加再删一次"这种工程上最省事、效果也够的方案，TTL 是最后的兜底。
A：是的，延迟双删**不是严格正确的算法，而是一个概率上的缓解**——它假设"最慢的那次旧值回填"发生在延迟时间之内。理论上只要有一个读请求被 GC 停顿、被网络抖动卡住超过延迟时间，它仍然可能把旧值写回缓存。更严格的方案有三类：① **回填时校验**——写缓存前比对自己读到的数据版本或更新时间是否仍是最新的（类似 CAS 回填）；② **版本号缓存**——缓存值里带 version，删除时不删 key 而是把版本加一，回填的旧版本自然失效；③ **放弃"读时回填"**——改为由 binlog 订阅（Canal 之类）在库侧统一驱动缓存更新，读写两条路彻底解耦。我目前选延迟双删的理由是**实现成本最低且能覆盖绝大多数窗口**，再加上 TTL 让不一致有上界；如果业务对一致性要求提高到"秒级也不能脏"，我会升级到方案①或③。**能说清"我知道它不是严格的、以及严格的怎么做"，比声称它完全一致更可信。**

**Q11：删除缓存成功了，但消息投递失败了怎么办？**
【新手版】分两种情况。**删除失败**那条路：表已经落库了，所以消息没投出去也不丢事实——数据还在，我可以扫表补发。**双删那条路**：删成功了但延迟消息没投出去，那次"第二次删除"就丢了，脏值只能靠 TTL 消失。这是我知道的薄弱点。
A：分两条路说，不能混：
- **补偿路径（删失败）**：事实已经落进 cache_sync_task（PENDING），所以**消息投递失败不会丢事实**——这张表本身就是待办清单，可以由定时任务扫 status 为 PENDING 且 update_time 超时的记录重新投递。当前代码没有这个扫表任务，属于待补项，但**数据基础已经在了**。
- **双删路径（删成功）**：这条延迟消息丢了，第二次删除就没了，脏值只能等物理 TTL（逻辑 TTL 的 3 倍）自然消失。这条路的可靠性依赖 RocketMQ 的持久化，**没有二次兜底**——这是当前设计里明确的一个薄弱环节，我会主动说出来。

**Q12：如果 Redis 整个挂了，写路径会怎样？**
【新手版】删缓存会失败（抛异常被 cacheClient.evict 捕获、返回 false），于是走补偿：落一张表加投一条消息。此时所有读请求也都会 miss，全部回源数据库——这就是雪崩。所以真到这一步，要靠限流（第 6 章）把入口流量压下来，保住数据库。
A：写路径的行为是**降级但不丢数据**：RedisCacheClient.evict 把异常吞掉并返回 false，CacheEvictService.evict 于是落 cache_sync_task 加投消息，**数据库的更新是成功的**（它在缓存操作之前，而且在一个事务里）。读路径则会全面 miss，回源压力全部落到数据库——getWithLogicExpire 的未命中分支会用一个 SETNX 去抢锁，但 Redis 挂了 SETNX 也会失败，实际表现是所有请求都自己回源。所以 Redis 全挂时的保护只能靠**入口限流加数据库连接池上限**（Hikari maximum-pool-size 是 20、connection-timeout 是 3000）来限制破坏面。我会诚实说：**这个项目没有做 Redis 高可用（哨兵或集群）和不依赖缓存的降级开关**，属于单机演示环境的边界。

**Q12b：缓存里的活动价格会不会导致"按旧价成交"？**
【新手版】会——如果商家改了价、缓存还没删掉，用户就会按旧价下单。所以我在**消费者落库前加了一道校验**：从数据库读当前价格，和用户看到的价格比对，不一致就**拒单**、把名额退回、让他刷新重抢。
A：这是我复盘时**自己找出来的隐患**，已经修掉。链路是：用户看到的价格来自缓存的活动详情，抢购时这个价格被带进消息、最终写成订单的成交价；而"商家改活动 → 删缓存"虽然做了补偿重试 + 延迟双删 + TTL 三层兜底，但**只能缩小窗口、不能消除窗口**——补偿本身也可能失败。那个窗口里按旧价成交，就是纠纷或资损。
修法遵循一条原则：**缓存只负责展示，成交前必须回权威源校验**。具体做法是把校验放在**消费者侧**（`OrderService.createOrder` 的第 0 步）：从数据库读活动当前价格，与消息里的价格比对；不一致就抛 `PriceChangedException`（**终态失败**），此时**既不扣数据库库存、也不插订单**（整个事务回滚）；消费者捕获后回滚 Redis 预扣的库存与名额、给前端标记"**价格已变化，名额已退回，请刷新页面后重新抢购**"，并把消息标记为已处理——**不做 MQ 重试**，因为重试多少次价格都不会变回来。
为什么放在消费者而不是抢购接口：抢购接口的原则是"**不碰数据库**"（28ms 靠的就是这个），为价格多查一次库就把原则破了；而消费者本来就要访问数据库，这次校验是**零额外成本**。
为什么不直接按新价成交：那样会出现"展示 399、实际扣 499"，**比拒单更糟**。抢购场景里最安全的是拒单让用户重来——反正价格变了，他本来就该重新看一遍。
**单测覆盖三种情况**：价格一致 → 正常成交（扣库存 + 插订单）；价格被改过 → 抛 `PriceChangedException` 且**库存一行都不许扣、订单一条都不许插**；活动不存在 → 拒单。

### 维度⑤ 真正的需求 · 实际产出

**Q13：一致性这套东西，你实测了吗？**
【新手版】这部分我**没有做专门的压测实验**——不像扣库存和一人一单那样有 28ms、157ms 这种可复现数字。压测工具里有一个 pay 实验会顺带验证"支付后订单不再被关单回滚库存"，超时实验会验证库存回滚前后 Redis 和数据库的剩余库存各加 1、能对上。一致性窗口这块我目前只能讲原理和设计，没有量化数字。
A：如实说明：**一致性方案我没有做独立的量化实验**（这是这个项目里我认为最该补的一块）。已实测的、能间接支撑的是：① Bench.expTimeout 会打印 reset 后、抢购落库后、关单后三个时点的 totalStock、dbAvailableStock、redisAvailableStock、orderCount、ordersByStatus，并断言**关单后 Redis 和数据库的剩余库存各加 1**——这验证了"缓存（Redis 库存）与数据库的最终一致"在关键路径上成立；② Bench.expPay 验证支付后订单不会被执行超时回滚（终态为 PAID）；③ 缓存侧有 cacheLoadCount 埋点，能观测到回源次数。**要设计一个能证明"延迟双删把脏值清掉了"的实验**，思路是：并发读写同一个 key，读侧故意在回源后 sleep 一小段再写回缓存（模拟慢回填），然后断言延迟窗口过后缓存里是新值。这个实验我没做，所以我不编数字。

▸ **追问：那你凭什么说这套方案是对的？**
【新手版】凭的是"每一个失败模式都有对应的兜底，而且每层兜底的范围我说得清楚"。我讲不出一个漂亮的一致率数字，但我能画出所有失败路径，也能指出哪条路径现在没有兜底（双删那条消息丢了）。
A：我不声称"一致率满分"，我声称的是**"不一致的窗口有上界，且失败路径都有明确归宿"**：删失败就有表有消息可重试；删成功但脏值回填就走延迟双删；全部失败还有物理 TTL。同时我明确标出缺口：① 双删消息丢失没有二次兜底；② cache_sync_task 没有扫表补发任务；③ 没有量化实验。**面试里我更愿意展示"我知道自己的方案在哪儿薄弱"，而不是把它讲成完美无缺。**

### 维度⑥ 方法论（这一段最容易被记住）

**Q14：缓存一致性，你的通用方法论是什么？**
【新手版】四步：第一步，先给数据分级——哪些能陈旧、哪些不能，不能的干脆别缓存。第二步，读少写多的场景用 Cache Aside：先更新库、再删缓存。第三步，把"删除失败"和"脏值回填"这两个失败模式分别兜住：补偿重试加延迟双删。第四步，永远给缓存设 TTL，让不一致有上界。
A：我的四步法：
1. **数据分级决定策略上限**——先问"这份数据能陈旧多久"。不能陈旧的（库存、余额）**不要放进这个缓存体系**，用别的机制（实时读 Redis、强一致存储）；能陈旧的才走缓存一致性方案。这一步做错，后面再精巧也是错的。
2. **写路径用 Cache Aside（先库后删），不更新缓存**——删除是幂等的、无序安全的，更新是顺序敏感的。
3. **失败模式逐一对号**——"删失败"用**补偿重试（消息加待办表）**；"删成功但脏值回填"用**延迟双删**；两者都失败用 **TTL** 兜底。记住这三层管的不是同一件事。
4. **一致性要给上界**——任何"最终一致"方案都必须能回答"最坏情况多久一致"。如果答案是"不确定"，那说明 TTL 或者对账机制缺了。
再补一条经验：**写路径可以变慢，读路径不行**。所有一致性的成本都应该加在写侧（多删一次、多投一条消息），读侧保持"先查缓存"这一条直线。

### 本章追问链（问完第一句之后最可能被追的四句）
1. **"延迟双删延迟多久最合适？"** → 大于"最慢一次读请求从查库到写回缓存的耗时"。我配的是 5 秒（double-delete-delay-seconds=5，正好落在 RocketMQ 的 5 秒档位上，不存在向上取整）。它是个经验值，要覆盖住的是并发读的回填耗时，不是固定的业务时间。
2. **"为什么不用 Canal 订阅 binlog 来更新缓存？"** → 那是更彻底的做法（读写路径解耦、不依赖业务代码记得删缓存），代价是要多维护一套中间件和数据链路。我这个项目的体量下，Cache Aside 加补偿加双删加 TTL 已经够用；如果写路径变多、多地部署，"谁改数据谁负责删缓存"这种约定就很容易漏，那时就该上 binlog 方案。
3. **"如果商家改活动的时候，正好有用户在抢购，会读到旧库存吗？"** → 不会，因为**库存不走这个缓存**：活动详情缓存里只有标题、价格、时间这类静态字段，剩余库存是每次实时从 seckill:stock:{activityId} 读的。而且商家改库存时 ActivityService.update 会调 stockService.reset(...) 强制覆盖 Redis 的库存与总库存（不走带 10 秒互斥的预热，避免 10 秒内连改两次时第二次不生效），Redis 侧的库存和数据库是同一时刻写的。
4. **"缓存和数据库最终一致，那'最终'是多久？"** → 上界是物理 TTL（逻辑 TTL 的 3 倍，默认就是 180 秒）；正常路径下是"更新库再删除缓存"这一瞬间，加上最坏情况下延迟双删的 5 秒。所以正常情况下是毫秒级，极端情况下是分钟级。

### 一分钟口述稿（被要求"讲讲缓存一致性"时照着说）
"我用的是 **Cache Aside**：写的时候**先更新数据库、再删除缓存**，而不是更新缓存。为什么删不更新——并发更新时两个请求写缓存的顺序没法保证，会出现后写的旧值覆盖先写的新值，而且不会自愈；删除则天然幂等、无序安全，代价只是下一次读回源一次。为什么是'先库后删'——反过来的话，删完缓存到更新库之间那个窗口里，读请求会把数据库的**旧值**读回来写进缓存，然后库才更新，缓存就长期脏了；先库后删把这个窗口压到最小。**剩下的两个失败模式我分别兜**：第一个是'删除动作失败了'——我会落一张 cache_sync_task 待办表并投一条 MQ 消息让消费者重试，表是状态真相、消息是执行手段，重试到上限还能人工按表重放；第二个是'删除成功了，但有个并发读请求在删之前读到旧值、删之后才写回缓存'——这就是**延迟双删**：过一小段时间（我配 5 秒，正好是 RocketMQ 的延迟档位）再删一次，把回填的脏值清掉。**最后 TTL 兜底**：物理 TTL 是逻辑 TTL 的 3 倍，保证不一致的时间有上界，不会永远脏。这三层不是重复——补偿保'删得掉'，双删保'删得干净'，TTL 保'最终会干净'。边界我也说清楚：延迟双删是概率缓解不是严格正确，双删那条消息丢了现在没有二次兜底，一致性这块我也**没有做量化实验**，不编数字。"

## 第 6 章 · bullet ⑤：Redis ZSet + Lua + AOP 注解滑动窗口限流

### 6.0 这句话里他会盯的词
**滑动窗口**（和固定窗口差在哪？）、**ZSet 加 Lua**（为什么是这两个？）、**AOP 注解**（怎么做到一个注解就限流？）、**全局、IP、用户三个维度**（分别防谁？）、**脚本刷单**。

### 维度① 它是什么 · 怎么用 · 为什么用

**Q1：滑动窗口限流是什么？**
【新手版】就是"看最近 N 秒内有多少请求"。比如最近 1 秒内这个用户已经请求了 3 次，上限是 5 次，那第 4、第 5 次放行，第 6 次就拦住。窗口跟着当前时间往前走，所以叫"滑动"。
A：滑动窗口限流把时间轴看成"以当前时刻为右端点、长度为 N 秒的一个窗口"，在这个窗口内统计请求数：
- 请求到来时，**先清掉窗口外的历史记录**（时间戳早于 now 减去 N 乘 1000 的）；
- 再统计窗口内**还剩多少条**；
- 小于阈值就**记录本次请求**并放行，否则拒绝。
我的实现窗口是**毫秒级精度**：ZSet 的 score 是请求时间戳（毫秒），ZREMRANGEBYSCORE 负责清理，ZCARD 负责统计，ZADD 负责写入。

**Q2：为什么用 Redis 的 ZSet？**
【新手版】因为 ZSet 是"有序集合"，它能按分数（我存的是时间戳）排序和按范围删除——正好对应"把窗口外的老请求清掉"这个动作。用 List 或者普通计数器做不到"按时间范围清理"。
A：ZSet 的能力和滑动窗口的需求精确对齐：① **按 score 做范围删除**——ZREMRANGEBYSCORE 一次清掉所有过期成员，这是滑动的核心动作；② **基数统计**——ZCARD 是 O(1) 得到窗口内请求数；③ **member 唯一性**——每个请求用唯一成员（我用 traceId 加 UUID），所以同一毫秒内的并发请求不会互相覆盖；④ **整体过期**——PEXPIRE key windowMillis，没人访问时 key 自动回收，不会留垃圾。相比之下：固定窗口计数器只需一个 INCR，但会有"窗口边界双倍放行"问题；令牌桶用 Hash 存令牌数和上次补充时间，允许突发。

**Q3：为什么这三步必须用 Lua？**
【新手版】因为"清理、统计、写入"如果分成三条命令，中间会被别的请求插进来：两个请求都统计到"还没超限"，于是都放行——限流就漏了。Lua 让这三步在 Redis 里一口气跑完，中间不被打断。
A：分三条命令就是一个典型的 check-then-act 竞态：请求 A 和 B 同时 ZCARD 都得到 4（上限 5），都判断"没超限"，然后都 ZADD——窗口内变成 6 次，**超发**。这和第 2 章库存超卖是同一类问题，解法也一样：**把判断和执行合进一个原子单元**。Redis 执行 Lua 期间不会穿插其他命令，所以"清理、统计、写入"要么全做完、要么没开始。

**Q4：AOP 注解是怎么实现的？**
【新手版】我定义了一个注解 @SlidingWindowLimit，上面写业务键、窗口大小、最大次数、限流维度。然后写了一个切面，只要方法上有这个注解，请求进来就先被切面拦一下，算一下限流 key、调限流器判断，超了就直接抛"请求过于频繁"异常，没超才真正执行方法。
A：三段：① **注解** @SlidingWindowLimit 带 key、windowSeconds、maxRequests、dimension、message 五个属性，dimension 是一个枚举（GLOBAL、IP、USER）；② **切面** SlidingWindowAspect 用 @Around 拦截所有带该注解的方法，从 MethodSignature 上取出注解实例，按维度算出身份、拼出 bucket key 和 member；③ **限流器** SlidingWindowLimiter.tryAcquire 执行 Lua，返回 false 就 throw BizException.tooManyRequests(message)。异常被 GlobalExceptionHandler 接住，业务码等于 429 时把 HTTP 状态码也设成 429。

**Q5：这些限流规则都加在哪些接口上？**
【新手版】三个：抢购接口按用户 1 秒 5 次，支付接口按用户 1 秒 3 次，登录接口按 IP 1 秒 20 次。选这三个是因为它们分别是"最容易被脚本刷的入口""涉及钱的入口""最容易被撞库的入口"。
A：代码里目前三处：
| 接口 | key | 窗口与阈值 | 维度 | 防什么 |
| --- | --- | --- | --- | --- |
| POST /api/seckill/{activityId} | seckill | 1 秒 / 5 次 | USER | 脚本刷单——刷进来一次就消耗一份库存 |
| POST /api/order/{orderNo}/pay | order_pay | 1 秒 / 3 次 | USER | 脚本反复调支付 |
| POST /api/auth/login | login | 1 秒 / 20 次 | IP | 撞库、暴力破解 |
限流规则写在注解上而不是配置文件里，好处是**规则和它保护的接口在一起**，看代码就知道这个接口被什么规则保护；代价是改阈值要重新发布。如果要动态调整，正确做法是把阈值挪到配置中心或数据库，注解只留业务键。

### 维度② 背景 · 为什么偏偏这么选

**Q6：为什么需要限流？不做会怎样？**
【新手版】因为抢购接口是最容易被脚本刷的地方。脚本一秒能点几百次，人只能点一次；而且每一次抢购请求都会真的去消耗库存和消息队列的资源。没有限流，一个脚本就能把整个活动的流量结构打乱。
A：抢购接口有三个"必须限流"的属性：① **写动作**——每次成功都消耗一份真实库存，不是只读接口；② **无状态、易被自动化**——攻击者用脚本可以稳定获得比人高几个数量级的请求速率；③ **链路长**——一次请求要过 Redis 脚本加 MQ 投递，被刷时这些资源都被无效消耗。限流的作用是**把"请求速率"这个维度的攻击成本抬起来**，保护的是后端的资源而不是接口本身。同时它也是一道**过载保护**：真出现流量异常（比如活动被分享到群里），限流能让系统在可承受的速率上稳定服务，而不是全量雪崩。

**Q7：为什么用滑动窗口，不用固定窗口或者令牌桶？**
【新手版】固定窗口有个老问题：第 1 秒的最后一下和第 2 秒的最前一下，加起来在很短时间内能放过两倍的量，因为它是按"每秒清零"算的。令牌桶是允许突发的（桶里攒着令牌），适合"平时攒、活动时放开跑"。我这个场景要的是**精确限次**——防脚本刷单，不能让它钻窗口边界的空子，所以用滑动窗口。
A：三种算法在这个场景下的对比：
- **固定窗口计数器**（INCR 加 EXPIRE）：最简单，但有**临界问题**——阈值 5 时，第 1 秒末和第 2 秒初可以在几十毫秒内放行 10 次。对"防脚本"来说这是致命的，脚本恰好就会利用这个特性。
- **令牌桶**（我上一个项目用的）：允许**突发**（桶里攒够令牌可以一次性消耗），适合"用户操作有突发、但要给个上限"的场景，比如投递简历。它**不保证**"最近 1 秒最多 N 次"这个精确语义。
- **滑动窗口**：精确统计"最近 N 秒内的请求数"，**不允许借未来的额度**。我要防的是脚本刷单和爬接口，本质诉求就是"精确限次"，所以选它。
一句话：**令牌桶是"限速加允许突发"，滑动窗口是"精确限次"，我的场景要的是后者。** 这也是和上一个项目刻意区分的地方——同一个问题两种解法。

**Q8：为什么要有"多维度"？一个维度不够吗？**
【新手版】不够，因为三种攻击长的不一样。**用户维度**防"一个账号狂刷"；**IP 维度**防"一台机器开一堆小号"（这时候每个号都没超限，但机器超了）；**全局维度**防"整个接口被打爆"，是保护下游资源的最后一道闸。三个维度是三种视角，互相补位。
A：三个维度对应三种不同的粒度，各自防的攻击面不同：
- **USER**：身份粒度。防"单账号脚本刷单"——即使一个人用多台机器，只要还是这个账号，就受同一个额度限制。它的前提是**身份可信**，所以必须取自服务端上下文（见 Q9）。
- **IP**：网络粒度。防"单机多账号"——注册一批小号轮流刷，每个账号都没超限，但请求都来自同一个 IP。我的登录接口用的就是 IP 维度（撞库的特征是同一来源大量尝试）。
- **GLOBAL**：系统粒度。防"整个接口被打爆"，它不看身份也不看来源，只看总量，是**保护下游资源**（数据库、Redis、MQ）的最后一道闸门。它的意义在于：即使前两个维度都被绕过（攻击者用海量代理 IP 加海量账号），总量上限仍然能保住系统不雪崩。
补充一个维度选择的原则：**越靠前的接口越应该用粗粒度（IP 或全局），越靠业务核心的接口越应该用细粒度（用户）**。我这里是登录用 IP、抢购和支付用用户。

### 维度③ 具体流程（要能画）

**Q9：限流的 key 怎么拼？身份从哪儿来？**
【新手版】key 的格式是 rate 冒号 业务键 冒号 维度 冒号 身份，比如 rate:seckill:USER:9003。身份一律从**服务端的登录上下文**里取，绝对不从请求参数里取——否则攻击者只要把别人的用户 ID 填进去，就能把别人的额度耗光，把人锁在门外。
A：bucketKey 的拼法是 "rate:" 加上注解的 key、维度、身份三段。身份按维度分流：
- USER → UserContext.userId()（为空时用 "anonymous"）；
- IP → 已登录的请求取 UserContext 里的 clientIp（拦截器解析 JWT 时从请求里写进去的）；**登录、注册这类不走拦截器的接口，UserContext 是空的，这时切面直接从当前 HTTP 请求里取真实 IP**（X-Forwarded-For 的第一段，取不到再用 RemoteAddr），两层都拿不到才落到 "unknown-ip"——不然所有登录请求会挤进同一个桶，IP 维度退化成全局限流，一个人刷就能把别人挡住；
- GLOBAL → 固定字符串 "global"。
UserContext 是由 AuthInterceptor 在解析 JWT 之后写入 ThreadLocal 的，**攻击者无法伪造**。这一条是限流方案里最容易被做错的地方：**信任边界必须在服务端**。成员（ZSet 的 member）用 TraceUtil.current() 拼接 UUID.randomUUID()，保证同一毫秒内的并发请求也不会互相覆盖。

**Q10：完整画一下限流的过程。**
【新手版】请求进来，AOP 切面看到方法上有注解，从上下文取身份，拼出 key，调 Lua：先删掉窗口外的、再数一数窗口内有多少、没超就记下这次请求并设置过期时间，返回 1 放行或 0 拦截，拦截就抛 429，放行才执行真正的方法。
A：

    请求 ──▶ SlidingWindowAspect.around()
              │ 读取方法上的 @SlidingWindowLimit
              │ identity = 按 dimension 从 UserContext 取（USER / IP / GLOBAL）
              │ bucketKey = "rate:" + key + ":" + dimension + ":" + identity
              │ member    = traceId + "-" + UUID          ← 同毫秒并发也不覆盖
              ▼
           SlidingWindowLimiter.tryAcquire(bucketKey, windowSeconds, maxRequests, member)
              │ EVAL lua/sliding_window.lua
              │      KEYS = [bucketKey]
              │      ARGV = [now(ms), windowSeconds, maxRequests, member]
              ▼
       ┌───────────────────────────────────────────────────┐
       │ ① ZREMRANGEBYSCORE key 0 (now - window*1000)       │ ← 滑动：丢掉窗口外的
       │ ② count = ZCARD key                                │ ← 统计窗口内请求数
       │ ③ if count >= maxRequests then return 0 end        │ ← 超限，不写入
       │ ④ ZADD key now member                              │ ← 记录本次
       │    PEXPIRE key windowMillis                        │ ← 没人访问自动回收
       │    return 1                                        │
       └───────────────────────────────────────────────────┘
              │
              ├─ 1 → point.proceed()（执行真正的业务方法）
              └─ 0 → throw BizException.tooManyRequests(message)
                       → GlobalExceptionHandler：业务码 429 → HTTP 429
                         + R.fail(429, "手速太快啦，歇一秒再抢")

    Lua 原子性保证：①②③④ 之间不会插入其他命令，
    所以不存在"两个请求都数到 4 然后都放行"的超发。

**Q11：Redis 挂了，限流会怎样？**
【新手版】会直接放行。tryAcquire 里 catch 住异常、打一条 warn 日志、返回 true。这是刻意的：限流是保护手段，不能因为限流组件自己挂掉，就把整个业务也停掉——那等于限流成了单点故障。
A：SlidingWindowLimiter.tryAcquire 里 catch 住 Exception，打 log.warn("滑动窗口限流降级放行 ...") 并 return true——**故障时放行（fail-open）**。这是明确的取舍：限流保护的是"后端不被打垮"，如果限流组件本身不可用，宁可放流量进来（由下游的库存扣减、数据库条件更新继续兜底），也不要因为"判断不了该不该拦"就把所有用户挡在门外。要能说出反向选择：**如果是安全性质的限制（比如支付风控、登录失败锁定），就应该 fail-close（拒绝）**，因为放行的代价大于拒绝的代价。这个判断标准是"**放行错和拒绝错，哪个后果更严重**"。

### 维度④ 特殊情况下的兜底策略

**Q12：限流和一人一单、库存扣减，三层的关系是什么？**
【新手版】三层拦的是不同的东西：限流拦的是"**频率**"（你一秒点了 100 次，先拦掉 95 次）；一人一单拦的是"**资格**"（你已经抢到了，再点也没用）；库存扣减拦的是"**数量**"（货就这么多，谁先到谁得）。所以一个脚本被限流拦下之后，即使绕过限流，还有后两层等着它。
A：三层的保护目标是正交的，不能互相替代：
| 层 | 拦什么 | 机制 | 被绕过的后果 |
| --- | --- | --- | --- |
| 限流 | 请求频率 | 滑动窗口 ZSet 加 Lua | 请求量变大，但正确性不受影响 |
| 一人一单 | 重复资格 | Redis Hash 加数据库唯一索引 | 不会超卖，但会多出无效请求 |
| 库存扣减 | 总量 | Lua DECR 加数据库扣减条件 | 最后一道，不能失守 |
所以限流是**性能与公平性保护**，不是正确性保证。**正确性由后面两层负责**——这个分工必须能说清楚，否则面试官会问"那限流被绕过是不是就超卖了"，答案是"不会，超卖从来不是靠限流防的"。

**Q13：为什么抢购接口是 5 次每秒、支付是 3 次每秒？这些阈值怎么定的？**
【新手版】说实话，这两个数是我**根据"正常人不会这么点"估的一个合理值**，不是压测算出来的。抢购 5 次是因为一个人手速再怎么快，一秒点 5 次已经很夸张了；支付 3 次更严，因为它涉及钱。真要定得科学，应该按"线上正常用户的 P99 请求速率乘以 2 到 3 倍"来留余量。
A：如实说明：**seckill 是 1 秒 5 次、order_pay 是 1 秒 3 次、login 是 1 秒 20 次，这三个阈值是经验估值（未实测调优）**，定阈值时考虑的是：① 阈值要显著高于**正常用户**的行为上限（人手点击的物理上限大概就是每秒几次）；② 涉及资金的操作阈值更保守（支付 3 次）；③ 登录这类"正常只发生一次"的接口，阈值定得相对宽（20 次）是为了避免误伤共享 IP（公司出口 IP、校园网）下的正常用户——**这是一个刻意的误伤权衡**：IP 维度天然会误伤 NAT 后的群体，所以它的阈值必须放宽。科学的定阈值方法应该是：先用"只观测不拦截"的模式跑一段时间，拿到真实用户请求速率的 P99，再按 2 到 3 倍留余量。这个我没做，属于已知的待优化项。

**Q14：窗口大小和阈值，为什么不用配置中心动态调？**
【新手版】现在写在注解上，改了要重新发版。这在演示项目里够用，但线上活动的时候往往需要临时放宽或者收紧阈值，所以正确做法是"注解只声明业务键、阈值从配置中心读"。
A：当前是硬编码在注解上，属于**已知的可运维性缺口**：活动期间运营要求"临时把某个活动的限流放宽到 20 次每秒"这种需求，现在必须改代码发版。改进路径很清晰：注解保留 key 和 dimension（这些是**结构性信息**，不该动态变），把 windowSeconds 和 maxRequests 挪到配置中心（Nacos 或 Apollo）或数据库表，切面每次执行时按 key 查一次（可以加本地缓存加监听变更推送，避免每次请求都查配置）。**能说清"哪些该动态、哪些不该动态"比笼统说"用配置中心"更好**。

### 维度⑤ 真正的需求 · 实际产出

**Q15：限流你实测了吗？**
【新手版】测了。压测工具里有个 ratelimit 实验，对同一个用户在 1 秒内并发打 10 次抢购，超出的那部分全部返回 **HTTP 429**，提示"手速太快啦，歇一秒再抢"。数字是：同一用户 1 秒内并发 10 次抢购 → **5 次通过 + 5 次 HTTP 429**（阈值 5 次/秒）；改成每 1.2 秒 1 次匀速请求 → **限流 0 次、全部通过**。另外在"一人一单"那个实验里也能看到限流的实际效果：并发 20 次的时候，**15 次在进入库存校验之前就被 429 拦掉了，真正走到 Lua 限购校验的 5 次里有 1 次成功、4 次被"每人限购 1 件"挡下**——工具会把这两类分开统计，原文返回都打表。登录的 IP 维度也单独验了一次：并发 30 次登录 → **通过 20 次 + 限流 10 次**（阈值 20 次/秒）。
A：Bench.expRateLimit 的设计是：同一用户 1 秒内并发 10 次抢购（服务端规则是每人 1 秒 5 次），断言超额部分返回 429。更值得注意的是 Bench.expOneUser 的输出结构——它把并发 20 次的结果分成五类：**成功进入队列（期望 1）、触发限购、限流 429、已被抢光、其他**，并且在最后明确打印："并发 20 次时有 N 次在进入库存和限购校验之前就被 429 拦掉了；真正走到 Lua 限购校验的是 M 次，其中 1 次成功、M 减 1 次被'每人限购 1 件'挡下。" 我特意让工具把这两层分开统计，就是因为**混在一起会得出错误的结论**——如果只看"20 次里只有 1 次成功"，你无法区分这是"一人一单生效"还是"被限流挡了"。所以工具还补了一个实验：**按 1.2 秒间隔匀速发 5 次**（绕开 1 秒窗口），结果是成功 0 次、限流 0 次、**全部被一人一单拦下**——**这一步才是对"一人一单"本身的干净验证。** 几个可以直接报的数：同一用户 1 秒内 10 并发 → 5 通过 + 5 个 429；每 1.2 秒 1 次匀速请求 → 全部通过（429 为 0）；并发 20 次的一人一单实验 → 1 成功 + 4 限购 + 15 个 429；登录接口（IP 维度、阈值 20 次/秒）并发 30 次 → 20 通过 + 10 个 429。

▸ **追问：为什么限流的数字要单独验证，不能和一人一单混着看？**
【新手版】因为两层的拦截长得很像（都是"没成功"），但原因完全不同。混着看就会得出"一人一单生效了"的结论，其实可能只是被限流挡了。分开测才能在面试里说清"哪一次拦截来自哪一层"。
A：这是一个**实验设计问题**，也是我觉得比数字本身更值得讲的点：Bench 把"限流拦截"和"限购拦截"作为两个独立的分类维度，并且额外设计了一个**绕开限流窗口的匀速实验**（每次间隔 1.2 秒，大于 1 秒窗口）来单独验证一人一单。如果只做一个并发实验，两个机制的效果会互相污染——**测出来的数字无法归因**。所以我的实验原则是：**一次只验证一个机制，其他机制要么被绕开、要么被显式标注。**

### 维度⑥ 方法论（这一段最容易被记住）

**Q16：限流这一类需求，你的通用方法论是什么？**
【新手版】我总结成四件事：**在哪儿限**（越靠前的接口越粗粒度）、**按谁限**（身份必须来自服务端）、**限多少**（阈值要按正常用户的速率留余量）、**限流自己挂了怎么办**（想清楚是放行还是拒绝）。
A：限流四要素：
1. **限流位置**——入口层（网关或 Nginx）做粗粒度总量保护，应用层做细粒度业务限流。我的场景在应用层（AOP），因为它能拿到**登录身份**，这是网关拿不到的（网关通常只有 IP）。
2. **限流维度与身份来源**——维度决定防谁（用户防刷单、IP 防多账号、全局防打爆）；身份**必须来自服务端上下文**，绝不能取请求参数，否则限流就是给别人递刀子。
3. **阈值与算法**——算法按语义选：要"精确限次"用滑动窗口，要"限速允许突发"用令牌桶，要"恒定速率"用漏桶。阈值按"正常用户 P99 乘以 2 到 3 倍"定，涉及资金的更保守，IP 维度要放宽以避免 NAT 误伤。
4. **降级策略**——必须明确"限流组件故障时是放行还是拒绝"。判断标准是**放行错和拒绝错哪个更严重**：业务保护类（抢购）fail-open，安全风控类（支付、登录）fail-close。
补一句：**限流永远不是正确性的保证，它只是性能和公平性的保护**。任何"靠限流来防超卖、防重复下单"的说法都是错的——正确性必须由数据层的约束承担。

### 本章追问链（问完第一句之后最可能被追的四句）
1. **"为什么不用 Redis 的 INCR 加过期时间做固定窗口？"** → 它有临界问题：阈值 5 时，第 1 秒末尾和第 2 秒开头能在极短时间内放行 10 次，而这恰好是脚本会利用的特性。滑动窗口用时间戳精确统计，没有这个缺口。
2. **"ZSet 里每个请求都存一条，量会不会爆炸？"** → 窗口内的成员数上限就是阈值本身（超过就不再写入了），而且 PEXPIRE 设为窗口大小，没人访问就自动回收。所以单个 key 的成员数天然被阈值封顶，不会无限增长。
3. **"Lua 里 ZREMRANGEBYSCORE 每次都清一遍，会不会很慢？"** → 不是全清，是按 score 范围清，只删除窗口外的成员；窗口内成员数被阈值封顶，所以这几次操作都是小数据量。真正需要注意的是**大窗口加高阈值**的组合（比如 1 小时 10 万次），那时 ZSet 会变大，更合适的是令牌桶或者分桶计数。
4. **"同一个用户在多台机器上请求，限流还能生效吗？"** → 能，因为窗口数据在 Redis 里而不是本地内存，所有实例共享同一个 ZSet。这是我选 Redis 而不是本地 Guava RateLimiter 的原因——**本地限流在多实例下等于把阈值乘以实例数**。

### 一分钟口述稿（被要求"讲讲限流"时照着说）
"我用 **Redis ZSet 加 Lua 加 AOP 注解**做了一套滑动窗口限流，支持**全局、IP、用户**三个维度。核心逻辑就三步：以当前时间戳为 score 往 ZSet 里记每个请求，进来的时候先 ZREMRANGEBYSCORE 清掉窗口外的历史成员，再用 ZCARD 数一下窗口内还剩多少，没到阈值就 ZADD 记下本次并放行，到了就返回 0。**这三步必须用 Lua**，因为它们分开执行会有 check-then-act 竞态——两个请求同时数到 4（上限 5）然后都放行，就超发了；这和库存超卖是同一类问题。**为什么用滑动窗口不用令牌桶**：令牌桶允许突发（桶里攒着令牌能一次放完），我上一个项目用的就是它；这个项目的诉求是**防脚本刷单，要精确限次**，不能让它借窗口边界的空子，所以用滑动窗口。**用注解是为了规则和接口在一起**：抢购接口 1 秒 5 次、支付 1 秒 3 次、登录按 IP 1 秒 20 次，看一眼代码就知道谁被什么保护。**key 是 rate:seckill:USER:9003 这种格式，身份一律从服务端上下文 UserContext 取，绝不用请求参数**——否则攻击者填别人的 userId 就能把别人的额度耗光。最后一个取舍我要主动说：**Redis 挂了我是放行的**，因为限流是保护手段，不能因为限流自己挂了就把业务熔断；但如果换成支付风控这种安全场景，就应该反过来拒绝。这三个阈值我是按经验估的，没做实测调优，科学的做法是先只观测拿到真实 P99 再留 2 到 3 倍余量。"

### 维度① 它是什么 · 怎么用 · 为什么用

**Q1：RocketMQ 的延迟消息是什么？**
【新手版】就是"发一条消息，但让 broker 过一段时间才把它投给消费者"。我用它来实现"订单 30 秒没付款就自动关掉"——下单成功的同时发一条延迟 30 秒的消息，到点了消费者就收到，去把这个订单关掉、库存退回去。
A：RocketMQ 的延迟消息是**在 broker 侧定时**的：生产者发送时指定 delayTimeLevel，broker 把它投递到一个内部 topic，到时间后再投给真正的消费者 topic，所以**应用端不需要任何定时器**。注意它的一个硬限制：**只支持固定档位**，不支持任意秒数。我在 MqProducer 里把档位写成常量数组 DELAY_LEVEL_SECONDS，内容依次是 1、5、10、30、60、120、180、240、300、360、420、480、540、600、1200、1800、3600、7200 秒（对应 RocketMQ 的 1 到 18 级），并用 nearestDelayLevel(seconds) 按秒数选**最接近且不小于**它的档位。

**Q2：为什么不用定时任务扫表？**
【新手版】定时任务扫表的问题是"要一直扫，但你不知道什么时候有新数据"。比如每 10 秒扫一次，订单可能在第 1 秒就超时了却要等到第 10 秒才被处理；而且订单表越跑越大，每次扫描的成本都在涨。延迟消息是"下单的时候就预约好到点叫我"，每条订单只处理一次，不用扫。
A：定时任务方案的三个固有代价：① **精度差**——扫描周期决定了关单延迟的抖动（10 秒扫一次，实际关单时间可能是 30 到 40 秒）；② **成本随数据量增长**——"status 是 PENDING_PAY 且 create_time 早于某时刻"这个查询即使有索引，随着历史订单累积，扫描和判断的成本也在涨；③ **空转**——绝大多数扫描是"扫了但没有到期的单"，纯粹的无效负载。延迟消息把"轮询"换成了"**预约**"：下单时一次性投一条消息，broker 负责到点唤醒，成本与订单量成**线性**（一单一条消息），且有精确的到点时间。这也是简历上那句"避免定时任务全表扫描"的来由。

**Q3：延迟消息的时间怎么算出来的？**
【新手版】订单超时时间配在 application.yml 里，是 30 秒。下单成功后，消费者会算一下这个 30 秒该用哪个延迟档位，投一条延迟消息出去。因为 RocketMQ 只有固定档位，所以会选**不小于**配置值的最近那一档——30 秒正好是一个档位。
A：链路是：application.yml 的 flashmart.seckill.order-timeout-seconds 配的是 30，OrderService.timeoutSeconds() 暴露给消费者，OrderCreateConsumer 投递延迟消息时调 MqProducer.nearestDelayLevel(orderService.timeoutSeconds())。nearestDelayLevel 的逻辑是遍历档位数组，找到**第一个大于等于目标秒数**的档位并返回下标加一（RocketMQ 的 level 从 1 开始）；如果目标超过最大档位就返回最大档位。30 秒刚好命中档位数组里的 30，所以是精确的。**注意超时时长有两个消费方**：一个是真正的关单消息投递，另一个是 OrderService.toVO 里算给前端显示的 payDeadline（创建时间加超时秒数），两处用的是同一个配置值，保证**前端倒计时结束的时刻和实际关单时刻一致**。

### 维度② 背景 · 为什么偏偏这么选

**Q4：为什么需要"超时关单"这个功能？不做会怎样？**
【新手版】因为抢购是**预扣库存**的：用户抢到了但没付款，货就一直挂在他名下。如果不管他，活动的货就会被一群"抢了不付"的人占住，真正想买的人反而抢不到。所以必须有个机制：到时间还不付款，就把这单作废、把货退回去。
A：这是"**资源预占必须有过期时间**"这个通用原则的具体体现。秒杀的资源（库存）是稀缺的、且是被人**先到先得**占用的，如果占用没有期限，会出现两个问题：① **资源被无效占用**——抢了不付的用户让库存沉淀，活动实际成交率大幅下降；② **激励扭曲**——"先全部抢下来，再慢慢挑"变成理性策略，黄牛可以用脚本把所有货占住。超时关单把"占用"变成**有期限的期权**：30 秒内付款就成交，否则资源回收。这个设计同时保护了商家（货能卖掉）和其他买家（货能回到池子里）。

**Q5：为什么选 RocketMQ 延迟消息，而不是别的方案？**
【新手版】三种常见方案我都想过：**定时任务扫表**——精度差、成本随数据量涨；**Redis 的过期 key 通知**——不可靠，key 过期通知是"尽力而为"的，丢了你也不知道；**时间轮或 RabbitMQ 死信队列**——要么要自己实现调度，要么要引入新的中间件。RocketMQ 延迟消息是**已经在用的中间件自带的能力**，不用多引一个组件，可靠性和可观测性都跟着 MQ 走。
A：三种替代方案的对比：
- **定时任务扫表**：实现最简单，但精度受扫描周期限制、成本随订单量增长、且需要处理"任务实例并发扫描"的幂等和分片问题（多实例部署时要加分布式锁或者分片）。更适合作为**兜底对账**，而不是主机制。
- **Redis 过期 key 通知**：看似优雅（key 一过期就触发），但它有两个硬伤：① **不可靠**——Redis 的 keyspace notification 是"尽力而为"的，客户端断连或 Redis 重启期间的通知会丢；② **不能重复投递**——key 过期是一次性事件，丢了就没有重试。用它做关单会出现"订单永远待支付"的静默故障。
- **RabbitMQ 死信队列或时间轮**：能力上可行，但我的技术栈里没有 RabbitMQ，为了一个关单功能引入新的中间件不划算；时间轮要自己实现调度和持久化，复杂度和风险都比直接用 MQ 高。
所以选 RocketMQ 延迟消息的理由是：**零新增组件，且与订单链路共用同一个可靠性和可观测性体系（有重试、有死信、有消息轨迹）**。

### 维度③ 具体流程（要能画）

**Q6：下单之后到关单，完整链路是什么？**
【新手版】消费者写到订单之后，马上投一条延迟 30 秒的消息。这 30 秒内用户付款了，订单变成已支付。30 秒一到，关单消息被投递，消费者去查这个订单：如果还是待支付，就把它改成已超时，并把库存加回去（Redis 和数据库都加）；如果已经支付了，就什么都不做。
A：

    OrderCreateConsumer（订单创建成功后）
      └─ sendAsync(topic_order_timeout, key="order:"+orderNo,
                   OrderTimeoutEvent(orderNo),
                   delayLevel = nearestDelayLevel(30))   ← RocketMQ 只支持固定档位

    ── 30 秒（broker 侧定时，应用端无定时器）──

    OrderTimeoutConsumer（topic_order_timeout / cg_order_timeout / consumeThreadMax=32）
      → TraceUtil.start(消息里的 traceId)
      → tryAcquire(msgId) 幂等（同一订单的关单消息重复投递也只处理一次）
      → OrderService.timeoutOrder(orderNo)  @Transactional
           ├─ findByOrderNo(orderNo) → 查不到？log.warn + return false
           ├─ orderMapper.timeoutIfPending(orderNo)
           │     UPDATE seckill_order SET status='TIMEOUT', cancel_time=NOW(),
           │            cancel_reason='TIMEOUT', version=version+1
           │     WHERE order_no=? AND status='PENDING_PAY'
           │     affected == 0 → log.info("订单已不是待支付状态，关单跳过") + return false
           │                     （已支付的订单绝不会被关掉、库存也不会被误回滚）
           └─ affected == 1 → 回滚库存（两边都回）
                ├─ activityMapper.increaseStock(activityId)   ← 数据库
                │     UPDATE ... SET available_stock = available_stock + 1
                │     WHERE id=? AND available_stock < total_stock ← 防回滚超总库存
                └─ stockService.rollbackStock(activityId)     ← Redis（lua/rollback_stock.lua：当前库存 < 总库存时才 +1）
                      注意：只回滚库存，**不回滚该用户的已购记录**
      → markSuccess(msgId)
      → 异常 → markFailed(msgId) + 抛出 → MQ 阶梯重试

**Q7：关单具体改了哪些数据？**
【新手版】三处：订单表的状态改成 TIMEOUT 并记下取消时间和原因；数据库的活动库存加 1；Redis 里的活动库存加 1。**唯独不改的是"这个人已购数量"**——因为他的名额已经用过了。
A：四处明细：
1. seckill_order：status 改成 TIMEOUT、cancel_time 记当前时间、cancel_reason 记 TIMEOUT、version 加 1（乐观锁），条件是 status 等于 PENDING_PAY；
2. flash_activity.available_stock：加 1，条件是 available_stock 小于 total_stock（**防止回滚把库存顶过总库存**）；
3. Redis 的 seckill:stock:{activityId}：+1，但**带上限**——rollbackStock 走 lua/rollback_stock.lua，先比较 seckill:total:{activityId}，只有当前库存小于活动总库存时才 INCR（以前是无脑 INCR，实测出现过在途关单消息把库存从 9999 加到 11679）；
4. **不做**：seckill:bought:{activityId} 里这个用户的已购数量**不变**——这是本章最重要的设计决策，见下题。

**Q8：为什么关单不回滚"已购记录"？**
【新手版】因为他的"名额"已经用掉了。货可以还回去给别人抢，但这个人用过一次机会了，不付款就作废。如果他关单之后还能再抢，那"超时"就变成了免费重来——恶意用户可以无限占库存、不付款，再用一个人的账号把活动锁死。
A：代码里 SeckillStockService.rollbackStock 的注释就是设计文档："**只回滚库存（超时关单时用）。注意这里是故意不回滚已购记录的：名额已经用掉了，用户不付款就作废，库存退回池子里给其他人抢 —— 这正是真实秒杀的做法（限购机会只有一次）。**" 对比 rollbackAll（下单失败时用）：那个方法**同时**把库存加 1、把该用户的已购数量减 1，因为那种场景用户什么都没拿到。**两个方法的存在本身就是这个决策的代码化表达。** 实测上也验证了这一点：超时关单之后让同一个用户再抢一次，会被"每人限购 1 件，你已经抢到啦"拦下——压测工具的 timeout 实验里有这个补充验证步骤。

### 维度④ 特殊情况下的兜底策略

**Q9：延迟消息丢了，订单不就永远待支付了？**
【新手版】会，这是延迟消息方案的最大风险点。所以工业级做法还要配一个**兜底对账任务**：低频扫一次"超时很久还是待支付"的订单，把它们补关掉。这个任务不用频繁跑（比如几分钟一次），因为绝大多数订单已经被延迟消息正常处理了，它只负责兜住漏网的那几条。
A：这是本方案**最重要的一条边界**，我会主动说：单靠延迟消息，**"消息丢失等于订单永远待支付"**，用户不付款、库存也不回池子。而当前代码里**没有兜底对账任务**（OrderTimeoutConsumer 只有 MQ 阶梯重试兜住"消费失败"这一类）。完整的方案应该是双保险：
- **主机制**：延迟消息（精确、低成本、无空转）；
- **兜底机制**：低频定时任务扫"status 是 PENDING_PAY 且创建时间早于超时时刻加余量"的订单，走同一个 timeoutOrder 方法补关单。
关键在于**兜底任务和主机制复用同一段有幂等保护的业务逻辑**——timeoutIfPending 的 WHERE 条件（status 必须等于 PENDING_PAY）保证了重复关单是安全的，所以"主机制成功处理过的订单，兜底任务再处理一次也没关系"。**这个设计让兜底机制的引入成本几乎为零，也是我要补的下一个功能。**

**Q10：如果用户恰好在第 30 秒付款呢？**
【新手版】这就是"支付回调"和"关单"撞在一起的情况。两个操作都只允许从"待支付"出发，而且都带乐观锁版本号，所以数据库层面只有一个能成功——要么支付成功订单变成已支付，要么关单成功订单变成超时。绝不可能出现"已经付款了又被关单、库存还被退回去"。
A：两道保险：① **状态条件**——payWithVersion 的 WHERE 里有 order_no、status 等于 PENDING_PAY、version 等于读到的版本三个条件，timeoutIfPending 的 WHERE 里有 order_no 加 status 等于 PENDING_PAY，两者都只接受"待支付"这个起点；② **版本号**——支付侧额外校验 version，如果订单在读取之后被改过（version 变了），UPDATE 影响 0 行，OrderService.pay 里就抛"订单状态已变化，请刷新后查看"。因为两个 UPDATE 都在各自的事务里对同一行加锁，数据库会串行化它们，**只有一个能拿到 PENDING_PAY 这个状态**。这就是第 8 章的主题。

**Q11：订单超时时间设多长合适？**
【新手版】我这个项目配的是 30 秒，因为它是**演示项目**——30 秒方便现场观察"到点真的会自动关单"。真实电商一般是 15 分钟到 30 分钟，因为要给用户留出打开支付 App、输密码的时间。
A：application.yml 里注释就写明了："**生产按业务定，演示用 30 秒便于观察**"。定这个值的两端约束是：① **下限**——必须大于"用户看到订单到完成支付"的正常耗时（真实场景是几分钟级），太短会造成大量"我刚要付款就被关单"的投诉；② **上限**——不能超过"库存被无效占用的可容忍时长"，太长会让活动实际成交率下降（货被占着但没人付）。还有个工程约束要提：**超时时长必须显著大于"消息可能的积压时长"**，否则会出现"订单刚落库就被关单消息关掉"的时序错乱（延迟消息到点投递时订单还没创建完）。演示值 30 秒正是为了让这个实验能在几十秒内跑完。

### 维度⑤ 真正的需求 · 实际产出

**Q12：超时关单你实测出了什么？**
【新手版】压测工具里有个 timeout 实验：发一次真实抢购，等订单落库，然后**不支付**，投一条延迟 30 秒的关单消息。到点之后订单状态从 PENDING_PAY 变成 **TIMEOUT**（实测轮询在 **22ms** 内就已经看到关单结果），Redis 和数据库的剩余库存**各回滚 1 件**（各加 1，工具会断言这一点）。最后订单状态分布是 **PAID 一条、TIMEOUT 一条**，工具还会再验证一次"这个人再抢会被限购拦下"。
A：实验步骤（Bench.expTimeout）：① reset 活动（库存、订单、Redis 已购记录、缓存计数全清）；② 记录关单前的 stats；③ 走**真实** /api/seckill 链路发一次抢购，拿到 orderNo；④ 轮询等订单落库为 PENDING_PAY；⑤ **不支付**，等 30 秒的延迟消息到点；⑥ 再查订单状态和 stats。结果：**订单最终状态等于 TIMEOUT（到点关单成功，轮询 22ms 内就已经看到状态变化）**，redisAvailableStock 和 dbAvailableStock **各加 1**（工具用断言语句直接校验这两个增量都等于 1），订单状态分布是 **PAID 为 1 条、TIMEOUT 为 1 条**。另外工具还做了一个**关键补充验证**：关单之后让**同一个用户再抢一次**，断言结果为 OVER_LIMIT（"每人限购 1 件，你已经抢到啦"）——这一步专门用来证明"**库存退回了池子，但这个人的名额已经用掉**"这个设计确实生效了。

▸ **追问：为什么订单状态是 PAID 一条、TIMEOUT 一条，不是只有 TIMEOUT？**
【新手版】因为跑 timeout 实验之前，先跑过支付实验，那张订单已经变成 PAID 了，并且它一直留在这个活动下。所以统计这个活动的订单状态时，就同时看到一条历史已支付的和一条刚超时的。这也顺带证明了"关单只关待支付的，不会动已支付的订单"。
A：ordersByStatus 统计的是**该活动下的全部订单**。PAID 那一条来自之前 expPay 实验留下的已支付订单（压测是连续跑多个实验的，只有带 clearOrders 等于 true 的 reset 才会清订单）。所以这两个数字放在一起看，意义比单个数字更强：**同一个活动下，一条订单被支付后保持 PAID，另一条订单超时被关成 TIMEOUT，两者互不干扰**——这正是 timeoutIfPending 里 status 必须等于 PENDING_PAY 那个条件在起作用。我在讲这个数字时会主动解释它的构成，而不是笼统说"超时关单成功了"。

### 维度⑥ 方法论（这一段最容易被记住）

**Q13：这类"时序任务"需求（到点做某事），你有通用方法论吗？**
【新手版】四条：**一是优先用"预约"而不是"轮询"**——延迟消息、定时器都是预约，扫表是轮询，预约永远比轮询精度高、成本低。**二是永远配一个兜底**——任何"预约"机制都可能丢，所以要有一个低频的"扫一遍看看有没有漏"的任务补上。**三是兜底和主机制复用同一段有幂等的业务逻辑**——这样重复执行不会出事，兜底才敢随便加。**四是处理的时候一定要带状态条件**——WHERE 里写"状态等于待处理"，这样"到点了但状态已经变了"就自动变成空操作。
A：我的时序任务四原则：
1. **预约优于轮询**——延迟消息（RocketMQ）和定时器（时间轮、JDK DelayQueue）是"事件驱动"，定时任务扫表是"轮询驱动"。前者的成本与任务数成线性、精度由中间件保证；后者的成本与数据量挂钩、精度受扫描周期限制。**只有在"任务丢失需要兜底"或"到点时间不确定（依赖外部条件）"时才用扫表。**
2. **必须有兜底机制**——任何单点机制都会丢：延迟消息会丢、定时器随进程重启会丢（内存态）、外部回调会丢。兜底的形态通常是"低频扫表加对账"，它的存在让主机制从"必须可靠"降级为"尽量可靠"。
3. **兜底必须复用幂等的主逻辑**——兜底任务绝不能自己写一套"补关单"的代码，而要调用和主机制**同一个方法**。因为主逻辑里的状态条件（status 必须等于 PENDING_PAY）本身就是幂等保护，重复执行只是空操作。**这是让"双保险"不增加复杂度的关键。**
4. **执行时必须带状态前置条件**——所有状态流转的 UPDATE 都要写成"UPDATE ... SET 新状态 WHERE 主键 AND 当前状态等于期望状态"，用**受影响行数**判断"我是不是真的改变了它"。这样并发和重复执行都会自动退化成安全的空操作。这条不只适用于关单，是所有状态机的通用写法（见第 8 章）。

### 本章追问链（问完第一句之后最可能被追的四句）
1. **"RocketMQ 只有固定档位，如果我要 45 秒超时怎么办？"** → nearestDelayLevel 会选**不小于**目标的最接近档位，45 秒会落到 60 秒档（比目标长）。这个偏差的后果是"实际关单比配置的晚"，是安全方向的偏差；要精确的话得用支持任意延迟的版本（RocketMQ 5.x 的定时消息）或者自己实现时间轮，这是个明确的取舍点。
2. **"关单消息重复投递会怎样？"** → timeoutIfPending 的 WHERE 条件保证第二次执行影响 0 行，直接跳过；而库存回滚在检查到 affected 等于 1 之后才执行，所以**不会重复回滚库存**。这是"状态条件加受影响行数"这个组合的典型收益。
3. **"订单超时关单之后，用户还能付款吗？"** → 不能。OrderService.pay 里会先检查状态，不是 PENDING_PAY 就抛"订单已关闭（TIMEOUT），无法支付"。这是刻意的：订单关闭的语义是"这笔交易结束了"，不能让用户在一个已经释放了库存的订单上付款，否则会出现"付了钱但库存已经卖给别人"。
4. **"如果关单成功了，但库存回滚那一步失败了？"** → 整个 timeoutOrder 在一个 @Transactional 里，所以数据库那部分（订单状态加数据库库存）会一起回滚；Redis 侧的 +1 不在这个事务里（走的是 lua/rollback_stock.lua），存在"数据库回滚了但 Redis 已经加 1"的可能。要诚实说这个边界：两侧现在都带上了上限（数据库 increaseStock 的 WHERE 带 available_stock 小于 total_stock，Redis 走 rollback_stock.lua 比较 seckill:total:{activityId}），所以不会再出现"库存被加超总量"；但"数据库回滚成功、Redis 没加上"这种方向上的偏差仍然存在，需要靠对账修正（对账任务目前没做，属于待补项）。

### 一分钟口述稿（被要求"讲讲超时关单"时照着说）
"超时关单我用的是 **RocketMQ 的延迟消息**，不用定时任务扫表。链路是：订单创建成功的那个消费者，立刻再投一条延迟消息到 topic_order_timeout，延迟档位按配置的超时时间算——我配的是 30 秒（生产按业务定，演示用 30 秒方便观察）。30 秒到点，关单消费者收到消息，去执行 timeoutOrder：先把订单从 PENDING_PAY 改成 TIMEOUT，然后**把库存加回去——Redis 和数据库各加 1**。**为什么不用定时任务**：扫表有三个固有代价——精度受扫描周期限制（10 秒扫一次，30 秒超时的单最坏 40 秒才关）、成本随历史订单增长、而且绝大多数扫描都是空转。延迟消息是'下单时就预约好到点叫我'，一条订单一条消息，成本是线性的。**关单最大的设计点是**：**只回滚库存，不回滚这个用户的已购记录**——名额用掉了，不付款就作废，货退回池子给别人抢；只有'订单根本没落库'的下单失败，才把库存和机会一起还回去。所以关单之后这个人再抢会被'每人限购 1 件'拦下，压测里我专门验证了这一点。**实测结果**：30 秒延迟消息到点关单成功，订单状态变成 TIMEOUT，Redis 和数据库库存各回滚 1 件，订单状态分布是 PAID 一条、TIMEOUT 一条。**边界我也说清楚**：延迟消息丢了订单就会永远待支付，所以工业级方案必须再配一个低频的兜底对账任务；而且 RocketMQ 的延迟只支持固定档位，45 秒会被向上取到 60 秒——这些都是我知道的取舍。"

## 第 8 章 · bullet ⑦：乐观锁解决支付回调与关单并发

### 8.0 这句话里他会盯的词
**乐观锁**（乐观在哪儿？和悲观锁什么区别？）、**支付回调**（回调是什么？你为什么是模拟的？）、**状态流转**（订单有哪几个状态？谁能到谁？）、**准确性**（你说准确，凭什么？）。

### 维度① 它是什么 · 怎么用 · 为什么用

**Q1：乐观锁是什么？跟悲观锁的区别？**
【新手版】乐观锁是"我先假设没人跟我抢，读的时候把版本号一起读出来，写的时候检查一下版本号变没变"——没变就说明没人动过，我改；变了就说明有人抢先了，我这次失败。悲观锁是"我上来就把这条数据锁住，别人都不许碰，等我改完再放开"。抢的人不多的时候，乐观锁不用真的加锁，更省。
A：**悲观锁**（SELECT ... FOR UPDATE、分布式锁）在读取时就独占资源，把冲突"挡在门外"，代价是持锁期间的等待、以及死锁和锁超时的风险，适合**冲突激烈**的场景。**乐观锁**不加锁，靠"**读取时带走版本号，写入时校验版本号**"来检测冲突（CAS 思想）：版本没变说明这次读到的版本之后没人改过，可以更新；变了就说明冲突，返回失败让上层处理。它适合**冲突不激烈**的场景，因为没有等待、没有锁开销，代价是冲突时需要重试或者向用户报错。我的订单状态流转里，"同一订单的支付回调和超时关单在毫秒级窗口内撞车"是**小概率**事件，所以乐观锁是合适的选择。

**Q2：你的乐观锁具体怎么写？**
【新手版】支付那条 SQL 是：更新订单状态为已支付、版本号加 1，条件是订单号对、当前状态还是"待支付"、版本号还是我刚才读到的那一个。如果数据库返回影响 0 行，就说明我读完之后状态被人改掉了，我就抛异常"订单状态已变化，请刷新后查看"。
A：SeckillOrderMapper.payWithVersion 的 SQL 是：
UPDATE seckill_order SET status = 'PAID', pay_trade_no = 参数, pay_time = NOW(), version = version + 1, update_time = NOW() WHERE order_no = 参数 AND status = 'PENDING_PAY' AND version = 参数
对应的方法是 int payWithVersion(orderNo, tradeNo, version)。OrderService.pay 里的用法是：先 findByOrderNo 读到 order（拿到它的 version），再做业务前置校验，然后调 payWithVersion 并把 order.getVersion() 传进去；**返回 0 行就抛 BizException("订单状态已变化，请刷新后查看")**。返回 1 行才是真的支付成功。

**Q3：关单那边也用乐观锁吗？**
【新手版】关单用的是同一个套路，但只校验状态、没校验版本号：条件是"订单号对且状态还是待支付"，影响 0 行就说明已经被人改过了（多半是已经支付了），那就跳过，什么都不做。
A：SeckillOrderMapper.timeoutIfPending 的 SQL 是：
UPDATE seckill_order SET status = 'TIMEOUT', cancel_time = NOW(), cancel_reason = 'TIMEOUT', version = version + 1, update_time = NOW() WHERE order_no = 参数 AND status = 'PENDING_PAY'
它**只校验状态、不校验 version**，因为它的语义是"只要现在还是待支付就关掉"，不需要知道中间被改过几次；而且它的目标状态是 TIMEOUT、和支付的目标状态 PAID 互不相同，所以即使关单时读到的 version 是旧的，也不会造成错误结果——**关键的保护来自 status 等于 PENDING_PAY 这个条件**，version 在这里是增量保护而不是必要条件。两者都会把 version 加 1，保证任何一次流转都留下"我改过"的痕迹。

**Q4：既然 status 已经能保证互斥了，为什么支付还要加 version？**
【新手版】因为 status 只有一个维度。"待支付"这个状态可能被好几件事同时争抢，光看状态判断不出"我读到的这条数据是不是我以为的那一条"。带上版本号，等于加上"从我读到它到我改它之间，它没有被动过"这个更强的保证，冲突时能明确地告诉用户"请刷新重试"，而不是让两个人都以为自己成功了。
A：三点理由：① **更强的并发检测**——status 只能区分"状态对不对"，version 能检测"在我读完之后这一行是否被任何更新动过"，是更细粒度的 CAS；② **明确的失败语义**——返回 0 行时我能区分出"这不是状态错误，而是并发冲突"，于是向前端返回"订单状态已变化，请刷新后查看"这种可重试的提示，而不是"无法支付"这种终结性错误；③ **为后续扩展留出空间**——如果以后订单增加了"已支付之后还能部分退款"这类操作，只靠 status 就不够了，version 是通用的并发保护手段。**代价**是调用方必须先读再写（多一次查询），但支付本来就是"先查订单是否存在、是否属于我"的流程，这次读是必须的，所以没有额外开销。

### 维度② 背景 · 为什么偏偏这么选

**Q5：这个并发冲突是怎么产生的？**
【新手版】我投了一条延迟 30 秒的关单消息。用户如果正好在第 30 秒左右点了支付，那么"关单"和"支付"两个动作很可能在几毫秒内同时发生，它们都要改同一个订单的状态。如果不管，就可能出现"订单已经关掉、库存也退回去了，但用户付的钱也扣了"这种最坏情况。
A：冲突的根源是**两条独立的异步链路指向同一个资源**：① 支付链路——用户点击支付，OrderService.pay 读订单、改状态；② 关单链路——30 秒的延迟消息到点，OrderTimeoutConsumer 调 timeoutOrder 改状态。两条链路的触发时刻**没有协调机制**，所以"用户在第 30 秒点支付"时它们必然重叠。它们要改的是同一行数据的同一个字段（status），这是典型的**并发写冲突**。要防的具体后果有三类：**重复支付**（用户付了两次）、**状态错乱**（先 PAID 后 TIMEOUT）、**库存误回滚**（已经付款的订单被关单，库存退回池子，导致这件货可能被卖给第二个人）。

**Q6：为什么用乐观锁，不用分布式锁或者数据库行锁？**
【新手版】因为这两条链路的并发冲突是**小概率**的（只在超时的那一瞬间），用锁属于为了小概率事件付大成本。乐观锁不需要加锁、不占连接、没有等待；而且我这条链路天然就是"先读订单再判断再改"，用乐观锁几乎不增加代码。另外一个理由：这个项目我刻意不用分布式锁（上一个项目用过了），这里就是要用"数据库自己能保证的手段"来解决。
A：三种方案的对比：
- **分布式锁**（Redisson）：要引入新组件、加锁解锁两次网络往返、还要处理锁续期和锁失效后的正确性。对于"只在这一瞬间可能冲突"的场景，**成本明显高于收益**。而且我还要保证"即使锁失效也不能出错"，那最终还是要在数据库加条件——**那不如直接用数据库的条件更新**。
- **数据库悲观锁**（SELECT ... FOR UPDATE）：把这一行锁住直到事务结束，简单直接，但它**占着行锁和连接**，在抢购这种高并发场景下容易引发锁等待；而且它有死锁风险（两个事务以不同顺序锁多行时）。
- **乐观锁（条件更新）**：无锁、无等待、不额外占用连接，冲突时最多是"返回 0 行然后报错让用户刷新"。**它把并发控制放进了那条 UPDATE 语句本身**，语义就是我要的："只有在状态还是待支付、且版本没变的情况下，才允许变成已支付。"
一句话：**冲突概率低，加上天然先读后写，再加上不想引入额外组件**，三点加起来让乐观锁成为最合适的选择。

**Q7：你说的"模拟支付网关回调"是什么意思？为什么是模拟的？**
【新手版】真实系统里，用户付款是通过第三方支付平台（微信、支付宝）完成的，付完之后支付平台会回调我们的接口，告诉我们"这笔订单付成功了"。我没有接真实的支付平台，所以这个"回调"是我自己写的一个接口（POST /api/order/{orderNo}/pay），行为上和真实回调一样：拿到订单号、改状态、记录流水号。简历和文档里我明确写的是"模拟支付网关回调"，不写"接入微信支付"。
A：真实链路是"**用户下单，跳转第三方支付，第三方异步回调我的 notify 接口，我验签、改订单状态、返回成功**"。我做的是**把第三方支付这一步替换成本地接口**，保留回调之后的所有逻辑：生成支付流水号（pay_trade_no，格式是 PAY 加时间戳加随机数）、用乐观锁把 PENDING_PAY 改成 PAID、记录 pay_time、做幂等处理（重复支付直接返回已支付）。**为什么要说清是模拟的**：① 诚实边界——真实支付涉及验签、证书、对账、退款，这些我都没做；② 但**回调之后的"状态流转正确性"这个核心问题我是真做了**，而且用乐观锁解决得比"假装的支付"更有价值。面试里我会主动说明这一点，因为"知道哪部分是模拟的、哪部分是真实现的"本身就是工程判断力。

### 维度③ 具体流程（要能画）

**Q8：完整画一下支付和关单的并发。**
【新手版】支付这边：先查订单，如果不是我的就拒绝；如果已经付过了就直接返回成功（幂等）；如果不是待支付就报"订单已关闭"；然后带着版本号去更新，改成已支付。关单那边：直接把"还是待支付"的订单改成超时。两个 UPDATE 都只接受"待支付"这个起点，所以数据库会串行执行它们，只有一个能成功。
A：订单状态机只有**三个出口**：PENDING_PAY 到 PAID（支付成功）、PENDING_PAY 到 TIMEOUT（超时关单）、PENDING_PAY 到 CANCELLED（预留，当前代码里定义了常量但主流程未使用，属未实测路径）。

**Q9：支付为什么要做幂等？**
【新手版】因为用户可能手抖点两次支付，或者网络超时了前端重试。我的做法是：进来看见订单已经是"已支付"，就直接返回"订单已支付，无需重复支付"，不再往下走。这样第二次、第三次点都不会重复扣款。
A：OrderService.pay 的第 ③ 步就是幂等分支：判断订单当前 status 等于 STATUS_PAID 就直接 return，返回 status 是 PAID、message 是"订单已支付，无需重复支付"。**这一层的意义**：真实的支付回调本身就是**至少一次**语义的（第三方平台可能重复通知），所以回调方必须幂等——这跟 MQ 消费端要做幂等的道理完全一样。我的实现是"**快路径幂等（读状态判断）加慢路径保证（乐观锁 UPDATE 条件）**"两层：绝大多数重复请求在第一步就被拦下，不产生任何写；万一两个请求同时穿过第一步，第二条 UPDATE 会因为 status 已经不是 PENDING_PAY 而影响 0 行，也不会重复更新。另外支付接口本身还加了滑动窗口限流（用户维度 1 秒 3 次），属于第三层。

### 维度④ 特殊情况下的兜底策略

**Q10：支付成功了但改状态失败了怎么办？**
【新手版】我的改状态和业务处理在同一个数据库事务里，所以如果 UPDATE 报错，整个事务回滚，不会出现"扣了钱没改状态"这种半成品。但要诚实说：真实的支付回调里，"第三方已经收到钱、我这边事务失败"这个窗口是存在的，标准解法是**对账**——定期拿第三方的流水和我的订单核对，把差异补回来。这个我没做。
A：分两层说：
- **当前实现**：pay 方法上有 @Transactional(rollbackFor 等于 Exception.class)，payWithVersion 的更新和它同事务，失败会一起回滚，所以**不会留下半更新的状态**。
- **真实场景的缺口**：真实支付接口是"**先收到第三方的钱，再回来改我的订单状态**"，中间的窗口（第三方成功但我这边事务失败、或者回调根本没收到）必然存在，这在任何系统里都无法靠本地事务消除。标准解法是**对账加补偿**：① 每日定时拉第三方对账文件，和本地订单比对；② 对"第三方有成功记录、本地还是待支付"的订单主动补成 PAID；③ 对"本地 PAID、第三方没有记录"的异常单人工介入。**这个项目没有实现对账**（因为它根本没有真实第三方），我会明确说这是模拟支付带来的边界。

**Q11：如果发现订单已经被关单了，但用户已经付了钱，怎么处理？**
【新手版】这种情况的正确做法是**退款加主动通知用户**，而不是把订单改回已支付——因为库存已经退回去了，这件货可能已经被别人买走，硬改成已支付会变成超卖。我的项目里没有实现退款，因为支付是模拟的；但我会指出这个路径和它的正确处理方式。
A：正确的处理顺序是：① **不改订单状态**——把它改成 PAID 会让"库存已经退给别人"这件事变成超卖；② **发起退款**——调用退款接口把钱退回用户，并记录退款流水；③ **主动通知**——站内信或短信告知"订单超时关闭，款项已退回"；④ **记录差异单**——把这类事件落一张异常表，供运营核查。这套流程的前提是**有真实支付渠道和对账机制**，我的模拟支付没有这些，所以我在文档里把它列为"知道但未实现"的部分。要强调的是**判断顺序**：先问"资源还在不在"，再决定是"补状态"还是"退款"——资源已经释放的场景永远不能靠改状态来修。

**Q12：关单和支付同时到达，会不会两个都成功？**
【新手版】不会。两个 UPDATE 都带"状态必须是待支付"这个条件，而且都跑在数据库事务里，数据库会对同一行加行锁把它们串起来。第一个先执行的把状态改掉了，第二个再执行时条件就不成立了，影响 0 行。所以最终只有一个生效。
A：不会，原因是 **UPDATE 语句的原子性加行锁串行化**：两个事务都对 seckill_order 的同一行做 UPDATE，InnoDB 会在第一个事务执行 UPDATE 时对该行加排他锁，第二个事务必须等它提交或回滚才能继续；等第二个拿到锁时，它读到的 status 已经变成 PAID（或 TIMEOUT），于是"status 等于 PENDING_PAY"这个条件不成立，影响行数为 0。所以：
- 如果**支付先赢**：订单 PAID，关单那条返回 0，timeoutOrder 里 affected 等于 0 就直接 return false，**库存不会被回滚**；
- 如果**关单先赢**：订单 TIMEOUT、库存各加 1，支付那条返回 0，pay 抛"订单状态已变化，请刷新后查看"，用户刷新后看到的是"订单已关闭"。
**这就是为什么"库存回滚"这一步必须放在 affected 等于 1 之后**——它不是一句顺序问题，而是"只有我真的改成 TIMEOUT 了，才有资格回滚库存"。压测里 expPay 的断言"支付后订单最终状态是 PAID、库存不再变化"验证的就是前半条路径。

### 维度⑤ 真正的需求 · 实际产出

**Q13：这个乐观锁你实测了吗？**
【新手版】压测工具里有个 pay 实验：真实抢购一单，拿到订单号，然后**连续调两次支付**，检查第一次是不是成功、第二次是不是幂等地返回"已支付"，最后确认订单终态是 PAID，并且**库存不会再被关单回滚**。我的超时关单实验里也验证过反面：不支付的那一单，30 秒后确实变成 TIMEOUT 且库存回滚。
A：Bench.expPay 的步骤：① reset 活动；② 走真实抢购链路拿到 orderNo，轮询到 PENDING_PAY；③ **连续调用两次支付接口**（pay1、pay2），把两次的 HTTP 状态、业务码、message、data.status 打成一张表；④ 轮询确认订单终态；⑤ 对比支付前后的 dbAvailableStock 和 redisAvailableStock。实测两次支付的返回都是 status 等于 PAID，第二次的 message 就是"订单已支付，无需重复支付"。断言有三条：**第一次支付成功且 status 是 PAID**、**第二次支付幂等返回且 status 仍是 PAID**、**订单最终状态是 PAID（支付后不会被超时关单回滚库存）**。配合 Bench.expTimeout 的断言（不支付的那单最终 TIMEOUT 且库存各加 1），两条路径合起来就是完整的验证：**同一套代码，付了款的状态保住、没付款的状态关掉**。

▸ **追问：并发冲突本身你压出来了吗？**
【新手版】没压出来。我验证的是"两条路径各自正确、支付后不会被关单影响"，但没有构造"第 30 秒整同时点支付和触发关单"这种精确到毫秒的对撞实验。要压出来需要一个能精确控制时序的注入点。
A：如实说：**我没有构造"支付与关单在同一毫秒对撞"的实验**（未实测）。已经验证的是"两条路径各自走到正确终态、且互不干扰"：expPay 证明支付后订单保住 PAID 且库存不动，expTimeout 证明不支付的订单超时加库存回滚。要精确压这个对撞，需要：① 在服务端加一个可控的时序开关（比如让关单消息的延迟档位可配置，Bench 的 force-timeout 接口其实已经能做到"按 1 秒投递关单消息"）；② 在客户端用栅栏让"支付请求"和"关单投递"尽量同时发出。所以**做一个对撞实验是可行的，只是我还没做**。我会主动说清这一点，而不是暗示我压过。

### 维度⑥ 方法论（这一段最容易被记住）

**Q14：状态流转这一类问题，你的通用方法论是什么？**
【新手版】四条：**一是先把状态机画出来**——有哪些状态、允许哪些迁移，不允许的迁移要在代码里显式拒绝；**二是每次迁移都带前置条件**——UPDATE 里写"当前状态必须是 X"，用影响行数判断有没有真的改成功；**三是重要迁移加版本号**——用来检测并发冲突，冲突时给用户一个可重试的提示；**四是副作用要挂在改成功之后**——库存回滚、发通知这些动作，只有状态真的改了才能做。
A：我的状态机四原则：
1. **先定义状态机，再写代码**——列出全部状态与合法迁移（我的订单是 PENDING_PAY 到 PAID、TIMEOUT、CANCELLED），**非法的迁移必须在代码里显式拒绝**（比如"已关闭的订单无法支付"），不能依赖"反正不会发生"。
2. **迁移必须带前置条件，并判断影响行数**——所有状态更新都写成条件更新，用 affected 等于 0 表示"这次迁移没有发生"。这既解决了并发（同一状态只有一个能改成功），也解决了幂等（重复执行自动变成空操作），**一条语句同时买到两个性质**。
3. **需要检测并发的迁移加版本号**——状态条件只能保证"状态对"，版本号才能保证"我读到的这行没被人动过"。冲突时的返回要**可重试**（"请刷新后查看"），而不是终结性错误。
4. **副作用必须挂在我真的改成功之后**——库存回滚、发通知、投递消息这些"因状态变化而产生"的动作，**只能放在 affected 等于 1 的分支里**。这是最容易写错的地方：如果先回滚库存再改状态，一旦状态没改成，就会凭空多出一件库存。
再补一句通用的：**状态流转的正确性不靠锁来保证，靠"条件更新加影响行数"来保证**——这样无论有没有并发、有没有重复消息，结果都是确定的。

### 本章追问链（问完第一句之后最可能被追的四句）
1. **"乐观锁冲突了，为什么不是自旋重试？"** → 因为这里的冲突语义是"订单已经被别人改成别的状态了"，重试也不会成功（状态不会自己变回 PENDING_PAY），所以正确的处理是**把冲突如实告诉用户**（"请刷新后查看"），让他看到真实状态。如果冲突语义是"资源被短暂占用、等一会儿就能成功"（比如库存扣减），那才适合自旋或重试。
2. **"用 version 字段需要每次都先查一次订单，这不就多了一次数据库读吗？"** → 是，但这次读是必须的：我要先判断"订单存在吗、是我的吗、当前状态是什么"，这些本来就要读。乐观锁只是**顺便把 version 一起带出来**，没有额外的查询成本。
3. **"如果两个事务同时更新，InnoDB 不就锁住了吗，那这不就是悲观锁？"** → 底层是行锁没错，但**语义不同**：悲观锁是"我先锁住再慢慢处理"，持锁时间长、影响面大；我这里是"一条 UPDATE 语句本身就带条件"，锁只在语句执行期间存在，而且**正确性不依赖锁**——即使隔离级别变化、即使语句被拆开执行，条件更新依然是对的。这叫"把并发控制下沉到数据约束"，比"靠锁"更稳。
4. **"CANCELLED 这个状态用来干什么？"** → 它是"用户主动取消订单"预留的状态，SeckillOrder 里定义了常量、cancel_reason 字段也留了位置，但**当前主流程没有实现用户取消这个入口**（只有超时关单会写 cancel_time 和 cancel_reason 等于 TIMEOUT）。我把它标成"定义了但未使用"，不假装它实现了。

### 一分钟口述稿（被要求"讲讲订单状态并发"时照着说）
"订单有四个状态：PENDING_PAY、PAID、TIMEOUT，还有预留的 CANCELLED。**唯一的入口是 PENDING_PAY**，从它出发只有两条路：支付成功变 PAID，或者超时关单变 TIMEOUT。冲突就发生在这儿：我给每个订单投了一条延迟 30 秒的关单消息，如果用户正好在第 30 秒点支付，**支付链路和关单链路会在几毫秒内同时改同一行订单**。我的解法是**乐观锁加状态条件**：支付那条 SQL 是'更新成 PAID、版本号加一，条件是订单号对、状态还是 PENDING_PAY、版本号还是我读到的那一个'；关单那条 SQL 是'更新成 TIMEOUT，条件是订单号对、状态还是 PENDING_PAY'。**两条 SQL 都只接受 PENDING_PAY 这个起点**，数据库对同一行加行锁把它们串行化，所以最终只有一个的受影响行数等于 1。受影响行数等于 0 的那一方：支付这边抛'订单状态已变化，请刷新后查看'，关单这边直接跳过、**什么都不做**。这里最关键的一条纪律是：**库存回滚必须放在受影响行数等于 1 之后**——只有我真的把订单改成 TIMEOUT 了，才有资格回滚库存；否则就会出现'订单没关掉、库存却多了一件'。支付那边还做了幂等：进来看见已经是 PAID 就直接返回'无需重复支付'，因为真实支付回调本身就是至少一次的通知语义。**实测**：连续调两次支付，两次返回的 status 都是 PAID、第二次的 message 是'订单已支付，无需重复支付'，订单终态 PAID 且库存不再变化；不支付的那单 30 秒后变 TIMEOUT 且 Redis 和数据库库存各回滚 1 件。**边界我要主动说**：我们做的是**模拟支付网关回调**，不是真实支付；而且'支付和关单在同一毫秒对撞'这个实验我没有精确压出来，我验证的是两条路径各自正确且互不干扰。"

## 第 9 章 · 方法论总收口：七条 bullet 背后的五套方法论

> 这一章是**面试官最后一定会问的那一句**："你这些东西，抛开具体业务，总结一下？"
> 前面八章是"术"，这一章是"道"。**能把七条 bullet 收敛成五句话，比把七条讲得再细都值钱**——因为它证明的不是"我做过"，而是"我想清楚了"。

### 9.0 先给一张总图：五个矛盾，五套方法论

七条 bullet 看起来是七个技术点，但抽象一层，它们其实在回答五个反复出现的问题。面试时**先抛出这张图**，再往下展开：

| 系统里的永恒矛盾 | 对应 bullet | 方法论的名字 | 一句话内核 |
| --- | --- | --- | --- |
| 有限的资源 vs 无限的并发 | bullet ① | **高并发扣减** | 把"判断加执行"压成一个原子动作 |
| 热点数据 vs 数据库承载 | bullet ③④ | **缓存** | 先问"能陈旧多久"，再选策略 |
| 定时做某事 vs 不知道何时发生 | bullet ⑥ | **时序任务** | 预约优于轮询，且永不无兜底 |
| 多个人改同一条数据 | bullet ⑦ | **状态机** | 条件更新加影响行数，不靠锁 |
| 慢活 vs 用户在等 | bullet ② | **异步化** | 把不可控耗时挪出用户等待 |

### 9.1 方法论一：高并发扣减（bullet ①）

**一句话**：**凡是"有限资源被并发争抢"，都要先把"判断加执行"压成一个原子动作，再在真正的存储上加一道不可绕过的硬约束。**

**五条动作**：
1. **原子化**：把"读—判断—写"合并成一个不可分割的执行单元（Lua 脚本、单条带条件的 UPDATE、CAS）。
2. **条件前置**：判断条件写进执行语句本身（WHERE available_stock > 0），而不是"先 SELECT 再判断再写"。
3. **硬约束兜底**：无论前面多少层校验，最终必须有一条数据库级约束（唯一索引、条件更新返回行数）。
4. **分层承载**：高频扣减放内存存储（Redis），数据库只承接"已经过削峰的写入"，两者的差值由最终一致性收口。
5. **回滚分语义**：区分"用户什么都没拿到"（全额回滚：资源加机会）和"拿到过但作废"（只回滚资源）。

**适用范围**：库存扣减、优惠券核销、额度占用、积分扣减、限购名额——凡是"数量有限、并发争抢"的场景，五条一模一样。

### 9.2 方法论二：缓存（bullet ③④）

**一句话**：**缓存的所有决策都从同一个问题开始——"这份数据允许陈旧多久？"** 答案决定策略，而不是反过来。

**决策树**：
- 数据**不能陈旧**（库存、余额、订单状态）→ **不要放进这套缓存体系**，用实时读或强一致存储；我的做法是把剩余库存从活动详情缓存里摘出去，每次实时读 Redis。
- 数据**可以陈旧**，但数据库里也不存在 → **空值缓存**（短 TTL）或布隆过滤器，防穿透。
- 数据**可以陈旧**，是热点、且允许返回旧值 → **逻辑过期加异步重建**（不阻塞，实测 100 并发只重建 1 次）。
- 数据**可以陈旧**，但绝对不接受读到旧值 → **互斥锁重建**（阻塞等待，换强一致）。
- 数据**会被修改** → **Cache Aside（先库后删）加补偿重试加延迟双删加 TTL**，并把"删得掉、删得干净、最终会干净"三件事分清。
- **大批数据同时可能失效** → TTL 打随机扰动、多级缓存、哨兵集群。

**一句话补充**：**缓存一致性永远要给一个上界**。回答不出"最坏多久一致"的方案，等于没有一致性方案。

### 9.3 方法论三：时序任务（bullet ⑥）

**一句话**：**"到点做某事"优先用"预约"而不是"轮询"，并且任何预约机制都必须配一个兜底。**

**四条**：
1. **预约优于轮询**——延迟消息、定时器是事件驱动，扫表是轮询驱动；前者的成本与任务数成线性、精度由中间件保证，后者成本与数据量挂钩、精度受扫描周期限制。
2. **永不无兜底**——延迟消息会丢、内存定时器会随进程重启丢、外部回调会丢。所以低频对账必须存在，它的作用是让主机制从"必须可靠"降级成"尽量可靠"。
3. **兜底复用幂等主逻辑**——兜底任务调用和主机制**同一个方法**，因为主逻辑里的状态条件本身就是幂等保护。这样"双保险"的增量成本几乎是零。
4. **执行带状态前置条件**——UPDATE 语句里写"状态等于期望状态"，用影响行数判断"这次到底有没有发生"。

**适用范围**：订单超时关单、优惠券过期、订阅到期提醒、任务重试调度、库存释放。

### 9.4 方法论四：状态机（bullet ⑦）

**一句话**：**状态流转的正确性不靠锁保证，靠"条件更新加影响行数"保证**——这样无论有没有并发、有没有重复消息，结果都是确定的。

**四条**：
1. **先画状态机再写代码**——列出全部状态和合法迁移，非法迁移在代码里显式拒绝。
2. **迁移必带前置条件**——一条语句同时买到"互斥"（并发只有一个成功）和"幂等"（重复执行是空操作）两个性质。
3. **需要检测并发的加版本号**——状态条件保证"状态对"，版本号保证"这行没被别人动过"；冲突时返回**可重试**的提示而不是终结性错误。
4. **副作用挂在成功之后**——库存回滚、发通知、投消息只能放在"影响行数等于 1"的分支里。**顺序错了就会凭空多出一件库存。**

**适用范围**：订单状态、支付状态、工单流转、审批流、任何"只能从 A 到 B"的迁移。

### 9.5 方法论五：异步化（bullet ②）

**一句话**：**用户不关心的耗时，就不该占用户的等待时间**；但异步的前提是"用户能自己看到进度"。

**四条判断标准**（四条全中才异步）：① 耗时不可控（依赖外部服务或超过 200ms）；② 结果不影响本次响应；③ 有明确的成功失败状态且可重试；④ 失败可观测（日志、死信、后台）。

**四条配套**：① **一定要有结果查询接口**（我的 orderNo 轮询），否则异步就是把不确定性甩给用户；② **一定要有幂等**（消息至少一次）；③ **一定要有重试与死信**；④ **一定要说清"投递失败"这个窗口**（我的边界是"Redis 扣了但消息没发出去"，正解是本地消息表）。

### 9.6 五套方法论怎么串成一句话

如果面试官只给你 30 秒，就这样说：

> "我这七条 bullet 背后其实是同一个套路：**先找到系统里那个真正的矛盾，再把保证正确性下沉到最可靠的那一层，最后给每一条失败路径都安排一个归宿。**
> 库存的矛盾是"并发抢有限资源"，我就把判断和执行压进一次 Lua，把最终约束落在唯一索引上；
> 缓存的矛盾是"热点数据扛不住数据库"，我就先分级再选策略，用逻辑过期换不阻塞、用空值缓存挡穿透、用补偿加双删加 TTL 兜一致性；
> 时序的矛盾是"到点却不知道何时发生"，我就用延迟消息做预约、用对账做兜底；
> 状态流转的矛盾是"两个人改同一行"，我就用条件更新加版本号，让数据库自己裁定谁赢；
> 异步的矛盾是"慢活和用户在等"，我就把不可控的耗时挪走，同时给用户一个能看见进度的接口。
> **这五套东西的共同点是：正确性从来不依赖任何一个可能失效的组件。**"

### 9.7 三个"我刻意没做"的选择（主动说，非常加分）

面试官很可能会问"那你为什么不用 X"。**主动把这三条摆出来，比被他问出来强得多**：

1. **没有用分布式锁（Redisson）**——库存扣减用 Lua 原子化，订单状态用乐观锁，重复下单用唯一索引。这三处都不需要锁：锁能提供的是"临界区互斥"，而我在这三处的诉求分别是"原子执行""并发检测""不可绕过的约束"，都有比锁更贴的机制。**上一个项目我用的是 Redisson 加看门狗，这个项目刻意不用**——因为我要展示的是"按问题选工具"，不是"手里有锤子就看什么都是钉子"。
2. **没有引入 MinIO、没有引 LangChain4j**——上一个项目（OfferMate）用的是这两样：MinIO 做对象存储、LangChain4j 做大模型接入。这个项目是纯粹的电商高并发，用不上文件存储也没有 AI 场景。**技术栈跟着问题走，不跟着上一个项目走。**
3. **没有做真实支付、没有做运维后台**——支付是模拟网关回调，后台只有商家侧的接口。这两件我都在简历和文档里明确标注了"未实现"，**不写在简历上的功能，绝不假装做过**。

### 9.8 一分钟口述稿（被要求"总结一下你的项目"时照着说）
"我这个项目表面上是七条技术点，但我自己把它们收敛成五套方法论。**第一套是高并发扣减**：凡是有资源被并发争抢，就把'判断加执行'压成一个原子动作，再把最终约束落在数据库唯一索引上；**第二套是缓存**：所有缓存决策都从'这份数据能陈旧多久'这个问题出发，能陈旧的走逻辑过期，不能陈旧的干脆别缓存，一致性用 Cache Aside 加补偿加双删加 TTL 收口；**第三套是时序任务**：到点做某事优先用预约而不是轮询，而且任何预约机制都必须配一个低频对账兜底，兜底复用有幂等保护的主逻辑；**第四套是状态机**：状态流转的正确性不靠锁，靠'条件更新加影响行数'，副作用只能挂在改成功之后；**第五套是异步化**：用户不关心的耗时就不该占用户的等待时间，但前提是给用户一个能看见进度的接口。这五套东西有一个共同点——**正确性从来不依赖任何一个可能失效的组件**。另外有三个我刻意没做的选择我也会主动说：没用分布式锁（因为 Lua、乐观锁、唯一索引在这三处更贴），没引 MinIO 和 LangChain4j（用不上），支付是模拟的、后台只做了商家侧——**没做的我不会假装做过**。"

## 第 10 章 · 不会答时的三段式兜底话术

> 这一章的用途只有一个：**遇到不会、没做、答不上来的问题时，不沉默、不硬编、也不露怯。**
> 三段式的顺序很重要：**先承认边界（让他知道你有数）→ 再说清现有做法（证明你不是一无所知）→ 最后给出改进方向（展示判断力）**。三段说完，一道"不会的题"就变成了一道"你知道自己边界在哪儿的题"。

### 10.1 三段式的模板

**模板（背下来，改成自己的话）**：

> **第一段（承认边界）**："这块我确实没有做过 / 没有实测过，我不能给你编一个数字。"
> **第二段（说清现有做法）**："但我知道它在我的系统里对应的是哪一部分，我现在的做法是……，这样做的边界是……。"
> **第三段（给出改进方向）**："如果要做，我会这样下手：……，因为……。"

**为什么这个顺序有效**：面试官问一个你不会的问题时，他心里真正在测的是**"这个人会不会硬编""他知不知道自己系统的边界"**，而不是"他知不知道这个冷门知识点"。**承认边界展示的是诚实，说清现有做法展示的是对自己的系统有掌控，给出改进方向展示的是可迁移的判断力**——三样加起来，比勉强答对半道题更值钱。

**最坏的回答**（务必避免）：沉默、"这个我没接触过"然后停住、或者把不相关的知识堆上去试图蒙混。**只要开口说第一段，你就已经不失分了。**

### 10.2 十道高频"不会答"的题，直接照着说

**Q1："你们怎么保证消息不丢？"（追问到本地消息表、事务消息）**
【新手版】这块我只做到了一半：消费端不丢我能保证（业务成功才 ACK），生产端"扣了 Redis 库存但消息发失败"这个窗口，我做了一层同步重发兜底，但没有本地消息表，所以窗口只是变窄、没有消失。要做的话就是落一张本地消息表加定时任务扫表补发。
A：分三段如实说。**消费端**已经闭环：业务成功才 markSuccess，失败 markFailed 后抛出交给 RocketMQ 阶梯重试，超限进死信。**Broker 端**用的是持久化，进程重启不丢。**生产端做了两层、但仍不完整**：第一层是 asyncSend 的 onException 里**同步重发一次**（复用同一个消息体，走同步发送，能拿到 broker 自带的失败重试），第二层是再失败只打 error 日志。所以"扣减成功但消息最终没投递"这个窗口仍然存在——用户会一直轮询到 QUEUING，没有失败信号。改进方向是本地消息表（把扣减和待发消息写进同一处，定时任务补偿重投）或者 RocketMQ 的事务消息。**这条改进我没有实测，所以不给数字。**

**Q2："你怎么做分布式事务？"（TCC、Seata、Saga）**
【新手版】我没有用分布式事务框架，因为我的业务被切成了"Redis 扣减"和"数据库落库"两段，中间用消息连接，走的是最终一致加补偿，不是强一致的分布式事务。要上 Seata 的话，这套链路的性能就没法看了。
A：我的项目里没有引入 Seata 或 TCC 框架，原因是链路设计上**刻意避开了强一致分布式事务**：抢购是"Redis 原子扣减（预占）加 MQ 异步落库"，中间的不一致由 rollbackAll（还库存加还名额）和数据库唯一索引兜住，属于**最终一致加补偿**。要真做分布式事务（比如跨库扣款），我会按业务容忍度选：TCC 适合"能明确拆出 Try、Confirm、Cancel 三段"的资金类操作；Saga 适合长流程、允许中间态。**我诚实说没做过，但我知道我的架构为什么不需要它。**

**Q3："ES、分库分表、读写分离 你们做了吗？"**
【新手版】都没做。我的订单表现在还是单库单表，(user_id, activity_id) 和 order_no 上有唯一索引，activity_id 上有普通索引。数据量真上来的话，订单表按 user_id 分片是最自然的选择，因为这些查询都是"我的订单"这种按用户维度的。
A：没做，我会明确说清边界和**如果要做的分片键选择理由**：订单表的分片键应该选 user_id，因为绝大多数查询是"我的订单"（按 user_id 过滤、按创建时间倒序）和"我的订单详情"（按 order_no，而 order_no 里带了用户尾号，可以做成基因分片）；如果按 activity_id 分片，商家看活动订单会更快，但买家查自己的订单会变成跨片扫描——**按访问频率最高的维度分片**。读方面，订单详情是点查、很少改，适合读写分离；但支付和关单都是写，主库压力才是真瓶颈，所以先考虑分片再考虑读写分离。

**Q4："Redis 集群、哨兵你怎么部署的？"**
【新手版】没有，我是单机 Redis。所以我没有做 Redis 的高可用和故障转移，宕机了系统就降级成"所有缓存 miss、全部回源数据库"。要上生产的话，第一步是哨兵或者集群，第二步是给缓存加降级开关。
A：没有做，是单机 Redis（本地 Docker），这是这个演示项目的边界之一。我知道要补两件事：① **高可用**——哨兵做主从切换，或者上 Cluster 做分片（我的库存和已购记录都是单 key，热点明显，Cluster 下要做分片设计）；② **降级开关**——Redis 不可用时不应该让所有读请求直接穿透到数据库（那是雪崩），应该有"缓存不可用就直接拒绝非核心读"的开关。**我的实验环境里没测过 Redis 故障场景，所以我不编故障恢复时间的数字。**

**Q5："这个 QPS 能扛多少？压到多少并发会挂？"**
【新手版】我没有压出极限值，所以我不能给一个"能扛 X 万 QPS"的数字。我能说的是链路的瓶颈位置：主链路只剩一次 Redis 脚本加一次异步发消息，数据库写被挪到了消费端；真正先到瓶颈的会是 Redis 单分片的热 key。
A：**未实测**，我不编。能给出的定性判断是**瓶颈转移的顺序**：① 第一层是 Redis 单分片（同一活动所有请求打同一个 stock key 和 bought Hash），解法是按 userId 分片；② 第二层是 Tomcat 线程（max 配的是 200）和连接池（Hikari 20），但主链路不碰数据库，所以这一层压力比同步版本小得多；③ 第三层才是数据库——它面对的是削峰之后的写入。**我压过的是对比实验（异步对同步）和机制验证（不超卖、一人一单、缓存只回源一次），不是极限压测**，这个区别我会主动讲清楚。

**Q6："你这个 Lua 脚本为什么不用 EVALSHA？每次都传脚本不慢吗？"**
【新手版】我用的 DefaultRedisScript，Spring Data Redis 默认会先尝试 EVALSHA、脚本不存在再回退到 EVAL 并缓存 SHA，所以实际执行时脚本内容不会每次都在网络上传来传去。我没有单独优化这一点。
A：这一点我要如实说：**我没有手工做 EVALSHA 优化，用的是 Spring Data Redis 的 DefaultRedisScript，它内部的脚本执行器默认走 EVALSHA 加 SCRIPT LOAD 回退的机制**（先 EVALSHA，失败再 EVAL 并缓存）。所以"每次传输整个脚本"这个担心在默认配置下不会发生。如果要更极致，可以显式管理 SHA 并把脚本预加载到所有节点（Cluster 下每个节点都要有）。**我没测过这两者的性能差异，所以不给数字。**

**Q7："如果活动一开始就有几十万人同时抢，你的方案还成立吗？"**
【新手版】主链路本身是扛得住的（一次 Redis 脚本加一次发消息），但有两个地方会先出问题：一个是同一个活动的库存 key 和已购 Hash 是热 key，会集中在一个 Redis 分片上；另一个是消息量太大，消费端会积压。要改就是分片热 key 加扩消费实例。
A：定性回答：**架构方向成立，但有三处要先改**：① **热 key**——seckill:stock 和 seckill:bought 都是单 key，几十万并发会打爆单个分片，解法是按 userId 取模把已购 Hash 拆成 N 份、库存用分段扣减（每段独立扣、段间汇总）；② **消费积压**——几十万条下单消息会让消费端积压，而积压时间一旦超过订单超时时间就会时序错乱，所以要么扩消费实例、要么拉长超时；③ **限流阈值**——现在抢购是每人 1 秒 5 次，这个阈值对"几十万人"来说太宽，全局限流维度要真正启用起来（代码里定义了 GLOBAL 维度但当前没有接口用它）。**这些都是量级问题，不是架构错误**——这是我的判断，但没有实测数据支撑。

**Q8："你怎么测试超卖？有自动化测试吗？"**
【新手版】我用的是一个自己写的压测工具（纯 JDK 单文件），它会重置活动的库存和订单、然后并发打抢购接口，最后把"总库存、数据库剩余、Redis 剩余、订单总数、各状态订单数"打出来对照。这不是单元测试，是端到端的实验工具；项目里没有 JUnit 覆盖这套链路。
A：诚实说：**没有 JUnit 层面的自动化测试覆盖并发链路**，我用的是端到端的压测工具（bench/Bench.java），它通过断言函数把"期望值"写进输出（比如"关单后库存各加 1""同一用户只成功 1 次"），本质是**可重复执行的实验脚本**，不是 CI 里的测试。我认为这块应该补的形态是：① 用 Testcontainers 起 Redis 和 MySQL，写"并发 N 个线程抢 M 件库存，断言订单数等于 M"的集成测试；② 对 Lua 脚本做单元测试（内嵌 Redis 或 Testcontainers）；③ 把压测工具的关键断言搬进 CI 做冒烟。**这套我没做，是明确的缺口。**

**Q9："你觉得你这个项目最大的问题是什么？"**
【新手版】最大的问题是"演示配置"和"生产配置"没分开：超时 30 秒、限流阈值靠估、单机 Redis、没有对账兜底。这些问题不影响演示，但上生产一件都不能留。
A：三个层次如实说：① **可靠性缺口**——"扣了库存但消息没发出去"没有自动补偿（异步失败只做了同步重发一次，缺本地消息表）；"延迟消息丢了订单永远待支付"没有对账兜底（缺定时补关单）；双删消息丢失没有二次兜底。② **可运维缺口**——限流阈值硬编码在注解上、超时时间只能改配置文件重启、没有监控告警看板（缓存补偿表的 PENDING 积压、死信队列的堆积都没有告警）。③ **实验缺口**——一致性方案没有量化验证，缓存穿透和击穿的实验是有的，但延迟双删的效果、乐观锁对撞的时序都没有专门的实验。**如果只能补一件，我补本地消息表加对账任务**，因为那两条是唯一会导致"用户拿到 orderNo 却永远没有订单"的路径。

**Q10："如果重做一遍，你会改什么？"**
【新手版】三件事：第一，把"扣减加记录待发消息"放进同一处，用本地消息表消掉那个投递窗口；第二，加一个低频对账任务兜住丢失的延迟消息；第三，把限流阈值和超时时间挪到配置中心。技术选型上我不会改——Lua、乐观锁、唯一索引、延迟消息这几个选择放到现在我还是这么选。
A：我会改三层，但**不会改选型**：
- **正确性层**：本地消息表消掉"扣减成功但消息未投递"的窗口；对账任务补关单；对账任务同时校验 Redis 与数据库的库存差值。
- **可运维层**：限流阈值和超时时间挪到配置中心；补死信与补偿表的监控告警；把 cache_sync_task 的 PENDING 积压做成指标。
- **验证层**：补 Testcontainers 的并发集成测试，把压测工具里的关键断言（不超卖、一人一单、只回源一次、关单回滚）搬进 CI。
**选型为什么不变**：这三个选择（Lua 做原子扣减、乐观锁做状态流转、唯一索引做兜底）至今我仍然认为是对的——它们都遵循同一个原则：**正确性不依赖任何一个可能失效的组件**。如果重做，我只会把它做得更完整，不会换掉它。

### 10.3 被质疑时的三段式（"这项目是不是跟教程做的？"）

这是最需要稳住的一类问题。**不要急着辩解，也不要怂，用三段式反过来展示厚度**：

**第一段（承认共性，不否认）**："您说的那套东西（Redis 预减库存、MQ 异步下单、延迟消息关单）确实是秒杀的标准套路，我一开始也是照着这个思路做的，市面上讲这套的资料很多。"

**第二段（把差异讲出来——这一步是关键）**："但我在实现的时候有几处和常见教程不一样，而且是我自己想清楚才这么写的：
① **一人一单我用 Hash 存已购数量，而不是 Set 或 String**——因为限购判断本质是"数量比较"（bought 加 1 是否超过限购件数），而且下单失败时我要能把这个人的已购数量减回去。当前活动限购固定 1 件，但存数量的写法保留了扩展成每人限购 N 件的空间（真要放开，得同时改订单表的唯一索引形状）；
② **超时关单我只回滚库存、不回滚已购记录**——名额已经用掉了，不付款就作废，货退回池子给别人抢；只有订单根本没落库的下单失败才把机会一起还回去。这个区别是我从"黄牛占位"这个攻击场景倒推出来的；
③ **缓存我没用互斥锁重建，用的是逻辑过期**——因为互斥锁会让过期瞬间的请求排队等待，而活动详情允许短暂陈旧、不接受响应变慢；
④ **我刻意没有引入分布式锁**——Lua 加乐观锁加唯一索引这三处都有比锁更贴的机制。"

**第三段（把验证讲出来）**："而且这些不是我觉得对，是压出来的：同一个用户并发抢只成功 1 次；缓存被删后 100 个并发只回源 1 次；逻辑过期瞬间 100 个并发全部成功、只触发 1 次重建；关单后 Redis 和数据库库存各回滚 1 件，订单状态分布是 PAID 一条、TIMEOUT 一条。压测工具是我自己写的纯 JDK 单文件，用什么口径测、怎么重置数据、怎么断言，都在代码里。"

### 10.4 反问环节：准备三个问题，问出你的技术品味

面试官问"你有什么想问我的"时，**问题本身就是你的水平展示**。不要问"公司福利""加班多吗"，问这三个：

1. **"这个岗位负责的系统，现在最大的性能瓶颈或者稳定性隐患在哪儿？"**
   —— 展示你关心的是问题而不是待遇，而且能听出这个团队有没有在解决真问题。
2. **"团队现在做需求，从评审到上线大致是什么流程？有没有代码评审和压测环节？"**
   —— 展示你在意工程规范，也能判断这里是不是一个能让你成长的环境。
3. **"如果我入职，前三个月您希望我在哪个方向上先产出价值？"**
   —— 展示你在想"怎么贡献"而不是"怎么学习"，同时把话题引回你的强项。

**反问的红线**：不要问能直接搜到的东西（公司做什么的）、不要问薪资福利（留给 HR 环节）、不要问"我表现得怎么样"（把评价压力推给对方，且得不到真话）。

### 10.5 三条红线（贴在桌上）

1. **不编数字**。没实测就说"未实测"，然后讲原理和设计。我这份文档里所有数字都来自 bench/Bench.java 的真实运行结果，凡是没压过的（Redis 单分片 QPS、极限并发、故障恢复时间、一致性量化）都明确标了"未实测"。
2. **不假装做过**。支付是模拟的、后台只有商家侧、没做分片、没做 Redis 高可用、没有 JUnit 覆盖并发链路——这些我全都主动说，并且都说清"如果要做会怎么做"。
3. **不背不属于自己的结论**。简历上每一条我都能画图、能说出代码在哪个文件、能讲出为什么这么选、以及它的边界在哪儿。**画不出来的，就从简历上删掉。**

### 10.6 一分钟口述稿（"遇到不会的怎么办"的心理准备）
"我给自己定了一个三段式：**先承认边界，再说清现有做法，最后给改进方向**。比如被问到分布式事务，我会说这块我没做过、不编数字；但我知道我的架构为什么不需要它——我把链路切成了'Redis 原子扣减加 MQ 异步落库'，走的是最终一致加补偿，中间的不一致由回滚和唯一索引兜住；如果要做，我会按业务容忍度在 TCC 和 Saga 之间选。这三段说完，一道不会的题就变成了'我知道自己边界在哪儿'的题。**被质疑项目是不是跟教程做的时候，我不会辩解，我会承认这套套路是标准的，然后把我和标准做法不一样的地方讲出来**——一人一单用 Hash 支持限购 N 件、关单只还货不还机会、缓存用逻辑过期而不是互斥锁、刻意不用分布式锁——最后用压测数字收尾。**三条红线我贴在桌上：不编数字、不假装做过、不背不属于自己的结论。**"
