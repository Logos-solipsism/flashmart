## 二、各阶段详述

### 阶段〇 前置准备

**做什么**

1. 装 JDK 17、Maven、Node 18+、Docker Desktop。
2. **先规划端口**再动手。本项目占用：MySQL 13307、Redis 6380、RocketMQ namesrv 9877、broker 10912、后端 18090、前端 5274、RocketMQ Dashboard 8181。全部刻意避开 3306 / 6379 / 9876 / 8080，方便与其他项目在同一台机器上共存。
3. 确定不用哪些组件：不引 MinIO（商品图用 `cover_color` 色块）、不引 LangChain4j、不引 Redisson。**在写第一行代码前把"不用什么"定下来**，比写到一半再砍成本低得多。

**怎么验收**

- `java -version` 输出 17.x；`mvn -v`、`node -v`（≥18）、`docker version` 均可用。
- 用 `netstat -ano | findstr "13307 6380 9877 10912 18090 5274"` 确认这些端口当前没有被占用。

### 阶段一 骨架与中间件

**做什么**

1. `server/pom.xml`：SpringBoot 3.2.5 parent、web / aop / validation / data-redis、`rocketmq-spring-boot-starter` 2.3.0（**SpringBoot 3 必须用 2.3.0 及以上**）、`mybatis-plus-spring-boot3-starter` 3.5.5（注意是 `-boot3-` 那个 artifact）、`spring-security-crypto`（只要 BCrypt，不引整个 Spring Security）、jjwt 0.12.5、Knife4j 4.5.0。
2. `docker-compose.yml`：MySQL / Redis / RocketMQ namesrv + broker + Dashboard 五个服务；MySQL 把 `schema.sql` 与 `data.sql` 挂到 `/docker-entrypoint-initdb.d/` 并加 `01-` / `02-` 数字前缀（容器按文件名字母序执行）；另外把 `deploy/mysql-client.cnf` 挂到 `/etc/mysql/conf.d/charset.cnf`，让初始化脚本执行时的客户端字符集是 utf8mb4 —— 否则中文种子数据会被二次编码成乱码。
3. `deploy/broker.conf`：`brokerIP1 = 127.0.0.1`、`listenPort = 10912`、`autoCreateTopicEnable = true`。**Docker 场景必配**，否则宿主机上的客户端从 namesrv 拿到的是容器内网地址，连不上。
4. `FlashMartApplication`（`@MapperScan("com.flashmart.**.mapper")`）、`application.yml`（每一项都写成 `${ENV:默认值}`，保证不配环境变量也能跑）。
5. 公共层：`R<T>` 统一响应、`BizException` + `GlobalExceptionHandler`、`TraceIdFilter` + `TraceUtil`。
6. `WebConfig`：BCrypt Bean + 拦截器注册（这个阶段先把拦截器留空或放行全部）。

**怎么验收**

```bash
docker compose up -d
docker compose ps                     # 五个服务都是 running
docker exec -it flashmart-redis redis-cli -a redis123456 ping          # PONG
docker exec -it flashmart-mysql mysql -uroot -proot123456 -e "select 1" # 能连上
```

启动后端后：

- `GET http://localhost:18090/doc.html` 能打开 Knife4j 页面。
- 任意一个不存在的接口返回体是 `R` 结构而不是 Spring 默认的 404 JSON —— 说明 `GlobalExceptionHandler` 生效。
- 日志前缀形如 `22:13:04.512 INFO [a1b2c3d4e5f6a7b8] c.f...` —— 说明 traceId 已经进了 MDC；响应头里也能看到 `X-Trace-Id`。
- 打开 <http://localhost:8181> 能看到 RocketMQ Dashboard 的 broker 列表（**这一步是后面所有 MQ 工作的前提**，broker 起不来先解决 `brokerIP1` 问题）。

**完成判据**：五个中间件 + 后端空壳能同时跑起来，traceId 出现在日志与响应头里。

### 阶段二 数据库与基础业务

**做什么**

1. `db/schema.sql`：6 张表。这一阶段要把索引一次性想清楚，尤其是：
   - `seckill_order` 上的 `UNIQUE KEY uk_user_activity (user_id, activity_id)` —— 一人一单的最后一道防线，**不能等出问题再加**；
   - `mq_consume_log.uk_msg_id` —— 消费幂等的依据；
   - `flash_activity.idx_time (start_time, end_time)` —— 活动列表按开始时间排序；
   - 金额字段全部 `INT`（分）。
2. `db/data.sql`：4 个账号（id 从 9001 起，避开库里已有数据）、6 个商品、4 个活动 —— 其中 9003 是"两分钟后开始"、9004 是"已结束"，**提前把三个时间窗口分支的演示数据准备好**。
3. 6 张表的实体（`@TableName` / `@TableId(AUTO)` / `@TableLogic deleted`）与 Mapper（继承 `BaseMapper`）。
4. 认证：`AuthController`（注册/登录）、BCrypt 加密、`JwtUtil` 签发、会话写 Redis（`session:token:{userId}`，24 小时）、`AuthInterceptor` 解析 JWT → 校验会话 → 写 `UserContext`。
5. 商品模块：`ProductController`（在售列表）、`ProductService`（商家创建与自己的商品）。

**怎么验收**

```bash
docker compose down -v && docker compose up -d      # 让初始化脚本重新执行
docker exec -it flashmart-mysql mysql -uroot -proot123456 flashmart -e "show tables;"
docker exec -it flashmart-mysql mysql -uroot -proot123456 flashmart -e "show index from seckill_order;"
```

- `show tables` 返回 6 张表；`show index` 里能看到 `uk_user_activity`、`uk_order_no`、`idx_user_status`、`idx_activity`。
- 用 13811110001 / 123456 登录返回 token；用错误密码返回"手机号或密码错误"。
- **不带 token** 访问 `/api/merchant/product/mine` 返回 HTTP 401 且 body 是 `{"code":401,...}`（拦截器直接写响应，不经过 `@RestControllerAdvice`）。
- 带 token 访问 `/api/auth/login` 之外的任意 `/api/**` 都正常；`/api/auth/**` 不需要 token（`WebConfig` 放行）。
- Redis 里能看到 `session:token:9003`，且 `TTL` 接近 86400 秒。
- 商家登录后创建商品 → `GET /api/merchant/product/mine` 能查到；用买家 token 调同一个创建接口返回 **HTTP 200 + code 403「只有商家账号可以执行该操作」**（`/api/merchant/**` 统一校验 MERCHANT 角色，前端的路由拦截只是体验层）。

**完成判据**：两种角色都能登录并拿到 token，商品数据能落库并查出来，空 token 请求被稳定拦成 401。

### 阶段三 缓存与限流

这一阶段是项目技术含量的第一半，**顺序不能乱**：先把读路径的缓存做对，再做限流，最后做写路径的缓存一致性（它依赖 MQ 基础设施）。

**做什么**

1. MQ 基础设施（先做，后面两个子任务都要用）：`MqTopics`（三个 topic + 三个消费组）、`MqEvents`（三个消息 record）、`MqProducer`（异步发送 + **失败后同步重发一次**的兜底 + 延迟档位换算 `nearestDelayLevel` + traceId 透传）、`MqIdempotentRepository` + `mq_consume_log` 实体与 Mapper。
2. 缓存读路径：`RedisCacheClient.getWithLogicExpire` —— 逻辑过期（value 包成 `{expireAt, data}`，物理 TTL = 逻辑 × 3）+ SETNX 异步重建 + 空值标记 `NULL_MARK`；配套 `countLoad` 回源计数（这是后面压测能量的前提）。
3. 活动模块：`ActivityCacheKeys`（Redis key 集中定义）、`ActivityCacheVO`（**刻意不含剩余库存**）、`ActivityService`（列表 / 详情 / 商家创建与修改 / 库存预热）、`ActivityController`。
4. 限流三件套：`SlidingWindowLimit` 注解（含 `Dimension` 枚举）、`SlidingWindowAspect`（拼 key、从 `UserContext` 取身份、超限抛 429）、`SlidingWindowLimiter`（执行脚本、Redis 异常降级放行）、`lua/sliding_window.lua`。挂到 `AuthController.login`（IP 维度；登录、注册不走拦截器，`UserContext` 是空的，所以切面改成从当前 HTTP 请求里取真实 IP —— 否则所有登录请求会挤进同一个桶，IP 维度退化成全局限流）。
5. 缓存写路径：`CacheEvictService`（Cache Aside + 失败落 `cache_sync_task` + 投 MQ + 延迟双删）、`CacheEvictConsumer`（处理 UPDATE / DOUBLE_DELETE 两类消息）、`CacheSyncTask` 实体与 Mapper。挂到 `ActivityService.update`。

**怎么验收**

| 验收项 | 操作 | 通过标准 |
| --- | --- | --- |
| 逻辑过期不阻塞 | 起 bench profile，`java Bench.java --exp cache-miss --activity 9001 --concurrency 100` | 100 个并发请求**全部成功**返回详情；`cache:loadcount:activity:detail:9001` 为 1（只触发一次异步重建）；实测逻辑过期瞬间 100 并发总耗时 119ms |
| 冷启动只回源一次 | 先 `GET /api/activity/9001` 预热，再 `POST /api/bench/reset/9001`（会删缓存并清零计数），然后并发打 100 次详情 | 回源计数为 1、100 个请求总耗时 114ms（修复前是回源 100 次） |
| 空值缓存防穿透 | `java Bench.java --exp cache-penetrate --activity 99999 --times 200` | 200 次查询不存在的活动，累计回源计数 ≤ 1；`GET activity:detail:99999` 的值是 `__NULL__` |
| 限流拦突发 | `java Bench.java --exp ratelimit --activity 9001` | 1 秒内并发 10 次 → **5 通过 + 5 × HTTP 429**；改成 1.2 秒一次 → 全部通过（429 为 0）。登录接口（IP 维度、20 次/秒）并发 30 次 → **20 通过 + 10 × 429** |
| 缓存一致性 | 商家后台改活动总库存（100 → 80），立刻刷新活动详情 | 详情返回新的总库存；`cache_sync_task` 表无新增记录（删除成功不需要补偿） |
| 补偿链路可用 | 停掉 Redis → 商家改活动 → 恢复 Redis，再看 `cache_sync_task` 与日志 | 改活动时 `cache_sync_task` 立即出现一条 `PENDING` 记录，说明"删除失败 → 落库 + 投 MQ"这条链路是通的；Redis 恢复后消费者重试删除成功，活动详情下一次读能回源到新值。注意：任务行的状态回写条件是 `status != SUCCESS`（原先写死 `= PENDING`，失败过的任务即使重试成功也回不到 `SUCCESS`），并且每次回写都会把 `retry_count` 加一 |
| 限流降级 | 停掉 Redis，调用登录接口 | **不报错、正常登录**（`SlidingWindowLimiter` 捕获异常后放行，日志里有"滑动窗口限流降级放行"） |

**完成判据**：缓存三兄弟（击穿 / 穿透 / 一致性）各有可复现的数字或状态，限流 429 能稳定复现且 Redis 挂掉不熔断业务。

### 阶段四 抢购链路

**做什么**

1. `lua/seckill_stock.lua`：把"判断库存 + 判断限购 + 扣库存 + 记已购"合成一次执行。四个返回码 `>=0 / -1 / -2 / -3` 在这一步就要定死并写进注释，后面的 Java 与压测分类都依赖它。
2. `SeckillStockService`：加载脚本为 `RedisScript<Long>`（`lua/seckill_stock.lua` 与 `lua/rollback_stock.lua`）、`ensurePrepared`（库存 key 不存在时才按数据库 `available_stock` 预热，并写入 `seckill:total:{id}` 作为回滚上限）、`reset`（强制覆盖，商家改活动用）、`currentStock`、`trySeckill`、`rollbackStock`（只回滚库存，带上限）、`rollbackAll`（库存 + 已购记录一起回滚，已购数量只在大于 0 时才减）。**两个回滚方法的语义差异要在这一步就想清楚**，否则超时关单会做错。
3. `SeckillService`：缓存校验活动 → 状态/开始/结束时间三重校验 → 幂等预热 → Lua 扣减 → 按返回码抛对应文案 → 生成订单号 → 发 MQ → 返回 `{orderNo, state:"QUEUING", message}`；`result(orderNo)` 提供轮询接口（未落库返回 QUEUING，非本人 403）。
4. `OrderNoGenerator`：`FM + yyyyMMddHHmmss + userId 后三位 + 6 位进程内自增序列`（共 25 位）。原来用 4 位随机数，实测两万次生成撞了 207 次，而 `order_no` 上有唯一索引，撞号就是下单直接失败。
5. `OrderCreateConsumer`：幂等 `tryAcquire` → 调 `OrderService.createOrder` → 成功则投延迟关单消息；重复下单（唯一索引拦下）与异常（数据库库存扣不动）都走 `rollbackOnce`（`seckill:rollback:{msgId}` 的 SETNX 保证每条消息只回滚一次，内部调 `rollbackAll`）。
6. `SeckillController`：挂 `@SlidingWindowLimit(key="seckill", windowSeconds=1, maxRequests=5, dimension=USER)`。

**怎么验收**

| 验收项 | 操作 | 通过标准 |
| --- | --- | --- |
| 抢购能走通 | 演示账号抢活动 9001 | 返回 `{orderNo, state:"QUEUING"}`；Redis `seckill:stock:9001` 从 100 变 99；`seckill:bought:9001` 里出现该 userId |
| 接口足够快 | 看接口耗时（前端 Network 或 bench 的延迟表） | 返回耗时约 **28ms**（不写库，只做 Redis + 发消息） |
| 异步落库 | 抢购后轮询 `/api/seckill/result/{orderNo}` | 从 `QUEUING` 变为 `PENDING_PAY`，实测约 **157ms**；`seckill_order` 里有对应行 |
| 一人一单 | `java Bench.java --exp oneuser --activity 9001 --times 20` | 同一用户并发 20 次**只成功 1 次**（实测分布：成功 1 + 限购 4 + 429 共 15，限流在限购之前生效）；再按 1.2 秒间隔匀速发请求 → 限流 0 次、全部被"每人限购 1 件"拦下 |
| 不超卖 | `java Bench.java --exp oversell --activity 9001 --stock 100 --users 500` | `orderCount == 成功数 <= totalStock`；DB 与 Redis 剩余库存均非负。实测（活动 30 件库存 / 60 个不同用户并发）：成功 30 次、落库 30 单、DB 剩余 0、Redis 剩余 0 |
| 唯一索引兜底 | 手工 `DEL seckill:bought:9001` 后让同一用户再抢 | Redis 侧放行，但数据库 `uk_user_activity` 拦下 → 消费者 catch 后回滚，订单表仍然只有一行 |
| 限流生效 | 连点抢购按钮 10 次 | 前 5 次进入业务逻辑，第 6 次起 HTTP 429 且 message 是"手速太快啦，歇一秒再抢" |

**完成判据**：500 个不同用户并发抢 100 件，订单数 ≤ 100 且库存不为负；同一用户并发只能成功一次。

### 阶段五 订单与关单

**做什么**

1. `OrderService.createOrder`（`@Transactional`）：`activityMapper.decreaseStock`（`WHERE available_stock > 0`），**返回 0 行就抛「数据库库存已扣不动，本次下单失败」**（文案只描述数据库这一侧，Redis 侧的回滚由消费者做）→ `insert` 订单 → 捕获 `DuplicateKeyException` 时 `increaseStock` 并把数据库库存还回去、返回 `null`。
2. `OrderService.pay`：归属校验 → 已支付直接幂等返回 → 非 PENDING_PAY 拒绝 → `payWithVersion`（`WHERE order_no=? AND status='PENDING_PAY' AND version=?`）→ 受影响 0 行说明被并发改过，抛"订单状态已变化"。
3. `OrderService.timeoutOrder`：`timeoutIfPending`（`WHERE order_no=? AND status='PENDING_PAY'`）→ 受影响 0 行直接跳过 → 成功才双端回滚（`activityMapper.increaseStock` + `stockService.rollbackStock`），两侧都带上限：DB 侧 `WHERE available_stock < total_stock`，Redis 侧 `lua/rollback_stock.lua` 比较 `seckill:total:{id}`。
4. `OrderController`：我的订单、订单详情、支付（挂 USER 维度 1 秒 3 次限流）。
5. `OrderTimeoutConsumer` + `OrderCreateConsumer` 里投递延迟消息（`nearestDelayLevel(orderTimeoutSeconds)`，默认 30 秒 → level 4）。
6. `OrderService.toVO` 补 `payDeadline`（= 创建时间 + 超时秒数），供前端算支付倒计时。

**怎么验收**

| 验收项 | 操作 | 通过标准 |
| --- | --- | --- |
| 支付成功 | 抢购后立即 `POST /api/order/{orderNo}/pay` | 返回 `status=PAID`；数据库里 `pay_trade_no`、`pay_time` 有值，`version` 从 0 变 1 |
| 支付幂等 | 对同一订单再点一次支付 | 返回"订单已支付，无需重复支付"，`version` 不再变化 |
| 超时关单 | 抢购后不支付，等 30 秒 | 订单状态变 `TIMEOUT`（**实测：第 30 秒变为 `TIMEOUT`**），`cancel_time` / `cancel_reason='TIMEOUT'` 有值，`version` +1 |
| 库存回滚 | 对比关单前后的 `BenchService.stats` | DB `available_stock` 与 Redis `seckill:stock:{id}` **各 +1** |
| 关单不回滚名额 | 关单后同一用户再抢 | 被"每人限购 1 件"拦下（库存退回池子，但名额已作废） |
| 已支付不会被误关 | 抢购后立刻支付，再用 `POST /api/bench/force-timeout/{orderNo}`（延迟 1 秒）触发关单 | 订单仍是 `PAID`，`timeoutIfPending` 返回 0，库存**不回滚** |
| 双路径并存 | 一个活动上：一单支付、一单超时 | 订单状态分布为 `PAID:1 / TIMEOUT:1`（这就是延迟 30 秒实测得到的分布） |
| 支付限流 | 1 秒内连续调支付 5 次 | 第 4 次起 HTTP 429（`maxRequests=3`） |

**完成判据**：支付与关单任意并发发生，最终状态唯一且库存只被回滚一次。

### 阶段六 前端

**做什么**

1. `vite.config.js`：端口 5274，`/api` 代理到 18090（前端不写死后端地址）。
2. `src/api.js`：`fetch` 封装 —— 自动拼 `/api`、自动带 `Authorization: Bearer`、统一解包 `data`、`payload.code !== 0` 抛错、**401 清登录态并跳登录页**、429 把后端原文抛给页面。

4. `src/router.js`：hash 路由 + 登录守卫 + `/merchant` 的角色拦截（非 MERCHANT 送回 `/activities`）。
5. 五个页面：`Login.vue`、`ActivityList.vue`、`ActivityDetail.vue`（抢购 → **400ms 轮询结果，最多 15 秒** → 用 `payDeadline` 与 `serverTime` 校准后的支付倒计时）、`MyOrders.vue`、`Merchant.vue`。

**怎么验收**

- `cd web && npm install && npm run dev`，打开 <http://localhost:5274> 能跳登录页。
- 未登录直接访问 `#/orders` 被守卫送回登录页；用买家账号登录后手动改 hash 到 `#/merchant` 被送回 `#/activities`。
- 抢购成功后页面上依次出现"排队中"→"订单已生成，请尽快支付"+ 倒计时；倒计时与服务器时间一致（不会出现整体偏移 8 小时）。
- 表头显示当前昵称与角色；商家账号能看到"商家后台"入口。
- `node web/.smoke-test.mjs` 18 步全部返回预期结果。

**完成判据**：不看后端日志，仅凭浏览器就能把"商家建活动 → 买家抢购 → 支付 → 商家看订单"这条主线跑完。

### 阶段七 压测

这一阶段的目标不是"跑出好看的数"，而是**让每个结论都能被第三方复现**。所以先写工具，再采数据。

**做什么**

1. `bench/Bench.java`：纯 JDK 单文件（`HttpClient` + 手写 JSON 解析器 + 虚拟线程/平台线程自动探测 + 中文宽度对齐的 ASCII 表格）。九个实验：`prepare` / `oversell` / `oneuser` / `throughput` / `cache-miss` / `cache-penetrate` / `ratelimit` / `timeout` / `pay`。
2. 服务端压测接口（`@Profile("bench")` 隔离）：`BenchService.reset`（DB + Redis 库存、已购记录、回源计数、**物理删除订单**）、`seckillAsyncSynthetic`（合成用户、跳过一人一单、走真实 Lua + MQ 链路）、`seckillSync`（同步对照组）、`stats`、`forceTimeout`、回源计数查询与重置。
   - 为什么必须做合成用户：真实接口有一人一单和限流，同一个账号只能成功一次，压不出并发。
   - 为什么必须物理删订单：逻辑删除的行仍占着 `uk_user_activity`，会让用户之后再也下不了单（`SeckillOrderMapper.deleteByActivityPhysically` 的注释写了这一点）。
3. 按实验采集并记录数字；测不到的宁可写"未获取到"，不编。

**怎么验收**

- `java Bench.java --help` 能打印全部实验与参数。
- 每个实验都有明确的 PASS/FAIL 判据，而不是只打一张表。例如：
  - `oversell`：`orderCount == 成功数`、`orderCount <= totalStock`、DB/Redis 库存非负、无异常分支；
  - `oneuser`：`ok == 1`，且匀速 5 次全部被限购拦下；
  - `cache-miss`：`loadCount < concurrency`；
  - `cache-penetrate`：`loadCount <= 1`；
  - `ratelimit`：`http200 == 5`、`http429 > 0`，且匀速 5/5 通过；
  - `timeout`：最终状态 `TIMEOUT`，Redis 与 DB 各 +1；
  - `pay`：第一次支付成功、第二次幂等、最终状态 `PAID`。
- **必须做异步/同步对照**：`--exp throughput --mode async` 与 `--mode sync` 各跑一遍，条件（库存、并发、请求数、预热次数）完全一致，唯一差别是不发消息。实测（50 并发 / 2000 请求，压测客户端与服务同机）：**异步 176 req/s、平均 280.66ms、P50 282ms、P90 307ms、P95 315ms、P99 329ms**；**同步（对照组）39 req/s、平均 1259.62ms、P50 1261ms、P90 1359ms、P95 1394ms、P99 1462ms** → **吞吐约 4.5 倍、单请求平均耗时降约 78%、P99 降约 77%**。

**已知的实测结论（来源均为 bench 实验）**

| 结论 | 数字 |
| --- | --- |
| 抢购接口返回耗时（异步版） | 28ms（主链路不写数据库） |
| 异步下单落库 | 接口返回后约 157ms 订单落库（状态 `PENDING_PAY`） |
| 削峰对比（50 并发 / 2000 请求，同机） | 异步 176 req/s、平均 280.66ms、P50 282ms、P90 307ms、P95 315ms、P99 329ms；同步（对照组）39 req/s、平均 1259.62ms、P50 1261ms、P90 1359ms、P95 1394ms、P99 1462ms → 吞吐约 4.5 倍、单请求平均耗时降约 78%、P99 降约 77% |
| 超卖验证（30 件库存 / 60 个不同用户并发） | 成功 30 次、落库 30 单、数据库剩余库存 0、Redis 剩余库存 0（成功数 = 落库数 = 总库存），无超卖、库存非负 |
| 一人一单（同一用户并发 20 次） | 成功 1 次 + 限购 4 次 + 429 共 15 次（限流在限购之前）；改成每 1.2 秒 1 次匀速请求 → 限流 0 次、全部被"一人一单"拦下 |
| 滑动窗口限流 | 同一用户 1 秒内 10 并发 → 5 通过 + 5 × 429（阈值 5 次/秒）；匀速 1.2 秒 1 次 → 全部通过 |
| 缓存击穿（详情缓存被删后 100 并发） | 回源数据库 1 次，100 个请求总耗时 114ms（修复前是回源 100 次） |
| 缓存击穿（逻辑过期瞬间 100 并发） | 全部成功，只触发 1 次异步重建，耗时 119ms |
| 缓存穿透 | 查询不存在的活动 200 次，只回源 1 次 |
| 超时关单 | **生产档位 30 秒**：第 30 秒订单变为 `TIMEOUT`，数据库与 Redis 剩余库存各 +1；关单后同一用户再抢被"每人限购 1 件，你已经抢到啦"拦下（库存退回池子、名额不退）。1 秒档（压测接口）：关单消息到点后下一次轮询 22 ms 内看到 `TIMEOUT` |
| 支付幂等 | 两次支付都返回 `PAID`，第二次 message = "订单已支付，无需重复支付" |
| 登录 IP 维度限流 | 并发 30 次登录 → 通过 20 + 限流 10（阈值 20 次/秒） |

口径：以上数字都是在本机 Windows + Docker 中间件、压测客户端与服务同机、闭环压测模型的条件下跑出来的，测前清空数据表并等 MQ 排空。没有实测的项目一律写"未实测"，不做推算。

**完成判据**：把工具交给另一个人，他能照着命令跑出同样的结论。

## 五、常见坑（按踩到的顺序记录）

1. **RocketMQ broker 起不来 / 宿主机连不上**：Docker 场景必须在 `deploy/broker.conf` 里配 `brokerIP1` 为宿主机可达的地址，且 `listenPort` 必须与 compose 里映射出来的端口一致（客户端是拿 `brokerIP1:listenPort` 去连的）。另外 broker 容器默认以 `rocketmq` 用户运行，而挂载进去的 `store` 卷属于 root，会写不进去导致启动失败 —— compose 里已经加了 `user: root`。
2. **SpringBoot 3 用 RocketMQ**：starter 必须 2.3.0+；用 2.2.x 会因为 Jakarta 命名空间的问题启动报错。
3. **MyBatis-Plus 在 SpringBoot 3 下**：artifactId 是 `mybatis-plus-spring-boot3-starter`，不是 `mybatis-plus-boot-starter`。
4. **逻辑删除与唯一索引冲突**：`deleted=1` 的行仍然占用 `uk_user_activity`。压测重置必须用物理删除 SQL，否则同一用户之后永远下不了单。这个问题是在压测阶段暴露出来的。
5. **空值标记有 30 秒 TTL**：反复跑 `cache-penetrate` 实验时，第二次跑会因为上一次留下的 `__NULL__` 而回源 0 次。工具里已经做了"探测 → 等待 TTL 过期 → 重置计数"的处理（`--no-wait` 可跳过等待）。
6. **延迟双删的延迟必须落在 RocketMQ 的固定档位上**：RocketMQ 只支持 1s / 5s / 10s / 30s… 这些档位，所以配置项直接按秒给（`double-delete-delay-seconds: 5`，实际生效 5 秒）。原先配的是毫秒（`double-delete-delay-millis: 500`），代码里还要折算一次，配出来的值和实际生效值对不上。
7. **限流会污染压测结论**：`oversell` / `throughput` 必须用合成用户（`BenchService` 里的路径不走限流注解），否则 429 会把成功率算错。反过来，`oneuser` 实验就是要故意吃限流，观察记录里要能把"429 拦下的"和"限购拦下的"分开统计。
8. **并发压测前必须预热**：`throughput` 实验里有 20~100 次不计入统计的预热请求，把连接、JIT、缓存都捂热，否则第一次跑出来的数字会明显偏差。
9. **前端时间解析**：后端返回的是不带时区的 ISO 本地时间字符串，直接用 `new Date(str)` 在部分浏览器会按 UTC 解析，倒计时会整体偏移。`utils.js` 的 `parseTime` 用正则手工构造 `Date`，详情接口还额外返回 `serverTime` 让前端校准本地时钟。
10. **改过 DDL 之后要重建数据卷**：`docker-entrypoint-initdb.d` 只在数据目录为空时执行，改 `schema.sql` 后要 `docker compose down -v`。
11. **中文种子数据乱码**：容器初始化时执行 `db/*.sql` 用的是容器里的 mysql 客户端，客户端字符集不是 utf8mb4 时中文会被二次编码，现象是"接口新建的数据正常、`data.sql` 里的种子数据全是问号或怪字符"。修复办法是把 `deploy/mysql-client.cnf`（`default-character-set=utf8mb4`）挂到 `/etc/mysql/conf.d/charset.cnf`，`docker-compose.yml` 里已经这么配了。
