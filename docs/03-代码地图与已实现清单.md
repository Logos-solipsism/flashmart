## 三、刻意保留的取舍（设计决策记录）

1. **不引入 Redisson / 分布式锁**。本项目的四类竞态分别用 Lua 原子脚本（库存）、`SETNX + TTL`（缓存重建互斥）、数据库唯一索引（一人一单）、条件更新（订单状态）解决，都不需要可重入与 WatchDog 续期。多引一个组件就是多一份要理解与运维的东西。
2. **不引入布隆过滤器**。空值缓存（`NULL_MARK`，TTL 30 秒）在本项目的数据规模下已经够用；代价是"每次换一个不存在的随机 id"的攻击仍会穿透，这是明确接受的边界。
3. **不做分布式事务与分库分表**。抢购链路接受最终一致，用"Redis 原子扣减 + 唯一索引 + 幂等表 + 消费者回滚"四件套兜底；数据量不支持分库分表，加了只有路由成本。索引已经按实际查询路径建好（`uk_user_activity`、`idx_user_status`、`idx_activity`、`idx_time`）。
4. **超时关单只回滚库存、不回滚已购记录**。名额是一次性机会，不付款就作废，否则用户可以"抢了不付 → 关单 → 再抢"零成本锁库存。同一用户在关单后再次抢购会被"每人限购 1 件"拦下，这是设计如此，不是 bug。
5. **逻辑过期缓存里不放剩余库存**。`ActivityCacheVO` 刻意不含库存字段，库存由 `currentStock` 实时读 Redis，避免"页面显示有货但抢不到"。代价是列表接口多 30 次 Redis 读，本项目量级下可接受。
6. **延迟双删的延迟被 RocketMQ 延迟档位"向上取整"到 1 秒**。配置写的是 `double-delete-delay-millis: 500`，代码里 `Math.max(1, (int)(500/1000))` 得到 1 秒。这是 RocketMQ 固定档位（最小 1s）带来的限制，属于已知代价，不是笔误。
7. **消息体只带业务主键与下单必要字段**（`OrderCreateEvent(orderNo, userId, activityId, productId, flashPrice)`）。消费端不回查商品表，所以商品改价不会影响已进入队列的订单语义，消息格式也不会随业务字段变化频繁升级。
8. **金额一律用「分」存整数**。`product.origin_price`、`flash_activity.flash_price`、`seckill_order.flash_price` 都是 `INT`；前端 `utils.js` 的 `fen2yuan` / `yuan2fen` 负责显示与提交时的换算。
9. **压测接口用独立 profile 隔离**。`BenchController` / `BenchService` 上的 `@Profile("bench")` 保证正常启动完全不暴露这些"能重置库存、能跳过一人一单"的接口。
10. **逻辑删除与唯一索引的冲突用物理删除接口绕开**。`SeckillOrderMapper.deleteByActivityPhysically` 是唯一的物理删除入口，只被压测重置调用。
11. **演示数据把三种活动状态都准备好**。`data.sql` 里 9001/9002 进行中、9003 两分钟后开始（演示"活动还没开始"）、9004 已结束（演示"活动已结束"），不用改系统时间就能演示全部时间窗口校验分支。

## 四、本地运行与验证

### 4.1 环境要求

JDK 17、Maven、Node 18+、Docker Desktop。端口占用情况：13307（MySQL）、6380（Redis）、9877（RocketMQ namesrv）、10912（broker）、18090（后端）、5274（前端）、8181（RocketMQ Dashboard）。这些都刻意避开了 3306 / 6379 / 9876 / 8080 等常用端口，方便与其他项目共存。

### 4.2 启动步骤

```bash
# 1. 起中间件（首次启动时容器会自动执行 01-schema.sql 与 02-data.sql）
cd flashmart
docker compose up -d

# 2. 起后端（默认端口 18090）
cd server
mvn spring-boot:run

# 3. 起前端（端口 5274，/api 代理到 18090）
cd ../web
npm install
npm run dev
```

打开 <http://localhost:5274>；接口文档在 <http://localhost:18090/doc.html>；RocketMQ Dashboard 在 <http://localhost:8181>。

需要注意的两点：

- **初始化脚本只在数据卷为空时执行**。改过 `schema.sql` / `data.sql` 之后要 `docker compose down -v` 删掉 `mysql-data` 卷再 `up`，否则改动不会生效；也可以手工 `docker exec -i flashmart-mysql mysql -uroot -proot123456 < server/src/main/resources/db/schema.sql`。
- **压测 profile 单独启动**：`mvn spring-boot:run -Dspring-boot.run.profiles=bench`，否则 `/api/bench/**` 全部 404。

### 4.4 手工验证清单（照着做一遍就能覆盖全部技术点）

| # | 操作 | 期望现象 | 覆盖的技术点 |
| --- | --- | --- | --- |
| 1 | 用 13811110001 登录 → 商家后台创建商品 → 创建活动（库存 100、限购 1、时间窗覆盖当前） | 活动出现在"我发布的活动"；Redis 里 `GET seckill:stock:{id}` 等于 100 | 活动预热 |
| 2 | 用 13911110001 登录 → 抢购专区 → 进活动详情，连点抢购按钮 10 次 | 前 5 次通过限流，第 6 次起 HTTP 429「手速太快啦，歇一秒再抢」 | 滑动窗口限流 |
| 3 | 隔 1 秒后再抢 1 次 | 返回「每人限购 1 件，你已经抢到啦」 | 一人一单（Lua 分支 -2） |
| 4 | 抢购成功后看页面提示 | 先显示"排队中"，几百毫秒后变成"订单已生成，请尽快支付"+ 支付倒计时 | 异步落单（实测约 157ms） |

## 五、核对代码时发现的"实际行为与注释/配置不一致"清单

以下是逐行读代码时记录下来的落差，**均未修改代码**，按"文档写的是什么、实际是什么"列出，供后续修复或补文档时参考。

| # | 位置 | 注释 / 配置 / 常识怎么说 | 代码实际怎么做 |
| --- | --- | --- | --- |
| 1 | `FlashActivity.version` + `schema.sql` 注释"乐观锁版本号（商家改活动时防止并发覆盖）" + `ActivityService.update` | 暗示活动表有乐观锁 | 全仓库没有 `OptimisticLockerInnerInterceptor`，`updateById` 不带版本条件，`version` 只在创建时置 0，之后从不变化。**该乐观锁未生效**（订单表的乐观锁是手写 SQL，是生效的） |
| 2 | `AuthController.login` 上的 `@SlidingWindowLimit(dimension = IP)` | 注释写"登录按 IP 维度限流：防止撞库" | `WebConfig` 把 `/api/auth/**` 从拦截器里排除，登录时 `UserContext` 必然为 `null`，`SlidingWindowAspect` 的 IP 分支取不到 `clientIp` 而落到 `"unknown-ip"`。**实际效果是"全部未登录登录请求共用一个 20 次/秒的桶"（等价于 GLOBAL 维度），不是按 IP 限流** |
| 3 | `MqProducer` 顶部注释"只有发送失败才降级记录日志" + `application.yml` 的 `rocketmq.producer.retry-times-when-send-failed: 3` | 听起来发送失败有重试兜底 | 这个配置项作用于**同步发送**；本项目抢购链路走的是 `asyncSend` + `SendCallback`，`onException` 里只有 `log.error`，外层 `catch` 也只有 `log.error`。**异步发送失败没有任何重试与补偿** |
| 4 | `application.yml` 的 `flashmart.mock.pay-fail-rate: 0.0` | 注释写"压测时把失败注入打开，用来验证补偿重试" | 全仓库没有任何代码读取该配置，`@Value` 都没有。**它是一个未接线的空开关** |
| 5 | `CacheSyncTask.retryCount`（表注释与字段名都是"重试次数"） | 应随补偿重试累加 | `CacheEvictService.evict` 插入时固定写 0，`CacheEvictConsumer.markTask` 只更新 `status`/`error_msg`。**该字段恒为 0** |
| 6 | `README`/`web/README.md` 未提及，但 `web/src/api.js` 注释写"429（限流）同样抛出后端提示语" | — | 行为与注释一致；但要注意 `GlobalExceptionHandler.handleBiz` 对**非 429** 的业务异常返回 HTTP 200，前端靠 `payload.code !== 0` 判断，两处逻辑耦合，改一处必须改另一处 |
| 7 | `ActivityService.update` 调用 `prepareStock` → `SeckillStockService.prepare` | 注释"重新预热库存" | `prepare` 用 `SETNX seckill:stock:init:{id}`（TTL 10 秒）做互斥，**10 秒内第二次调用不会写入**。所以商家在 10 秒内连续改两次库存，第二次的新库存不会同步到 Redis |
| 8 | `flashmart.cache.double-delete-delay-millis: 500` | 看着是 500 毫秒 | `Math.max(1, (int)(500 / 1000))` = 1 秒，再经 `nearestDelayLevel(1)` = level 1 = 1 秒。**实际延迟是 1 秒，配置里的毫秒精度无效** |
| 9 | `SeckillOrder.STATUS_CANCELLED`、`cancel_reason='CANCELLED'`、`FlashActivity.inProgress()`、`ActivityService.requireActivity()`、`SeckillStockService.clearUserRecord()`、`MqTopics.DLQ_ORDER_CREATE` | 看起来都在用 | 这六个成员**没有任何调用方**（`grep` 全仓库只有定义处），是预留或历史遗留 |
| 10 | `OrderController.detail` 与 `SeckillService.result` | 两个接口都能查订单 | `SeckillService.result` 有 `!userId.equals(order.getUserId()) → 403` 归属校验；`OrderController.detail` **没有**。而且 `toVO(null)` 会 NPE，订单号不存在时返回 500 而不是 404 |
| 11 | `/api/merchant/**` 六个接口 | 看名字是商家功能 | 后端只校验"已登录"，不校验 `role == MERCHANT`；买家 token 也能创建商品与活动。前端 `router.js` 拦住了页面，但拦不住直接调接口 |
| 12 | `OrderCreateConsumer` 的失败分支 | 注释"回滚 Redis 预扣的库存与机会，再抛出去让 MQ 重试" | 逻辑正确，但**重试会再次执行 `rollbackAll`**（幂等表把 FAILED 消息重新置为 CONSUMING 并放行），而 `rollbackAll` 用的是无上限的 `INCR` / `HINCRBY -1`。反复重试可能把 Redis 库存加超总库存。对照：`FlashActivityMapper.increaseStock` 带了 `WHERE available_stock < total_stock` 上限保护，Redis 侧没有 |
| 13 | `MqIdempotentRepository.markFailed` 与 `tryAcquire` | 注释"之前处理失败过的消息允许重试" | `markFailed` 把状态置 FAILED 后重新抛出异常，RocketMQ 阶梯重试；重试时 `tryAcquire` 命中 `DuplicateKeyException` 分支、查到 FAILED 就置回 CONSUMING 并放行。**这是有意设计（否则失败消息永远无法重试）**，但要知道"幂等表在失败场景下是放行的" |
| 14 | `AuthInterceptor` 类注释"改密码、封号后旧令牌立刻作废" | 支持服务端主动失效 | 拦截器只做 `redis.hasKey(sessionKey)`，**不比对会话里存的 token 值**。所以"删 key"能让旧令牌立刻失效（封号可以做到），但**同一用户重新登录并不会让旧 token 失效**（第二次登录只是覆盖了 value，旧 token 仍能通过 `hasKey`） |
| 15 | `bench/Bench.java` 顶部 Javadoc 描述工具用途时用了"把某某材料里那些数字真实跑出来"这类表述 | — | 工具本身的实现与业务无关，但这句注释把压测工具的性质描述成了"为对外材料取证"，与"工程验收工具"的定位不一致，建议后续改成"把验收指标在本机真实跑出来"之类的中性表述 |
| 16 | `CacheEvictConsumer.markTask` | 逻辑是"删缓存成功后把补偿任务置为 SUCCESS" | `markTask` 的 `UPDATE` 带 `WHERE status = 'PENDING'`。一旦某次尝试失败把任务置成了 `FAILED`，后续（Redis 恢复后）重试删除**即使成功也改不回 SUCCESS**，任务行会永久停在 FAILED。也就是说"删缓存失败了"与"补偿最终成功了"这两件事在表里区分不出来 |
| 17 | `BenchController` / `BenchService` 的 `@Profile("bench")` | 注释说"正常启动不会暴露" | 行为与注释一致；但要注意 `/api/bench/**` 仍然落在 `WebConfig` 的 `/api/**` 拦截范围内，**调用时同样需要 `Authorization: Bearer <token>`**，工具与手工 curl 都要先登录 |
