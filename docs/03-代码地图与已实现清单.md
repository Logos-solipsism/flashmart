## 三、刻意保留的取舍（设计决策记录）

1. **不引入 Redisson / 分布式锁**。本项目的四类竞态分别用 Lua 原子脚本（库存）、`SETNX + TTL`（缓存重建互斥）、数据库唯一索引（一人一单）、条件更新（订单状态）解决，都不需要可重入与 WatchDog 续期。多引一个组件就是多一份要理解与运维的东西。
2. **不引入布隆过滤器**。空值缓存（`NULL_MARK`，TTL 30 秒）在本项目的数据规模下已经够用；代价是"每次换一个不存在的随机 id"的攻击仍会穿透，这是明确接受的边界。
3. **不做分布式事务与分库分表**。抢购链路接受最终一致，用"Redis 原子扣减 + 唯一索引 + 幂等表 + 消费者回滚"四件套兜底；数据量不支持分库分表，加了只有路由成本。索引已经按实际查询路径建好（`uk_user_activity`、`idx_user_status`、`idx_activity`、`idx_time`）。
4. **超时关单只回滚库存、不回滚已购记录**。名额是一次性机会，不付款就作废，否则用户可以"抢了不付 → 关单 → 再抢"零成本锁库存。同一用户在关单后再次抢购会被"每人限购 1 件"拦下，这是设计如此，不是 bug。
5. **逻辑过期缓存里不放剩余库存**。`ActivityCacheVO` 刻意不含库存字段，库存由 `currentStock` 实时读 Redis，避免"页面显示有货但抢不到"。代价是列表接口多 30 次 Redis 读，本项目量级下可接受。
6. **延迟双删的延迟直接按秒配，落在 RocketMQ 的固定档位上**。配置是 `flashmart.cache.double-delete-delay-seconds: 5`，`nearestDelayLevel(5)` 命中第 2 档，**实际生效 5 秒**。RocketMQ 不支持任意秒数（档位是 1s/5s/10s/30s…），延迟时间只能取档位值，这是已知代价；早先写成毫秒配置再折算成秒，配出来的值和实际生效值对不上，已经改掉。
7. **消息体只带业务主键与下单必要字段**（`OrderCreateEvent(orderNo, userId, activityId, productId, flashPrice)`）。消费端不回查商品表，所以商品改价不会影响已进入队列的订单语义，消息格式也不会随业务字段变化频繁升级。
8. **金额一律用「分」存整数**。`product.origin_price`、`flash_activity.flash_price`、`seckill_order.flash_price` 都是 `INT`；前端 `utils.js` 的 `fen2yuan` / `yuan2fen` 负责显示与提交时的换算。
9. **压测接口用独立 profile 隔离**。`BenchController` / `BenchService` 上的 `@Profile("bench")` 保证正常启动完全不暴露这些"能重置库存、能跳过一人一单"的接口。
10. **逻辑删除与唯一索引的冲突用物理删除接口绕开**。`SeckillOrderMapper.deleteByActivityPhysically` 是唯一的物理删除入口，只被压测重置调用。
11. **演示数据把三种活动状态都准备好**。`data.sql` 里 9001/9002 进行中、9003 两分钟后开始（演示"活动还没开始"）、9004 已结束（演示"活动已结束"），不用改系统时间就能演示全部时间窗口校验分支。种子数据的中文靠 `deploy/mysql-client.cnf`（utf8mb4）保证不被二次编码。
12. **Redis 库存回滚也带上限**。`lua/rollback_stock.lua` 只在当前库存小于 `seckill:total:{id}` 时才 +1：在途的关单消息可能比一次压测重置来得更晚，无脑 `INCR` 会把库存加超总量（实测出现过从 9999 涨到 11679）。数据库侧本来就有 `available_stock < total_stock` 的条件，两边口径现在一致。
13. **下单失败的回滚做了"每条消息只回滚一次"**。`OrderCreateConsumer.rollbackOnce` 用 `seckill:rollback:{msgId}` 的 SETNX 兜底，否则 MQ 的阶梯重试会把同一份库存反复加回去（凭空多出库存比超卖更难查）。

#### 实测结果（本机 Windows + Docker 中间件、压测客户端与服务同机、闭环压测模型，测前清空数据表并等 MQ 排空）

| 实验 | 结果 |
| --- | --- |
| 抢购接口返回耗时（异步版） | 28 ms |
| 异步下单落库 | 接口返回后约 157 ms（状态 PENDING_PAY） |
| 削峰对比（50 并发 / 2000 请求，同机） | 异步 176 req/s、平均 280.66 ms、P50 282 ms、P90 307 ms、P95 315 ms、P99 329 ms；同步（对照组）39 req/s、平均 1259.62 ms、P50 1261 ms、P90 1359 ms、P95 1394 ms、P99 1462 ms → 吞吐约 4.5 倍，单请求平均耗时降约 78%，P99 降约 77% |
| 超卖验证（活动 30 件库存 / 60 个不同用户并发） | 成功 30 次、落库 30 单、数据库剩余库存 0、Redis 剩余库存 0（成功数 = 落库数 = 总库存），无超卖、库存非负 |
| 一人一单（同一用户并发 20 次） | 成功 1 次 + 限购 4 次 + 429 共 15 次（限流在限购之前）；改成每 1.2 秒 1 次匀速请求 → 限流 0 次、全部被"一人一单"拦下 |
| 滑动窗口限流 | 同一用户 1 秒内 10 并发 → 5 通过 + 5 × 429（阈值 5 次/秒）；匀速 1.2 秒 1 次 → 全部通过 |
| 缓存击穿（详情缓存被删后 100 并发） | 回源数据库 1 次，100 个请求总耗时 114 ms（修复前是 100 次） |
| 缓存击穿（逻辑过期瞬间 100 并发） | 全部成功，只触发 1 次异步重建，耗时 119 ms |
| 缓存穿透（查不存在的活动 200 次） | 回源 1 次 |
| 超时关单 | **30 秒档（生产配置）**：第 30 秒订单变为 `TIMEOUT`，数据库与 Redis 库存各 +1；关单后同一用户再抢被"每人限购 1 件，你已经抢到啦"拦下（库存退回池子、名额不退）。**1 秒档（压测接口）**：关单消息到点后下一次轮询 22 ms 内看到 `TIMEOUT` |
| 支付幂等 | 两次支付都返回 `PAID`，第二次 message = "订单已支付，无需重复支付" |
| 登录 IP 维度限流 | 并发 30 次登录 → 通过 20 + 限流 10（阈值 20 次/秒） |
| 应用层 IP 黑名单（被封的 IP 不再跑限流 Lua） | 阈值调小到 5 次 / 60 秒、封禁 60 秒：伪造 `X-Forwarded-For` 的 IP 在 1 秒内 10 并发 → **200 × 5（1 成功 + 4 限购）+ 429 × 5**，突发耗时 **0.102 s**，违规累计到阈值后该 IP `banned=true`；封禁后同 IP 再打 10 次 → **10/10 全是黑名单 429**，而 `limiterCalls` 增量为 0、`blacklistRejected` 增量为 10（命中黑名单时一次限流 Lua 都没跑）；换对照 IP 打 3 次 → 黑名单拒绝 0 次、`banned=false`（按 IP 隔离） |

没有实测的项目一律写"未实测"：Redis 单分片 QPS 上限、极限并发、故障恢复时间、延迟双删的一致性量化、支付与关单毫秒级对撞，都还没有做过实验，不做推算。

## 五、核对代码时发现的"实际行为与注释/配置不一致"清单

以下是逐行读代码时记录下来的落差。**本轮按这份清单逐条复核过：已经修掉的在末列标注"→ 已修复"并写明修法，仍未修的保留并标注"→ 仍未修"。**

| # | 位置 | 注释 / 配置 / 常识怎么说 | 代码实际怎么做 |

| 1 | `FlashActivity.version` + `schema.sql` 注释"乐观锁版本号（商家改活动时防止并发覆盖）" + `ActivityService.update` | 暗示活动表有乐观锁 | 全仓库没有 `OptimisticLockerInnerInterceptor`，`updateById` 不带版本条件，`version` 只在创建时置 0，之后从不变化。**（原行为）该乐观锁未生效**（订单表的乐观锁是手写 SQL，是生效的） **→ 已修复**：新增 `config/MybatisPlusConfig` 注册 `OptimisticLockerInnerInterceptor`，`@Version` 生效，`updateById` 会自动带版本条件 |
