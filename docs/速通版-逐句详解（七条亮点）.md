# 亮点① Redis + Lua 原子扣减库存与一人一单

## 卡片原文（对照用）

> ① **是什么/怎么用**：把「判断限购 + 判断库存 + 扣库存」写进**一段 Lua 脚本**，在 Redis 里**一次原子执行**
> ② **为什么这么选**：拆成三条命令的话，并发下会出现两个请求都读到库存 1 → **双双扣减（超卖）**；同一用户两个请求都读到"没买过" → **落下两单**。分布式锁能解决，但多了加锁/释放/续期的开销，而这条链路只有"读-判断-写"三步，Lua 更直接
> ③ **具体流程**：抢购请求 → 限流 → 读活动（缓存）→ 预热库存 → Lua（库存没了返回 -1、超限购返回 -2）→ 成功则生成订单号 + 投 MQ → 立刻返回
> ④ **兜底**：数据库侧 `unique(user_id, activity_id)` 唯一索引 + 扣减 SQL 带 `available_stock > 0`；Redis 判断失效也落不下第二单、也扣不成负数
> ⑤ **实测产出**：30 件库存 / 60 个用户并发 → **成功 30、落库 30、数据库与 Redis 剩余库存都是 0**（成功数 = 落库数 = 总库存，无超卖）
> ⑥ **方法论**：高并发扣减 = **把"判断+扣减"压成一次原子操作 + 数据库唯一约束兜底 + 数量永远不为负**

## 维度① 是什么 · 怎么用

| 卡片里的词 | 大白话 |
| --- | --- |
| **Lua 脚本** | Redis 内置支持的一门小脚本语言。它不是"另一个服务"，而是**把几条 Redis 命令打包成一次调用**的东西 |
| **原子执行** | 这段脚本从第一条命令到最后一条**中间不会被别的请求插进来**（Redis 处理命令是单线程的，脚本整体当成一条命令跑）——这就是"原子"的全部含义，不是"事务"、不是"回滚" |
| **KEYS / ARGV** | 脚本的两个入参通道：`KEYS` 传"我要操作哪些 key"，`ARGV` 传"普通参数"。分开写是为了让 Redis Cluster 能按 key 算分片（本项目是单节点，但写法保持一致） |
| **DECR** | 把 key 的字符串值当整数**减 1**，是 Redis 的原子命令 |
| **HGET / HINCRBY** | Hash 结构的读 / "加 N"。`HINCRBY` 是原子的，加 1 就是"这个人的已购数量 +1" |
| **Hash** | Redis 里的一种结构，一个 key 下面挂很多"字段 → 值"。这里 **字段 = userId，值 = 这个人已经买了几件**（为什么不用 Set 见下面） |
| **一人一单** | 同一个用户在一个活动里只能成功一次（`flash_activity.limit_per_user` 默认 1） |
| **预热** | 活动创建时 / 第一次抢购时，**把数据库的剩余库存抄一份到 Redis**，之后扣减发生在 Redis 里、不再走数据库 |
| **-1 / -2 / -3** | 脚本"没扣成功"的三种原因，见下面那张表。**Java 侧把它们映射成常量**，业务代码只认常量不认魔法数字 |
| **唯一索引** | 数据库层面的"这张表里不允许出现重复行"。`uk_user_activity(user_id, activity_id)` = 一个用户在一个活动下最多一条订单 |
| **分布式锁** | 用一个共享的"锁"让多个进程排队进临界区。能解决同样的问题，但**多了加锁、解锁、续期三件事要处理**——这是本项目没选它的原因 |

**这段 Lua 到底做了什么**（`server/src/main/resources/lua/seckill_stock.lua`，逐句拆）：

| 脚本里的第几步 | 代码 | 含义 | 返回 |
| --- | --- | --- | --- |
| ① 读库存 | `GET seckill:stock:{activityId}` | key 不存在 → 说明这个活动**还没预热** | `-3` |
| ② 判断库存 | `if stock <= 0` | 库存没了，抢光了 | `-1` |
| ③ 读已购数量 | `HGET seckill:bought:{activityId} {userId}`（取不到按 0 算） | 我看看这个人已经买了几件 | —— |
| ④ 判断限购 | `if bought + 1 > limitPerUser` | 再买一件就超了每人限购 | `-2` |
| ⑤ 扣减 | `DECR` 库存 + `HINCRBY` 已购 +1 | 库存 -1、这个人的已购 +1，**一口气做完** | —— |
| ⑥ 返回 | `return stock - 1` | 扣减之后的剩余库存（**≥0 就是成功**） | 剩余库存 |

**Java 侧怎么接这四个返回值**（`SeckillStockService` 里就是三个常量）：

| 脚本返回 | Java 常量 | 抢购接口抛给用户的话 |
| --- | --- | --- |
| **≥ 0** | ——（成功） | 继续走：生成订单号 + 投 MQ |
| **-1** | `SOLD_OUT` | 「手慢了，已被抢光」 |
| **-2** | `OVER_LIMIT` | 「每人限购 N 件，你已经抢到啦」 |
| **-3** | `NOT_PREPARED` | 「活动库存尚未就绪，请稍后重试」 |

**四个 Redis key，各管一件事**：

| Redis key | 类型 | 谁写 | 干什么 |
| --- | --- | --- | --- |
| `seckill:stock:{activityId}` | String | 预热 / Lua 的 `DECR` / `rollback_stock.lua` | **库存真身**，TTL 7 天 |
| `seckill:bought:{activityId}` | Hash | Lua 的 `HINCRBY` | `userId → 已购数量`，**一人一单靠它** |
| `seckill:total:{activityId}` | String | 预热 / 压测的 `reset` | 活动总库存，**回滚时的上限**（防止把库存加超） |
| `seckill:stock:init:{activityId}` | String | `ensurePrepared` | **预热互斥标记**，TTL 10 秒 |

**为什么已购记录用 Hash 而不是 Set / String**：

| 方案 | 能表达什么 | 为什么不用 / 用 |
| --- | --- | --- |
| `Set`（买过就把 userId 塞进去） | 只有"买过 / 没买过"两种状态 | 表达不了数量，也做不了"把机会还回去"（下单失败要还给用户一次机会） |
| `String`（每人一个 key，`seckill:bought:{activityId}:{userId}`） | 能记数量 | 一个活动几万个用户就是几万个 key，key 空间和过期管理都更难 |
| **`Hash`** ✅ | 一个 key 下 `userId → 已购数量` | 限购判断是"数量比较"（bought + 1 是否超过限购件数），所以存数量最自然；`HINCRBY` 能原子 +1 / -1（下单失败时把机会还回去）。当前活动限购固定 1 件 |

**"预热"这件事的两个关键细节**（写在 `SeckillStockService.ensurePrepared` 的注释里）：

1. **读的是数据库的 `available_stock`（剩余库存），不是 `total_stock`（总库存）**。库存 key 一旦丢失（被误删、过期），按总库存重建会把**已经卖出去的部分"补回来"**，凭空多出库存——这比超卖还难查。
2. **"库存 key 已经存在就直接返回"是快路径**。抢购接口每个请求都会调一次预热，如果每次都去对"初始化锁"做 `SETNX`，不仅每个请求多一次写操作，还会在锁 TTL 过期后出现"用数据库库存覆盖 Redis 计数器"的窗口。

## 维度② 为什么这么选

**同样是"判断 + 扣减"，五种做法对比**：

| 方案 | 长什么样 | 结果 |
| --- | --- | --- |
| **拆成三条命令**（`GET` → Java 里 `if` → `DECR`） | 代码最好读 | ❌ 两个请求都读到库存 1 → **双双扣减（超卖）**；同一用户两个请求都读到"没买过" → **落两单**。判断与写之间有缝隙，并发一定钻进去 |
| **分布式锁**（Redisson `RLock` 包住三步） | 加锁 → 查 → 扣 → 解锁 | ⭕ 能解决，但每次抢购**多两次往返**（加锁、解锁），还要处理锁续期、锁失效、误删别人的锁；而这条链路只有"读-判断-写"三步，加锁属于**用重武器打小目标** |
| **数据库 `UPDATE ... WHERE stock > 0`** | 一条 SQL 就原子 | ⭕ 原子性没问题，但**每次扣减都写库**，热点行锁排队——这正是本项目要避开的（数据库只做兜底，不做热点扣减） |
| **数据库悲观锁**（`SELECT ... FOR UPDATE`） | 行锁串行 | ❌ 连接池只有 20 个连接，热点行会把连接全部占住，等待时间随并发非线性变长 |
| **Redis + Lua** ✅ | 一次 `EVALSHA` | ✅ 一次网络往返完成"判断 + 扣减"，无锁等待；数据库不参与热点扣减 |

**代价与收益（面试时主动说代价，比只讲收益可信）**：

| 收益 | 代价 |
| --- | --- |
| 判断与扣减之间的缝隙被彻底消掉，不需要锁、也就没有"锁失效"这类问题 | **Lua 脚本不好调试**：不能打断点，只能靠返回值和日志；所以脚本里只放简单判断，复杂逻辑（订单号、发消息）都留在 Java |
| 比加锁方案少两次 Redis 往返，扛的是同一份并发 | **Redis 成了这条链路的强依赖**：Redis 挂了抢购直接失败（限流那一层做了"降级放行"，**扣减这一层没有降级**——放行就等于不扣库存了，这是明确的边界） |
| 数据库不用承担热点扣减，只承担"异步落库 + 兜底" | **库存变成了两份数据**（Redis 一份、数据库一份），所以必须配齐"预热 + 回滚 + 回滚上限"三件事，见维度④ |
| 脚本缓存后按 SHA1 执行（`EVALSHA`），不用每次传脚本体 | 脚本与 Java 的返回值约定要**两边同时改**（改脚本必须同步改常量注释），属于隐式契约 |

## 维度③ 流程（能画出来）

```
POST /api/seckill/{activityId}                     ← 用户点"立即抢购"
  │
  ├─[0] AOP 滑动窗口限流：rate:seckill:USER:{userId}，1 秒 5 次
  │       超了 → 429「手速太快啦，歇一秒再抢」（方法体一行都不执行）
  │
  ├─[1] 读活动详情：activity:detail:{activityId}（逻辑过期缓存）
  │       命中空值标记 __NULL__ → 「活动不存在」
  │       校验 status == 上线 && now ∈ [startTime, endTime]
  │       未开始 / 已结束 / 已下线 → 直接拒绝
  │
  ├─[2] 预热库存 ensurePrepared（幂等）
  │       seckill:stock:{id} 已存在？ → 直接返回（快路径）
  │       否则 SETNX seckill:stock:init:{id}（TTL 10 秒），抢到锁的那个请求：
  │           SET seckill:stock:{id} = 数据库 available_stock   ← 注意不是 total_stock
  │           SET seckill:total:{id} = 活动 total_stock         ← 回滚上限
  │
  ├─[3] EVALSHA lua/seckill_stock.lua
  │       KEYS = [seckill:stock:{id}, seckill:bought:{id}]
  │       ARGV = [userId, limitPerUser]
  │         -3 → 「活动库存尚未就绪，请稍后重试」
  │         -1 → 「手慢了，已被抢光」
  │         -2 → 「每人限购 1 件，你已经抢到啦」
  │         ≥0 → 扣减成功，值 = 剩余库存
  │
  ├─[4] 生成订单号：OrderNoGenerator.next(userId)
  ├─[5] 异步投递：topic_order_create，key = order:{orderNo}（消息里带 traceId）
  └─[6] 返回 { orderNo, state: "QUEUING" }
          ↑ 走到这里为止，一次数据库操作都没做
```

**分步说明（每一步为什么必须在主链路 / 失败会怎样）**：

| 步骤 | 为什么在这一层 | 失败了会怎样 |
| --- | --- | --- |
| [0] 限流 | 抢购是最容易被脚本刷的入口，**刷进来一次就消耗一份库存**，所以挡在最前面 | 429，方法体不执行 |
| [1] 读活动（缓存） | 活动是否存在、是否在时间窗口内，是**纯读**操作，走缓存不碰数据库 | 业务异常（活动不存在 / 已下线 / 没开始 / 已结束） |
| [2] 预热 | 让第 [3] 步有东西可扣；预热是**幂等**的，可以每个请求都调 | 一般不会失败；Redis 不可用时会直接抛异常 |
| [3] Lua 扣减 | **整条链路唯一的"资格判定"**，必须在返回给用户之前完成 | 三种失败返回值，对应三句人话 |
| [4] 订单号 | 用户需要一个"凭证"去轮询结果 | 见亮点② 的边界（进程内自增） |
| [5] 投 MQ | 真正写库的活在消费者那边，这里只负责"把任务交出去" | 异步发送失败会同步重发一次（见亮点②） |
| [6] 返回 | 用户**只等一次 Redis 脚本的时间**（实测 28ms，见亮点② 维度⑤） | —— |

## 维度④ 兜底（十二个"如果"）

| 如果…… | 会怎样 | 靠什么兜住 |
| --- | --- | --- |
| **① 同一个用户两个请求同时到达** | 两个请求都想"判断有没有买过" | 判断在 Lua 里，Redis 串行执行：第二个请求读到的是已经 +1 之后的值 → 返回 `-2` |
| **② 库存只剩 1 件、两个用户同时抢** | 谁都不想超卖 | `stock <= 0` 的判断和 `DECR` 在同一段脚本里，第二个进来时读到的是 0 → 返回 `-1` |
| **③ Redis 库存 key 被误删 / 过期了** | 下一个请求会重新预热 | `ensurePrepared` 读数据库的 **`available_stock`**（不是 `total_stock`），已卖出的部分不会被补回来 |
| **④ 预热时并发进来好几个请求** | 只有一个该真正写库存 | `SETNX seckill:stock:init:{id}`（TTL 10 秒）+ **快路径**（key 已存在直接返回）双层 |
| **⑤ Redis 整个挂了** | **抢购接口直接失败**（全局异常处理返回"系统繁忙，请稍后重试"） | **没有降级**——这是明确边界：限流那层可以"降级放行"，扣减这层不能放行（放行 = 不扣库存 = 超卖） |
| **⑥ Redis 的判断被绕过 / 失效了** | 数据库也不会落下第二单 | `seckill_order` 的 `UNIQUE KEY uk_user_activity(user_id, activity_id)`；插入抛 `DuplicateKeyException` → `createOrder` 返回 null → 消费者按"重复单"处理 |
| **⑦ 数据库库存被扣成负数** | 不可能 | `decreaseStock` 的 SQL 带 `WHERE available_stock > 0`，返回 0 行就抛异常 |
| **⑧ 订单最终没落库（数据库扣不动 / 唯一索引拦下）** | Redis 预扣的**库存和名额一起还回去** | 消费者 `rollbackOnce` → `rollbackAll`（`rollback_stock.lua` 把库存 +1、`HINCRBY -1` 把已购数量 -1）——用户什么都没拿到，所以机会也还给他 |
| **⑨ 订单超时被关单** | **只还库存、不还名额** | `OrderService.timeoutOrder` 只调 `increaseStock`（DB）+ `rollbackStock`（Redis）：名额已经用掉，不付款就作废，**库存退回池子给其他人抢** |
| **⑩ 同一条消息被 MQ 重试了好几次** | 不会把库存反复加回去 | `SETNX seckill:rollback:{msgId}`（TTL 2 小时）把"**每条消息只回滚一次**"钉死；否则阶梯重试会把库存越加越多（凭空多出库存，比超卖更难查） |
| **⑪ 在途的关单消息比一次压测重置来得还晚** | 库存不会被加超总量 | `rollback_stock.lua` 的上限：当前库存 ≥ `seckill:total:{id}` 时**不再 +1**（数据库侧的 `increaseStock` 同样带 `available_stock < total_stock` 条件，两边口径一致） |
| **⑫ `HINCRBY -1` 被并发执行** | 已购数量不会被减成负数 | `rollbackAll` 先读一次，**值 > 0 才减** |

**主动说的边界（这句话说出来比被问出来好）**：

> "限购"在 Redis 侧的能力是**每人限购 N 件**（Hash 存的是数量），但**当前版本在创建活动时把限购数固定成 1 件**：商家传大于 1 会被接口直接拒绝。
>
> 为什么不在入口放开：数据库侧 `uk_user_activity(user_id, activity_id)` 只允许**一个用户在一个活动下有一条订单**，如果放开 `limit_per_user > 1`，第二单会被唯一索引拦下，消费者把它当成"重复单"把库存和名额回滚掉，而接口早就返回了 `QUEUING`——**用户会一直轮询不到订单，也拿不到任何失败信号**（静默失败比直接报错难查得多）。真要支持多件，得先把唯一索引改成能容纳 N 条的形状（或者不建它、只靠 Redis 限购），这是我有意留到下一版的改动。

## 维度⑤ 实测产出

| 实验 | 做法 | 结果 |
| --- | --- | --- |
| **不超卖（核心）** | 活动 **30 件库存**、**60 个不同用户并发**抢购，压测工具轮询等 MQ 排空后读统计 | **成功 30 次、落库 30 单、数据库剩余库存 0、Redis 剩余库存 0**（成功数 = 落库数 = 总库存） |
| **一人一单（突发）** | 同一用户 **1 秒内并发 20 次**抢购 | **成功 1 次 + 限购 4 次 + 429 共 15 次**。为什么不是 19 次限购：限流（每人 1 秒 5 次）在限购校验**之前**，第 6 次起就被 429 挡了 |
| **一人一单（匀速）** | 同一用户改成**每 1.2 秒 1 次**（绕开 1 秒窗口） | **限流 0 次，全部被「每人限购 1 件，你已经抢到啦」拦下**——这才是"一人一单"本身的效果 |

**这三个数怎么读**：
- 第一行看的是**四个数一起对**：成功数、落库订单数、数据库剩余库存、Redis 剩余库存。**四个数互相印证**，比只看"没报错"可靠得多。
- 第二、三行是**同一个功能的两种请求节奏**：突发被限流挡住、匀速暴露的才是限购本身。**做实验时要主动把限流这个干扰变量绕开**，否则你证明的是限流，不是限购。

**必须主动说的环境边界**：本机 Windows + Docker 中间件，压测客户端与服务**同机**，绝对值不代表线上；超卖实验走的是 bench profile 的合成用户接口（**跳过一人一单**，否则一个账号只能成功一次、压不出并发）。

## 维度⑥ 方法论

**高并发扣减，按顺序问自己五个问题**：

| # | 要回答的问题 | 本项目怎么落 |
| --- | --- | --- |
| ① | **"判断"和"扣减"之间有没有缝隙？** | 有缝隙就会被并发钻。把三步压成**一次原子操作**（一段 Lua），而不是用锁去堵缝隙 |
| ② | **数量会不会变成负数？** | 每一层都要有下限：Lua 里的 `stock <= 0`、SQL 里的 `WHERE available_stock > 0` |
| ③ | **原子层失效了怎么办？** | 数据库的**唯一约束**是最后一道防线：`uk_user_activity`。锁会失效（主从切换、超时），唯一索引不会 |
| ④ | **失败要还什么？** | 每种失败的回滚语义都不一样：**下单失败** = 库存 + 名额一起还（用户什么都没拿到）；**超时关单** = 只还库存（名额已用掉）。**判错一种，用户就会凭空多出一次抢购机会** |
| ⑤ | **回滚本身幂等吗、有上限吗？** | 回滚很可能被重试：用 `SETNX` 标记"每条消息只回滚一次"，并给回滚加**上限**（不能超过总量） |

**一句话**：**能用一次原子操作解决的，不要用锁；能用数据库约束兜底的，不要指望应用层判断。**

## 40 秒口述版

> "抢购的扣减我做成了**一段 Lua 脚本**，在 Redis 里一次原子执行：先读库存，key 不存在返回 -3（说明没预热）；库存 ≤ 0 返回 -1（抢光）；再读 Hash 里这个人的已购数量，+1 超过限购返回 -2；全过了才 `DECR` 库存、`HINCRBY` 已购数量 +1，返回剩余库存。
> 为什么不用分布式锁：这条链路只有'读-判断-写'三步，拆成三条命令并发下会**两个请求都读到库存 1、双双扣减**，或者**同一用户落下两单**；用锁能解决，但每次抢购多两次往返、还要处理续期和锁失效，Lua 更直接。
> 已购记录我用 **Hash** 而不是 Set，因为限购判断本质是数量比较，Hash 存的就是数量，下单失败时也能把机会减回去（当前活动限购固定 1 件）。
> 数据库兜底有两层：`unique(user_id, activity_id)` 唯一索引，和带 `available_stock > 0` 的扣减 SQL。
> 还有一个语义我特意做了区分：**超时关单只回滚库存、不退该用户的抢购机会**（名额用掉就作废、库存退回池子）；**下单失败才把库存和机会一起还回去**。
> 实测 30 件库存、60 个不同用户并发：成功 30、落库 30、两边剩余库存都是 0。"

# 亮点② RocketMQ 异步下单削峰

## 卡片原文（对照用）

> ① **是什么/怎么用**：抢购接口**不写数据库**：只校验、扣 Redis、发一条消息就返回；订单落库、扣数据库库存、发延迟关单消息全在消费者做
> ② **为什么这么选**：开抢瞬间是**尖峰**：几千个请求同时写库会打满连接池、响应雪崩。异步把尖峰**摊平成队列**，数据库只面对消费速度
> ③ **具体流程**：抢购接口 → 发消息（带 traceId）→ 返回 orderNo → 前端轮询结果 → 消费者：幂等表 → 扣库库存 → 写订单 → 投延迟关单消息
> ④ **兜底**：消费幂等表 `mq_consume_log`（msg_id 唯一索引）；异步发送失败**同步重发一次**兜底；失败抛异常交给 MQ 阶梯重试
> ⑤ **实测产出**：接口 **28ms** 返回、订单 **157ms** 后落库；50 并发 2000 请求：**异步 176 req/s（P99 329ms）vs 同步 39 req/s（P99 1462ms）→ 吞吐 4.5 倍、P99 降 77%**
> ⑥ **方法论**：该不该异步：**用户是否必须马上拿到结果？动作是否不可逆？失败能否用重试/补偿兜住？** 三条都满足才异步

## 维度① 是什么 · 怎么用

| 卡片里的词 | 大白话 |
| --- | --- |
| **削峰** | 把"某一瞬间涌进来的几千个请求"**摊平**成"数据库按自己速度慢慢处理的队列"。峰还在，只是不再直接砸在数据库上 |
| **尖峰 / 平稳** | **尖峰** = 开抢那一秒流量是平时的几十倍（抢购就是典型）；**平稳** = 流量长期稳定。削峰只对尖峰有意义 |
| **生产者 / 消费者** | 发消息的一方（抢购接口）/ 取消息干活的一方（三个消费者程序） |
| **Topic** | 消息的**频道名**，按业务分类：`topic_order_create`（下单）、`topic_order_timeout`（超时关单）、`topic_cache_evict`（缓存删除补偿） |
| **消费组**（`consumerGroup`） | 干同一件事的一群实例：**同一个组里一条消息只会被其中一个实例处理** → 消费不过来了加实例就能提速 |
| **幂等表** | 一张数据库表（`mq_consume_log`），`msg_id` 建唯一索引。**插入成功 = 第一次消费**，插入冲突 = 这条消息我处理过了 |
| **QUEUING** | 抢购接口返回给前端的临时状态，意思是"**你抢到了，订单还在排队生成**"。前端据此显示"排队中"并开始轮询 |
| **轮询** | 前端每隔 400ms 调一次 `/api/seckill/result/{orderNo}`，直到状态变成 `PENDING_PAY`（订单已生成） |
| **traceId** | 一次请求的"跟踪号"。入口生成，**塞进消息属性带到消费者**，所以"接口 → MQ → 消费者"三段日志能被同一个 ID 串起来 |
| **阶梯重试** | 消费失败后 RocketMQ 自动按**越来越长的间隔**重投（不是立刻重试、也不是无限重试） |
| **同步重发一次** | 本项目对"异步发送失败"的兜底动作：`onException` 里改用 `syncSend` 再发一次（带 broker 自带的 3 次重试） |
| **闭环压测** | 压测模型：固定 N 个工作线程，每个线程**发一个请求、等响应、再发下一个**，直到打完总数——模拟真实用户，而不是一次性把 2000 个请求全丢出去 |
| **对照组** | 同一套业务的另一条实现路径（`/api/bench/seckill-sync`：同步扣库 + 同步写单），用来证明"差异来自异步本身" |

**抢购接口到底做了哪几件事**（`SeckillService.seckill`，一共四件、**没有一件是写数据库**）：

| # | 做什么 | 在哪 |
| --- | --- | --- |
| ① | 校验活动（缓存读 + 时间窗口 + 状态） | `activityService.detailForSeckill` |
| ② | 幂等预热库存 + Lua 原子扣减 | `stockService.ensurePrepared` / `trySeckill` |
| ③ | 生成订单号 | `OrderNoGenerator.next(userId)` |
| ④ | 投一条 MQ 消息，然后返回 | `mqProducer.sendAsync` |

**消费者做的活（都是"重活"，但已经不在用户等待的时间里了）**：先查幂等表 → 扣数据库库存（`WHERE available_stock > 0`）→ 插订单（唯一索引兜底）→ **投一条延迟 30 秒的关单消息** → 标记成功。

| 参数 | 真实值 | 在哪 |
| --- | --- | --- |
| 下单消费者线程数 | `consumeThreadMax = 32` | `OrderCreateConsumer` 的 `@RocketMQMessageListener` |
| 数据库连接池上限 | `hikari.maximum-pool-size = 20` | `application.yml` |
| Tomcat 工作线程上限 | `server.tomcat.threads.max = 200` | `application.yml` |
| 生产者发送超时 | `send-message-timeout = 3000`（毫秒） | `application.yml` |
| 生产者同步发送失败重试 | `retry-times-when-send-failed = 3` | `application.yml`（**注意：只对同步发送生效**） |

**这三个数放在一起看，就是"削峰"的全部证据**：Tomcat 有 200 个线程可以去接抢购请求，但它们**不等数据库**；真正打数据库的是 32 个消费者线程，而数据库连接池只有 20 —— **抢购接口的并发再高，落到数据库上的并发也就是这 20 个连接**。

## 维度② 为什么这么选

**为什么不能"多开几个线程去写"（@Async 线程池）**：

| 线程池（@Async）的问题 | MQ 怎么解决 |
| --- | --- |
| 任务在**内存**里，服务一重启就没了 | **消息落磁盘**，进程挂了消息还在 → **可靠** |
| 失败要么在内存里重试、要么丢 | 能**阶梯重投**（越等越久），还能进死信 → **可重试** |
| 高峰期把**业务线程也占满**（线程池本身也会满） | 任务堆在 Broker，消费者按自己的速度消费 → **削峰** |
| 没有流量视图：堆积了多少、失败了几条看不见 | Broker 与控制台能看到堆积量、重试次数、消息轨迹 → **可观测** |

**为什么是 RocketMQ，不是别的**：

| 备选 | 为什么没选 |
| --- | --- |
| **Kafka** | 吞吐更强，但**没有原生延迟消息**（关单要自己写调度层）；本项目量级也用不上它的吞吐 |
| **Redis List / Stream 当队列** | 可靠性与重试要自己实现（消费确认、重投、死信、堆积监控），等于自己造一个 MQ；而且和缓存共用实例，队列积压会影响缓存 |
| **数据库轮询表** | 那就是"定时任务扫表"的另一种形式：扫描范围、漏扫、扫描本身的开销都要自己处理（见亮点⑥） |
| **RocketMQ** ✅ | 原生**延迟消息**（超时关单直接用）、**死信队列 + 控制台 + 消息轨迹**、国内生态好查资料 |

**代价（这一段一定要主动说）**：

| 代价 | 说明 |
| --- | --- |
| 用户拿不到"最终结果"，只能拿一个 `orderNo` | 所以**必须配一个结果查询接口**（`/api/seckill/result/{orderNo}`），否则异步就是把不确定性甩给用户 |
| 消息会重复 | MQ 保证的是"**至少送到一次**"，所以消费端**必须幂等**（`mq_consume_log`） |
| 多了一个"投递失败"的窗口 | Redis 扣了、消息没发出去 → 用户一直看到 `QUEUING`。本项目只做了"同步重发一次"，**没有本地消息表**（明确的边界） |
| 排查变复杂 | 一次抢购跨 HTTP → MQ → 消费端，所以要用 **traceId 贯穿日志与消息** |

## 维度③ 流程（能画出来）

**两条链路，画图时一定要分开画**：

```
【链路 A：用户等待的这段，必须快】实测 28ms
  前端点击
    ↓
  POST /api/seckill/{activityId}
    ↓ 限流（Redis ZSet + Lua）
    ↓ 读活动（逻辑过期缓存）
    ↓ Lua 原子扣减库存 + 一人一单
    ↓ 生成 orderNo
    ↓ sendAsync(topic_order_create)   ← 不等 broker 回执
    ↓
  返回 { orderNo, state: "QUEUING" }
    ↓
  前端每 400ms 轮询 /api/seckill/result/{orderNo}

【链路 B：消费者干的活，用户可以不等】实测订单约 157ms 后落库
  topic_order_create
    ↓ OrderCreateConsumer（消费组 cg_order_create，32 线程）
    ↓ ① 幂等表 tryAcquire(msg_id)      ← 重复消息在这里被丢掉
    ↓ ② 扣数据库库存（WHERE available_stock > 0）
    ↓ ③ 插入订单（uk_order_no + uk_user_activity 兜底）
    ↓ ④ 投延迟消息 topic_order_timeout（30 秒档）→ 见亮点⑥
    ↓ ⑤ markSuccess(msg_id)
    ↓
  轮询接口这时返回 state = "PENDING_PAY" + 订单详情
```

**分步说明与失败路径**：

| 步骤 | 干什么 | 失败了怎么办 |
| --- | --- | --- |
| ① 幂等 | 往 `mq_consume_log` 插一行（`msg_id` 唯一索引） | 插入冲突：查这条记录，**成功过 → 直接 return（丢弃）**；**失败过 → 置回 CONSUMING、`retry_count + 1`、放行重试** |
| ② 扣库存 | `UPDATE flash_activity SET available_stock = available_stock - 1 WHERE id = ? AND available_stock > 0` | 影响 0 行 → 抛异常；消费者回滚 Redis 预扣的库存与名额 |
| ③ 插订单 | `INSERT INTO seckill_order ...` | 抛 `DuplicateKeyException`（同一用户重复下单）→ 把刚扣的数据库库存还回去、返回 null → 消费者按"重复单"走 `rollbackAll` |
| ④ 投延迟消息 | `sendAsync(topic_order_timeout, ..., nearestDelayLevel(30))` | 发送失败 → 同步重发一次；仍失败只记 ERROR（边界，见维度④） |
| ⑤ 标记成功 | `markSuccess(msg_id)` | —— |
| （异常路径） | 任一步抛异常 | `rollbackOnce`（回滚 Redis 库存与名额，**每条消息只回滚一次**）+ `markFailed` + 抛出 → **交给 MQ 阶梯重试** |

## 维度④ 兜底（四个"如果" + 一个明确的缺口）

**如果① 消息重复了**：MQ 保证"**至少送到一次**"，所以重复一定会发生（重试、broker 重投、调用方重发都会造成重复）。
拦法：**幂等表**，`mq_consume_log.msg_id` 建唯一索引——插入成功就是第一次；冲突就按状态判断（成功过 → 丢弃；失败过 → 放行重试）。**业务层还有第二层**：`uk_user_activity` 唯一索引，即使幂等表被清空，也不可能落下同一个用户的第二单。

**如果② 消息丢了**：分三段看——

| 哪一段 | 现状 |
| --- | --- |
| **生产端**（发消息） | `asyncSend` 失败 → `onException` → **同步重发一次**（`syncResend`，带 broker 自带的 3 次重试）；仍失败只打 `log.error`。**这就是缺口**：极端情况（发消息前进程崩溃）消息仍会丢，用户会一直轮询到 `QUEUING` |
| **Broker 端**（存消息） | 用持久化存储，进程重启不丢 |
| **消费端**（收消息） | 业务成功才 `markSuccess`；失败 `markFailed` 后抛出 → MQ 阶梯重试 → 超限进死信 |

> **必须主动说的边界**：**项目没有本地消息表**。正确做法是"把扣减和待发消息写进同一处，定时任务补发"，或者用 RocketMQ 的事务消息。我没做，所以"扣了库存但消息没发出去"这个窗口目前只有"同步重发一次 + 错误日志"兜着。

**如果③ 消息积压了**：先诊断是"**进来的太多**"还是"**出去的太慢**"（药完全不同）。
- 进来的多 → 加消费实例（消费组保证一条消息只被一个实例处理，加实例就能提速）；源头限流（限流见亮点⑤）；非核心动作降级。
- 出去的慢 → 找出是哪个下游慢（本项目消费链路里只有数据库）、**不要用无限重试把下游越打越死**、把慢活拆到别的 Topic。
- **本项目的现实边界**：Redis、RocketMQ 都是**单节点**，没有集群与多副本，所以"加实例"这件事在当前部署形态下是受限的——压测时就是靠"等 MQ 排空"来保证对照组干净的。

**如果④ 消息乱序了**：**本项目设计成"不需要顺序"**。`OrderCreateEvent` 只带业务主键（`orderNo / userId / activityId / productId / flashPrice`），关单消息只带 `orderNo`；消费者拿到消息后**按 `orderNo` 回查数据库再决定动作**，所以谁先到都对。真要求强顺序（比如流水），要用 RocketMQ 的顺序消息 + 按业务键固定发到同一队列。

**如果⑤ 用户一直看到"排队中"**：这是异步化的固有代价。三条路：结果查询接口（已有）、超时提示（前端轮询最多 15 秒）、以及真正的解法——**本地消息表 / 事务消息**（未做）。

## 维度⑤ 实测产出

| 指标 | 数字 | 怎么来的 |
| --- | --- | --- |
| **抢购接口返回耗时** | **28 ms** | 异步版接口：只做校验 + Redis 扣减 + 发消息，不等数据库 |
| **订单落库延迟** | 接口返回后约 **157 ms** 订单可查（状态 `PENDING_PAY`） | 前端轮询到订单可见的耗时；**这是"通常值"，不是 P99** |
| **削峰对比（50 并发 / 2000 请求，同机）** | **异步 176 req/s**、平均 280.66 ms、P50 282 ms、P90 307 ms、P95 315 ms、**P99 329 ms** | 打 `/api/bench/seckill-async`（Lua 扣减 + MQ 异步下单） |
| （同上，对照组） | **同步 39 req/s**、平均 1259.62 ms、P50 1261 ms、P90 1359 ms、P95 1394 ms、**P99 1462 ms** | 打 `/api/bench/seckill-sync`（同步扣库 + 同步写单） |
| **结论** | **吞吐约 4.5 倍、P99 降约 77%** | 176 ÷ 39 ≈ 4.5；(1462 − 329) ÷ 1462 ≈ 77% |

**怎么读懂这几个数**：

| 词 | 什么意思 | 为什么看它 |
| --- | --- | --- |
| **req/s（吞吐）** | 每秒能处理完多少请求 | 反映系统"能扛多少" |
| **平均 280.66 ms** | 所有请求耗时的平均值 | 容易被少数极慢请求带偏，只作参考 |
| **P50 / P90 / P95 / P99** | **99% 的请求都比这个数快**（P50 就是中位数） | P99 最接近"用户遇到的最差体验"。**削峰的效果在 P99 上体现得最明显：1462 → 329**  |
| **50 并发、各 2000 请求** | 闭环压测：50 个工作线程，每个发完一个请求再发下一个 | 模拟真实客户端，不是一次性把 2000 个请求全丢出去（那样测的是"瞬时压力"，不是吞吐） |

**对照实验的纪律（不做这三条，数字会互相污染）**：

1. 两组必须在**同样的背景噪音**下测：先把上一轮的 MQ 消息消费干净（轮询统计接口直到 `orderCount` 不再增长）再跑下一组；
2. 把订单超时时间调长（压测时用启动参数把 `flashmart.seckill.order-timeout-seconds` 调大），否则跑到 30 秒后前面的订单会被超时关单，额外的库存回滚会干扰吞吐；
3. 每次跑之前重置库存与订单，保证起点一致。

**必须主动说的环境边界**：本机 Windows + Docker 中间件、**压测客户端与服务同机**（客户端会抢 CPU），绝对值不代表线上，只能说明趋势。另外**同步对照组在高并发下会打满数据库连接池**（池子只有 20 个连接）——这恰好就是"为什么要异步"的现场证据。

## 维度⑥ 方法论

**该不该异步，三个问题，全"是"才做**：

| # | 问题 | 本项目的答案 | 反例 |
| --- | --- | --- | --- |

**异步化必须配的四件套**：

| 配套 | 缺了会怎样 | 本项目怎么落 |
| --- | --- | --- |

## 40 秒口述版

# 亮点③ 逻辑过期防击穿 + 空值缓存防穿透

## 卡片原文（对照用）

> ① **是什么/怎么用**：**逻辑过期**：缓存里额外存一个过期时间，物理 key 不删；逻辑过期后**返回旧值** + 后台异步重建（SETNX 互斥）。**空值缓存**：查不到的数据写一个空值标记 + 短 TTL
> ② **为什么这么选**：**击穿**：热点 key 一失效，全量请求同时打库。用互斥锁重建会让请求排队等；逻辑过期让请求立刻拿到旧值，重建在后台做。**穿透**：查不存在的 id 会每次打库，写空值标记就能挡住
> ③ **具体流程**：读缓存 → 命中空值标记直接返回 null → 未命中则 SETNX 只放一个线程回源（其余等 60ms 重读）→ 命中后判断逻辑过期，过期就异步重建
> ④ **兜底**：重建失败继续用旧值；空值 TTL 只有 30 秒，真有数据了不会被长期挡住；物理 TTL 是逻辑 TTL 的 3 倍，保证逻辑过期后旧值还在
> ⑤ **实测产出**：缓存被删后 **100 并发只回源 1 次**（114ms）；逻辑过期瞬间 **100 并发全部成功、只重建 1 次**（119ms）；查不存在的活动 **200 次只回源 1 次**
> ⑥ **方法论**：缓存三问：**数据存不存在（穿透）？热点会不会同时失效（击穿）？大量 key 同时过期（雪崩）？** 三问各有各的解法

## 维度① 是什么 · 怎么用

| 卡片里的词 | 大白话 |
| --- | --- |
| **缓存穿透** | 查的东西**数据库里也不存在**，缓存永远不命中 → **每一次请求都白跑一趟库**。典型场景：查不存在的活动 id、被恶意遍历 id |
| **缓存击穿** | 某个**热点 key 在某一瞬间失效**，N 个并发请求同时发现"缓存没了"，一起扑向数据库 |
| **缓存雪崩** | **大量 key 在同一时刻集体过期**（比如批量预热时给了同样的 TTL），数据库瞬间被全量回源砸中 |
| **逻辑过期** | 缓存里**额外存一个"逻辑过期时间"**（`expireAt`），到点**不删 key**，只是标记"我过期了"；请求照常拿到旧值继续服务，重建交给后台 |
| **物理 TTL** | Redis 里那个 key **真正的过期时间**（到点 Redis 自己删掉）。本项目把它设成**逻辑 TTL 的 3 倍**，就是为了保证"逻辑过期之后旧值还在" |
| **异步重建** | 逻辑过期后，**用一个后台线程**去查数据库、把新值写回缓存；**当前请求不等它**，直接返回旧值 |
| **SETNX 互斥** | `SET key value NX`（不存在才设置）当"一把简易锁"：**只有一个线程能抢到**，其他线程不重复回源 |
| **空值缓存 / 空值标记** | 回源发现"数据库里真没有"时，往缓存写一个特殊标记 `__NULL__` + **30 秒 TTL**。后续请求命中它就直接返回 null，不再打库 |
| **回源** | 缓存没命中 → **回到数据库去查**这一次。所有指标看的都是"回源次数" |
| **回源计数** | 代码里埋的一个计数器（`cache:loadcount:{key}`），**只有真回源时才 +1**，专门用来把"只回源一次"变成可复现的数字 |
| **冷启动** | 缓存**被完全删掉**（不是逻辑过期）的那种状态：连旧值都没有，没得返回 |

**读缓存的三条分支**（`RedisCacheClient.getWithLogicExpire`，这就是全部逻辑）：

| 读到什么 | 怎么处理 | 为什么 |
| --- | --- | --- |
| `__NULL__`（空值标记） | **直接返回 null**，不回源 | 这就是**防穿透**：数据库里确实没有，别再去问了 |
| `null`（什么都没有） | `SETNX` 抢重建锁（TTL 10 秒）：抢到的线程**同步回源**并写入缓存；**没抢到的等 60ms 后重读缓存**，还读不到就**自己兜底回源一次** | 这就是**防冷启动击穿** |
| 有值（包装体 `{expireAt, data}`） | 比对 `expireAt`：没过期直接用；**过了期也先把旧值返回**，同时 `SETNX` 抢锁、抢到的提交一个后台重建任务 | 这就是**逻辑过期防击穿** |

**几个真实配置值**：

| 配置 | 真实值 | 在哪 |
| --- | --- | --- |
| 活动详情的逻辑过期时间 | `flashmart.cache.activity-logic-expire-seconds: 60`（秒） | `application.yml` |
| 物理 TTL | 逻辑 TTL × 3 = **180 秒** | `RedisCacheClient.writeWithLogicExpire` |
| 空值标记 TTL | `flashmart.cache.null-value-ttl-seconds: 30`（秒） | `application.yml` |
| 重建互斥锁 TTL | 10 秒（`cache:rebuild:lock:{key}`） | `RedisCacheClient` |
| 没抢到锁的等待时间 | **60 毫秒**后重读缓存 | `RedisCacheClient.sleepQuietly(60)` |
| 异步重建线程池 | **固定 4 个守护线程**，名字 `cache-rebuild` | `RedisCacheClient` |
| 缓存 key | `activity:detail:{activityId}` | `ActivityCacheKeys` |

**一个容易漏的设计**：**剩余库存故意不放进缓存**。`ActivityCacheVO` 里没有库存字段，详情接口的 `remainingStock` 是**每次实时读 Redis** 的。这样"标题、价格可能短暂陈旧，但**库存永远实时**"，不会出现"页面显示有货、点进去抢不到"。

## 维度② 为什么这么选

**防击穿：三种做法对比**：

| 方案 | 请求会不会被阻塞 | 结果 |
| --- | --- | --- |
| **什么都不做** | 不阻塞 | ❌ 热点 key 失效瞬间，N 个并发**同时回源**，数据库被打穿 |
| **互斥锁重建**（谁抢到锁谁回源，其他人**等着**） | ✅ **阻塞**：没抢到锁的请求要等重建完成才能返回 | 数据是新的，但**响应时间被重建时间绑架**；重建慢的时候还会连锁拖垮线程池 |
| **逻辑过期 + 异步重建** ✅ | ❌ 不阻塞：**旧值立刻返回**，重建在后台 | 短暂返回旧值（60 秒逻辑 TTL 的代价），换来"重建期间所有请求都不受影响" |

**为什么还要额外补一条"冷启动路径"**：逻辑过期只在"**key 还在**"时有效。如果缓存**被整个删掉**（本项目的商家改活动就会删缓存、压测的 reset 也会删），连旧值都没有，就得用 `SETNX` 互斥 + 60ms 等待重读来顶住。**这两条路径解决的是两个不同的问题**，卡片的 ③ 里其实两条都写了。

**防穿透：为什么是空值缓存而不是布隆过滤器**：

| 方案 | 优点 | 为什么本项目没选 / 选了 |
| --- | --- | --- |
| **布隆过滤器** | 内存极省、能挡任意 id | 要额外维护位图与数据同步，还有**误判**要处理；本项目数据量级（活动表几十条）完全用不上 |
| **空值缓存** ✅ | 几行代码、立竿见影 | 代价是"每次换一个不同的不存在 id"仍会穿透（这是明确接受的边界）；**30 秒 TTL** 保证真有数据了不会被长期挡住 |

**代价与收益**：

| 收益 | 代价 |
| --- | --- |
| 击穿场景下请求**不阻塞**，100 并发全部成功、总耗时 119ms | 逻辑过期后**有最多 60 秒的旧值窗口**（所以库存字段坚决不放缓存） |
| 穿透场景下 200 次查询只回源 1 次 | 空值标记本身也占内存，且要接受"30 秒内真数据也可能看不到" |
| 冷启动有互斥，只有 1 个线程回源 | **60ms 的等待是一把双刃剑**：后端被压时，抢到锁的线程回源超过 60ms，其余线程就会走"自己兜底回源"这条**不加锁**的分支 → 退化成 N 次回源（见维度④） |

## 维度③ 流程（能画出来）

```
读活动详情 GET /api/activity/{id}
  ↓
GET activity:detail:{id}
  │
  ├─(A) 读到 __NULL__  ──────────────→ return null  →「活动不存在」     【防穿透】
  │
  ├─(B) 读到 null（缓存被删/从没写过）
  │       SETNX cache:rebuild:lock:{key}（TTL 10 秒）
  │        ├─ 抢到 → countLoad() → 查数据库
  │        │            ├─ 查到了 → 写 {expireAt, data}，物理 TTL = 逻辑 TTL × 3
  │        │            └─ 没查到 → 写 __NULL__（TTL 30 秒）→ return null
  │        │          最后 finally 删锁
  │        └─ 没抢到 → sleep 60ms → 重读缓存
  │                     ├─ 读到值 → 直接返回
  │                     └─ 还是读不到 → countLoad() → 自己回源（★ 这条分支不加锁）
  │
  └─(C) 读到值 {expireAt, data}
          ├─ now <= expireAt → 直接用
          └─ now >  expireAt → 【逻辑过期】
                ① 立刻把旧值返回给请求（不阻塞）
                ② SETNX 抢锁（TTL 10 秒），抢到的提交后台任务：
                      countLoad() → 查库 → 写回新值
                ③ 没抢到的什么都不做（继续用旧值）
```

**分步说明**：

| 步骤 | 关键点 | 为什么这么设计 |
| --- | --- | --- |
| (A) 空值标记 | 标记是个字符串常量 `__NULL__`，不是 JSON | 命中判断只需要一次字符串比较，**代价最低** |
| (B) 冷启动 | 抢到锁的线程**同步回源**（这条路径必须等，因为没有任何值可以返回） | 用 60ms 的短等待换"大多数并发只回源一次" |
| (B-兜底) | 等待后仍读不到就**自己回源，不再加锁** | ⚠️ 这是**有意的退让**：宁可多回源几次，也不能让请求永久等待。**后端被压时它就是退化的原因**（如实说） |
| (C) 逻辑过期 | 先返回旧值，再 `SETNX` 抢锁丢给 4 线程的后台池 | 请求路径上没有任何"等待重建"的动作 → 这就是 100 并发 119ms 的来源 |
| 重建写回 | `writeWithLogicExpire`：新的 `expireAt` + 物理 TTL = 逻辑 × 3 | 保证下一次逻辑过期时**旧值还在**，循环成立 |

## 维度④ 兜底

| 如果…… | 会怎样 | 靠什么兜住 |
| --- | --- | --- |
| **① 重建失败了（数据库抖了一下）** | 本次请求早就拿到旧值返回了；旧值继续服务 | `asyncRebuild` 里 catch 住只打 `log.warn`，异常自吞；物理 TTL 还没到，旧值还在；下一个请求会再触发一次重建 |
| **② 重建太慢，旧值已经物理过期了** | 缓存真的没了 → 走冷启动路径 | 物理 TTL 是逻辑 TTL 的 **3 倍**，就是为了给重建留足时间 |
| **③ 多个线程同时发现逻辑过期** | 只有 1 个线程去重建 | `SETNX `cache:rebuild:lock:{key}`（TTL 10 秒）互斥；锁在 `finally` 里删掉，**异常也不会把锁留下** |
| **④ 后端被压时冷启动退化了** | 回源次数会从 1 涨到接近并发数 | ⚠️ **没有兜住，如实说**：等 60ms 后仍读不到就自己回源，这条分支不加锁。实测**后端空载时 100 并发回源 1 次；后端被压时回源 100 次**。想彻底解决要把等待改成"带退避的多次重读"或者干脆"等锁 + 超时后返回降级值" |
| **⑤ 缓存里写的是空值，但数据刚被创建出来** | 最多 **30 秒**看不到这条数据 | 空值 TTL 只有 30 秒，且**商家创建活动时会主动预热并删详情缓存**，正常路径不会等这么久 |
| **⑥ 缓存被完全删掉（商家改活动 / 压测 reset）** | 走 (B) 冷启动路径，不会集体打库 | `SETNX` 互斥 + 60ms 重读 |
| **⑦ 库存显示不准** | 不会 | **剩余库存不进缓存**：`ActivityCacheVO` 刻意不含库存字段，详情每次都实时读 Redis |
| **⑧ Redis 整个挂了** | 读缓存抛异常 | ⚠️ **本项目没有为"读写缓存"做兜底**：缓存异常会一路抛到全局异常处理器（返回"系统繁忙"）。这属于明确边界——只有限流那一层做了"Redis 挂了就放行"的降级 |

## 维度⑤ 实测产出

| 实验 | 做法 | 结果 |
| --- | --- | --- |
| **击穿（缓存被删）** | 先读一次让缓存生效 → 服务端**删掉详情缓存并把回源计数清零** → **100 个并发**请求详情 | **回源数据库只 1 次**，100 个请求**总耗时 114 ms**（修复前是 100 次） |
| **击穿（逻辑过期瞬间）** | 把逻辑 TTL 调短，**在逻辑过期的那一瞬间**打 **100 个并发** | **100 个请求全部成功**、**只触发 1 次异步重建**，总耗时 **119 ms** |
| **穿透** | 查一个**不存在的活动 id**，并发 **200 次** | 全部返回"活动不存在"，**累计回源 1 次** |

**这三个数为什么有说服力**：

| 数 | 它在证明什么 |
| --- | --- |
| **回源 1 次 / 100 并发** | 互斥真的生效了：**99 个请求没有打数据库** |
| **总耗时 114 ms / 119 ms** | 这是"100 个并发请求**全部拿到响应**"的墙钟时间。如果用的是"互斥锁让请求排队等重建"的方案，没抢到锁的请求要等重建完成，**这个数字会明显变大**——所以 119ms 同时也是"请求没有被重建阻塞"的证据 |
| **200 次只回源 1 次** | 空值标记生效：从第 2 次起全部命中 `__NULL__` |

**必须主动说的边界**：**100 并发只回源 1 次这个结论只在"后端空载"时成立**；后端被 MQ 消费压着的时候，抢到锁的那次回源会超过 60ms，其余线程走兜底分支自己去回源，**100 并发就变成 100 次回源**。这不是工具的问题，是代码里那条"等待后自己回源"的分支可复现的行为。另外，环境仍是本机 Windows + Docker、客户端与服务同机。

## 维度⑥ 方法论

**缓存三问，逐条对照自己的系统**：

| 问题 | 名字 | 典型症状 | 本项目的解法 |
| --- | --- | --- | --- |
| 查的**数据存不存在**？ | **穿透** | 数据库里也没有 → 每次请求都白跑一趟库 | 空值缓存 `__NULL__` + 30 秒 TTL |
| **热点 key 会不会在某一瞬间同时失效**？ | **击穿** | 一个 key 失效 → N 个并发同时回源 | 逻辑过期 + 异步重建（不阻塞）；冷启动补 SETNX 互斥 |
| **大量 key 会不会同时过期**？ | **雪崩** | 大批 key 集体失效 → 全量回源 | ⚠️ 本项目**没有专门处理**：活动详情逻辑 TTL 固定 60 秒，靠"逻辑过期不阻塞 + 物理 TTL 3 倍"减弱影响；正解是 TTL 加随机抖动。这一条要如实说是边界 |

**再往上一步，是"缓存设计的四个自问"**：

| # | 自问 | 本项目的答案 |
| --- | --- | --- |
| ① | **这份数据能容忍多旧？** | 活动标题/价格能容忍 60 秒 → 逻辑过期；**库存不能容忍** → 不进缓存 |
| ② | **这份数据有多热？** | 活动详情是热点（所有人都在看同一个活动）→ 值得为它做防击穿 |
| ③ | **失效的那一瞬间，谁来承担回源？** | 一个线程（互斥），而不是全部请求 |
| ④ | **重建期间用户看到什么？** | 旧值（可接受），而不是转圈或报错 |

## 40 秒口述版

> "活动详情是典型热点，我做了两个针对性设计。
> **防击穿用逻辑过期**：缓存里除了数据再存一个 `expireAt`，物理 TTL 设成逻辑 TTL 的 **3 倍**，所以逻辑过期后 key 还在、旧值还读得到；读到逻辑过期时**先把旧值返回**，再用 `SETNX` 抢锁、丢给后台线程池重建。这样重建期间请求**既不阻塞、也不会打穿数据库**——实测逻辑过期瞬间 100 个并发全部成功、只触发 1 次异步重建，总耗时 119ms。
> 另外我还补了一条**冷启动路径**：如果缓存是被**整个删掉**的（商家改活动就会删），旧值没得返回，那就用 `SETNX` 只放一个线程同步回源，其余线程等 60 毫秒重读缓存。实测缓存被删后 100 个并发**只回源 1 次**，总耗时 114ms。
> **防穿透用空值缓存**：回源查不到就写一个 `__NULL__` 标记、TTL 30 秒，同一批不存在的 id 只会打一次库。实测查不存在的活动 200 次，累计只回源 1 次。
> 有一个边界我会主动说：**'只回源 1 次'这个结论只在后端空载时成立**——后端被压的时候，等 60 毫秒仍读不到缓存的线程会走'自己兜底回源'那条不加锁的分支，100 并发就会退化成 100 次回源。"

# 亮点④ Cache Aside + 补偿重试 + 延迟双删 + TTL

## 卡片原文（对照用）

> ① **是什么/怎么用**：更新数据时：**先更新数据库 → 再删缓存**（不是更新缓存）；删失败落补偿任务 + 投 MQ 重试；再投一条**延迟 5 秒**的消息做"延迟双删"；最后还有 TTL 兜底
> ② **为什么这么选**：并发更新时"更新缓存"会出现后写的旧值覆盖先写的新值，而且不自愈；"删除"天然幂等、下次读自然回源。延迟双删是为了清掉"并发读在删除之后才回填的旧值"
> ③ **具体流程**：商家改活动 → 更新数据库 → 删缓存（失败则落 `cache_sync_task` + 投 MQ）→ 投延迟 5 秒消息再删一次 → TTL 兜底
> ④ **兜底**：三层：**补偿重试**（删失败重试）、**延迟双删**（清回填）、**TTL**（最终一定过期）。删缓存失败也不影响主流程
> ⑤ **实测产出**：补偿与双删链路都跑通（补偿任务状态 PENDING → SUCCESS、`retry_count` 会累加）；**一致性没有做量化验证，如实说**
> ⑥ **方法论**：缓存一致性四步：**先库后删 → 删除失败要能重试 → 并发回填要能补一刀 → 最后一定有 TTL**

## 维度① 是什么 · 怎么用

| 卡片里的词 | 大白话 |
| --- | --- |
| **Cache Aside** | 缓存一致性的经典写法：**读的时候**没命中就回源并写回缓存；**写的时候**先更新数据库、再让缓存失效（删掉）。缓存不是"数据的第二份真相"，只是一个副本 |
| **为什么是"删"不是"更新"** | 删 = 让这份副本**失效**，下次读自然回源拿新值；更新 = 你得**算出一份正确的新值写进去**，算错了就是脏数据，而且**不会自愈** |
| **补偿任务** | 删缓存失败时，往 `cache_sync_task` 表落一条 **PENDING** 记录（`cache_key / status / retry_count / error_msg`），这就是一份**持久化的待办清单** |
| **延迟双删** | **删两次**：更新库后立刻删一次，**5 秒后再删一次**。第二刀专门用来清掉"并发读在第一次删之后才回填进去的旧值" |
| **TTL 兜底** | 缓存 key 本身有物理过期时间，**就算前面所有手段都失效，它最终也一定会过期**，下一次读自然回源 |
| **回填** | 读路径把数据库查出来的值**写进缓存**这个动作 |
| **最终一致** | 允许中间有一小段时间不一致，但**最终会一致**。本项目接受的就是这个语义 |
| **对账** | 定时把两份数据拉出来比一比、把不一致的修掉。**本项目没做**（明确边界） |

**更新一次活动，代码里到底发生了什么**（`ActivityService.update` + `CacheEvictService`）：

| # | 动作 | 代码 | 关键细节 |
| --- | --- | --- | --- |
| ① | 校验归属 | `activityMapper.selectById` + 比对 `merchantId` | 只能改自己的活动 |
| ② | 算新的可用库存 | `availableStock = 新总库存 − 已售出`（`已售 = 原总库存 − 原可用库存`），并且不小于 0 | **改库存不能把已卖出去的抹掉** |
| ③ | **先更新数据库** | `activityMapper.updateById` | 顺序不能反 |
| ④ | **再删缓存** | `cacheEvictService.evictWithCompensation("activity:detail:{id}")` | 见下 |
| ⑤ | 强制覆盖 Redis 库存 | `stockService.reset(activityId, availableStock, totalStock)` | ⚠️ 这里不用 `ensurePrepared`：预热带 10 秒 `SETNX` 互斥，商家 10 秒内连改两次的话第二次不会生效（踩过这个坑，已改成强制覆盖） |

**第 ④ 步展开**（`CacheEvictService`）：

```
evictWithCompensation(cacheKey)
  ├─ evict(cacheKey)
  │     ├─ 删除成功 → return
  │     └─ 删除失败 → ① INSERT cache_sync_task（status = PENDING, retry_count = 0）
  │                  ② sendAsync(topic_cache_evict, reason = "UPDATE", 延迟 0)
  └─ sendAsync(topic_cache_evict, reason = "DOUBLE_DELETE",
                nearestDelayLevel(5) = 第 2 档 = 延迟 5 秒)      ← 延迟双删
```

| 配置 / 常量 | 真实值 | 在哪 |
| --- | --- | --- |
| 延迟双删的延迟 | `flashmart.cache.double-delete-delay-seconds: 5`（秒） | `application.yml` |
| 实际生效的延迟 | **5 秒**（`nearestDelayLevel(5)` 命中 RocketMQ 第 2 档） | `MqProducer.DELAY_LEVEL_SECONDS` |
| 补偿任务状态 | PENDING / SUCCESS / FAILED | `CacheSyncTask` + DDL |
| 消费者回写状态的条件 | `status != 'SUCCESS'`（放开 FAILED，让失败过的任务重试成功后也能回到 SUCCESS） | `CacheEvictConsumer.markTask` |
| 重试次数累加 | `retry_count = retry_count + 1`（每次回写都 +1） | 同上（`setSql`） |
| 活动详情缓存物理 TTL | 逻辑 TTL × 3 = 180 秒 | `RedisCacheClient` |

**两类消息走同一条链路，用 `reason` 区分**：

| reason | 谁发的 | 消费者干什么 |
| --- | --- | --- |
| `UPDATE` | 删缓存失败时的补偿 | 重试删除；**成功就把补偿任务回写成 SUCCESS**；仍失败就置 FAILED 并抛异常走 MQ 重试 |
| `DOUBLE_DELETE` | 每次改数据都会发（延迟 5 秒） | 再删一次，清掉并发读回填的旧值（删不存在的东西是幂等的，不需要状态） |

## 维度② 为什么这么选

**四种缓存更新策略对比**：

| 策略 | 怎么做的 | 问题 |
| --- | --- | --- |
| **先更新缓存，再更新数据库** | 两个写操作 | ❌ 数据库写失败 → 缓存是新的、库是旧的，且不自愈 |
| **先删缓存，再更新数据库** | 删完再写库 | ❌ 经典并发漏洞：请求 A 删了缓存 → 请求 B 读缓存未命中、**从库里读到旧值并回填** → A 才把新值写进库 → **缓存里永久留着旧值** |
| **更新缓存**（写完库再写缓存） | `SET` 新值 | ❌ 并发下**后写的旧值覆盖先写的新值**（两个请求写入顺序无法保证）；而且算新值的逻辑一旦有 bug 就是脏数据，不自愈 |
| **Cache Aside：先更库、再删缓存** ✅ | `UPDATE` 库 → `DEL` 缓存 | ✅ 删除**天然幂等**；删完之后下一次读自然回源拿新值，**能自愈**；并发窗口小得多 |

**那为什么还要"延迟双删"**：因为"先更库再删缓存"**仍然有一个小窗口**：

```
时刻   请求 A（商家改活动）              请求 B（买家读详情）
 t0                                     读缓存未命中 → 回源读到【旧值】
 t1     UPDATE 库（新值）
 t2     DEL 缓存（此刻缓存里还没有东西）
 t3                                     B 把【旧值】写回缓存   ← 脏了！
```

**延迟 5 秒再删一次**，就是专门把这条"在删之后才回填进来的旧值"再清掉一刀。**这不是证明绝对一致的手段，只是把窗口缩小到"5 秒内到点的那个并发读"**。

**为什么延迟要用 MQ 而不是应用内定时任务**：

| 方案 | 问题 |
| --- | --- |
| 应用内 `ScheduledExecutor` / 线程池 | **应用一重启就没了**，延迟任务丢失；多实例还会重复执行 |
| **RocketMQ 延迟消息** ✅ | 消息**可持久化**、重启不丢、有重试；而且这套延迟能力本项目本来就在用（超时关单，见亮点⑥） |

**代价与收益**：

| 收益 | 代价 |
| --- | --- |
| 删除幂等、可自愈，不用维护"怎么算出正确的新缓存值" | **改数据到缓存失效之间，仍有一小段时间读到旧值**（最终一致，不是强一致） |
| 删缓存失败不影响主流程（落补偿任务 + 投消息） | 多了一张表、多了一个消费者、多了一条 MQ 链路要维护 |
| 三层兜底（补偿 / 双删 / TTL）互相独立，一层坏了两层还在 | 延迟双删的延迟**只能取 RocketMQ 的固定档位**（所以配置直接写成"秒"、命中 5 秒档） |
| —— | **一致性没有做量化验证**（见维度⑤），也没做对账任务 |

## 维度③ 流程（能画出来）

```
商家改活动 PUT /api/merchant/activity/{id}
  ↓
① 校验：这个活动是不是我的（不是 → 403）
② 算新的可用库存 = 新总库存 − 已售（不小于 0）
③ UPDATE flash_activity（先更库）              ← 顺序一
  ↓
④ DEL activity:detail:{id}（再删缓存）          ← 顺序二
  │     ├─ 成功 → 继续
  │     └─ 失败 → INSERT cache_sync_task（PENDING）
  │              + sendAsync(topic_cache_evict, UPDATE)     ┐
  │                                                          │ 兜底一：补偿重试
  ↓                                                          │
⑤ sendAsync(topic_cache_evict, DOUBLE_DELETE, 延迟 5 秒)     ┘ 兜底二：延迟双删
  ↓
⑥ stockService.reset()：强制覆盖 Redis 库存 + 总库存 + 清空已购记录
  ↓
                         …… 5 秒后 ……
  topic_cache_evict（DOUBLE_DELETE）
    ↓ CacheEvictConsumer（先过幂等表）
    ↓ DEL activity:detail:{id}      ← 把 5 秒内被回填的旧值再清一次
    ↓ markSuccess

【补偿路径】
  topic_cache_evict（UPDATE）
    ↓ CacheEvictConsumer
    ↓ DEL cacheKey
        ├─ 成功 → markTask(SUCCESS)，条件 status != 'SUCCESS'，retry_count + 1
        └─ 失败 → markTask(FAILED) + markFailed + 抛异常 → MQ 阶梯重试

【兜底三】activity:detail:{id} 物理 TTL = 逻辑 TTL × 3 = 180 秒，最终一定过期
```

**分步说明**：

| 步骤 | 为什么这么安排 | 失败了会怎样 |
| --- | --- | --- |
| ③ 先更库 | 数据库是"真相"，缓存只是副本 | 抛异常 → 整个 `update` 事务回滚（@Transactional(rollbackFor = Exception.class)），缓存**根本不会被删**，所以不会出现"库旧缓存也旧"以外的第三种状态 |
| ④ 再删缓存 | 删完之后的读会自动回源拿新值 | 删失败 → 落补偿任务 + 投消息；**主流程照常返回成功** |
| ⑤ 延迟双删 | 清掉并发读回填的旧值 | 消息发送失败 → 同步重发一次（走的是同一个 `sendAsync` 兜底）；再失败只有日志 |
| ⑥ 重置库存 | 改库存后 Redis 里的库存必须立即对齐 | 见"预售覆盖"，用 `reset` 保证 10 秒内连改两次也生效 |

## 维度④ 兜底（三个"如果" + 一个必须承认的缺口）

| 如果…… | 会怎样 | 靠什么兜住 |
| --- | --- | --- |
| **① 删缓存失败（Redis 抖了一下）** | 缓存里还是旧值，用户看到旧数据 | 落 `cache_sync_task`（PENDING）+ 投 `UPDATE` 消息 → 消费者重试删除 → 成功后**回写 SUCCESS**（条件 `status != 'SUCCESS'`，且 `retry_count + 1`） |
| **② 补偿重试也一直失败** | 补偿任务停在 FAILED，能查得到 | 状态字段就是"待办清单"：能查 PENDING/FAILED 的积压量；**再不行还有 TTL**——180 秒后 key 自己过期 |
| **③ 并发读把旧值回填进去了** | 缓存里短暂留着旧值 | **延迟双删**：5 秒后再删一次 |
| **④ 改完数据、缓存也删了，但用户就是看到了旧值** | 这是**最终一致**的固有代价 | 只能缩小窗口，不能消除。⚠️ **本项目的一致性没有做量化验证**，也没有对账任务——只能说明"链路跑通了"（见维度⑤） |
| **⑤ 延迟双删的消息丢了** | 那一刀没补上 | 没有二次兜底，只能靠 TTL 过期。**这是明确边界**（延迟消息和普通消息共用同一个"同步重发一次"的兜底） |
| **⑥ 商家 10 秒内连改两次库存** | 第二次必须生效 | `ActivityService.update` 用 `stockService.reset()` **强制覆盖**，而不是用带 `SETNX` 互斥的预热方法（这个坑踩过） |
| **⑦ 商家改了价、缓存还没删掉，用户按旧价下单** | 展示价与成交价不一致 → 纠纷或资损 | **成交前用数据库价格校验**（`OrderService.createOrder` 第 0 步）：与用户看到的价格不一致 → 抛 `PriceChangedException` → **不扣库存、不插订单** → 消费者回滚名额 + 提示“价格已变化，请刷新页面后重新抢购”。原则是**缓存只负责展示，成交前必须回权威源校验** |

**主动说的边界**：

> "我会很明确地说：**延迟双删是概率手段，它只能缩小不一致窗口，不能证明绝对一致**；我也**没有做对账任务**、没有量化验证不一致的持续时间。要做的话是两件事：一是加对账（定时比对 Redis 库存与 `available_stock`，不一致就告警或修正），二是把删缓存的失败率做成指标。这两件我都没做。"

## 维度⑤ 实测产出

| 项目 | 状态 |
| --- | --- |
| **补偿链路** | ✅ 跑通：删缓存失败 → `cache_sync_task` 落一条 **PENDING** → 消费者重试删除 → 状态回写成 **SUCCESS**；`retry_count` 每次回写都会累加 |
| **延迟双删链路** | ✅ 跑通：延迟 5 秒的消息按档位投递，到点由消费者再删一次（`reason = DOUBLE_DELETE`） |
| **主流程不受影响** | ✅ 删缓存失败不会让"改活动"接口失败 |
| **一致性量化验证** | ❌ **未实测**：没有测过"改完数据后，缓存里最多脏多久"、没有统计过不一致的占比，也没有对账任务 |

**为什么这一节几乎没有数字——而且这句话本身要主动说**：

> "缓存一致性这一项，我给不出数字。因为它要证明的是'**有多久不一致**'和'**不一致的概率**'，需要构造并发读写的对撞实验并统计脏读次数，**我没有做这个实验**。我能说的是链路跑通了、三层兜底都在，**但我不说'保证了强一致'**。"

## 维度⑥ 方法论

**缓存一致性四步，按顺序做**：

| # | 步骤 | 一句话理由 | 本项目怎么落 |
| --- | --- | --- | --- |
| ① | **先库后删** | 数据库是真相；删缓存比更新缓存幂等、且能自愈 | `UPDATE` → `DEL` |
| ② | **删失败要能重试** | 缓存组件的失败是常态，不能靠"这次运气好" | `cache_sync_task`（PENDING）+ MQ 补偿 |
| ③ | **并发回填要能补一刀** | 读路径的回填可能比删除更晚到 | 延迟双删（5 秒） |
| ④ | **最后一定要有 TTL** | 前面三层都失效时，过期是唯一的确定性保证 | 物理 TTL = 逻辑 TTL × 3 |

**再往上一层，是"选什么一致性语义"的判断**：

| 自问 | 本项目 |
| --- | --- |
| 这份数据**能不能容忍短暂不一致**？ | 活动的标题/价格/时间：能（秒级）→ 用"缓存 + 补偿 + TTL"这套便宜方案 |
| 有没有**不能容忍**的部分？ | 有——**库存**。所以库存不走缓存那套逻辑，而是"Redis 扣减 + 数据库兜底 + 回滚"（亮点①） |
| 强一致要花多大代价？ | 分布式事务 / 强同步，性能和复杂度都会上一个台阶。**本项目刻意避开**（抢购链路接受最终一致） |

**一句话**：**能容忍短暂不一致的走"最终一致 + 补偿 + TTL"；不能容忍的那部分，一开始就不要放进缓存。**

## 40 秒口述版

> "缓存一致性我用的是 **Cache Aside**：更新活动时**先更新数据库、再删缓存**，而不是更新缓存——因为并发更新时'更新缓存'会出现后写的旧值覆盖新写的新值，而且**不自愈**；而'删除'天然幂等，下次读自然回源，所以能自愈。
> 删缓存失败怎么办：落一条 `cache_sync_task` 记录（状态 PENDING）+ 投一条 MQ 消息让消费者重试删除，删成功后把状态回写成 SUCCESS，`retry_count` 会累加；**删缓存失败不会让'改活动'这个接口失败**。
> 还有一种更隐蔽的情况：**并发读在我删完之后才把旧值回填进缓存**——所以我再加一条**延迟 5 秒的延迟双删**，专门清这一刀。延迟用 **RocketMQ 延迟消息**做，不用应用内定时任务，因为应用一重启定时任务就没了。
> 最后还有 **TTL 兜底**（活动详情物理 TTL 是逻辑 TTL 的 3 倍）。
> 这一项我会主动承认：**链路都跑通了，但一致性我没有做量化验证**，延迟双删只能缩小窗口、不能证明绝对一致，对账任务也没做。"

# 亮点⑤ Redis ZSet + Lua + AOP 注解滑动窗口限流

## 卡片原文（对照用）

> ① **是什么/怎么用**：ZSet 存请求时间戳，Lua 一次完成"清理窗口外的成员 → 统计 → 写入"；注解 `SlidingWindowLimit` + AOP 切面，支持**全局 / IP / 用户**三个维度
> ② **为什么这么选**：抢购要"**精确限次、不预支突发额度**"：令牌桶允许突发（第一个项目用的就是它），固定窗口有边界双倍流量的漏洞，滑动窗口按"最近 N 秒内的请求数"精确统计
> ③ **具体流程**：切面读注解 → 拼 key `rate:seckill:USER:9003` → 执行 Lua（清理 → 统计 → 写入 + 设过期）→ 超阈值抛 429
> ④ **兜底**：Redis 不可用时**放行**（限流是保护手段，不能变成故障点）；身份一律取自服务端上下文（未登录接口从 HTTP 请求取真实 IP，否则会退化成全局限流——这个坑我踩过）
> ⑤ **实测产出**：同一用户 1 秒内 10 并发 → **5 通过 + 5 × 429**；改成每 1.2 秒 1 次匀速 → **全部通过**；登录接口并发 30 次 → 通过 20 + 限流 10
> ⑥ **方法论**：限流四要素：**维度（限谁）、算法（允不允许突发）、阈值（按正常行为分布定）、降级（组件挂了怎么办）**

## 维度① 是什么 · 怎么用

| 卡片里的词 | 大白话 |
| --- | --- |
| **限流** | 主动**拒绝一部分请求**，保住系统里其他请求能正常跑完。它保护的是"系统"，不是"用户" |
| **固定窗口** | 最简单：给每秒开一个计数器，满了就拒绝，下一秒清零 |
| **滑动窗口** | 不算"自然秒"，而是算"**最近 N 秒内**有多少请求"——窗口跟着当前时间往前滑 |
| **ZSet（有序集合）** | Redis 里"**每个成员带一个分数、自动按分数排序**"的集合。这里的**分数 = 请求的时间戳（毫秒）**，成员 = 这一次请求的唯一标识 |
| **ZREMRANGEBYSCORE** | 按分数范围**批量删除**成员。用在限流里就是"**把窗口外的老请求清掉**" |
| **ZCARD** | 数一数集合里有多少成员 → 就是"**窗口内的请求数**" |
| **ZADD** | 加一个成员 → 就是"**记录这一次请求**" |
| **PEXPIRE** | 设置 key 的过期时间（毫秒）。**没人再访问这个 key 时，它会被自动回收**，不用写清理任务 |
| **Lua 原子** | "清理 + 统计 + 写入"三步必须一口气做完，否则并发下会**都统计到没超限、于是都放行** |
| **AOP / 切面 / 注解** | 在方法上贴一个 `SlidingWindowLimit` 标签，切面在**方法执行前**自动做限流——**业务代码里一行限流都看不到** |
| **维度** | 按什么限：`GLOBAL`（整个接口）/ `IP`（客户端 IP）/ `USER`（登录用户） |
| **429** | HTTP 标准状态码 Too Many Requests，"你请求太多了"。本项目对限流异常**真的返回 HTTP 429**（其他业务异常返回 200 + code=400） |
| **阈值 / 窗口** | 注解上的 `maxRequests`（窗口内最多几次）和 `windowSeconds`（窗口多大） |
| **降级放行** | 限流组件自己挂了的时候**选择放行**（宁可能超发一点，也不能把业务全部熔断） |

**注解长什么样**（两个真实用例）：

| 接口 | 注解 | 含义 |
| --- | --- | --- |
| `POST /api/seckill/{activityId}` | `SlidingWindowLimit(key="seckill", windowSeconds=1, maxRequests=5, dimension=USER, message="手速太快啦，歇一秒再抢")` | **每个用户** 1 秒最多 5 次 |
| `POST /api/auth/login` | `SlidingWindowLimit(key="login", windowSeconds=1, maxRequests=20, dimension=IP, message="登录过于频繁，请稍后再试")` | **每个 IP** 1 秒最多 20 次（防撞库） |

**key 是怎么拼出来的**：

```
rate : {注解上的 key} : {维度} : {身份}
  ↓
rate : seckill : USER : 9003        ← 用户维度：身份 = UserContext 里的 userId
rate : login   : IP   : 203.0.113.7 ← IP 维度：身份 = 真实客户端 IP
rate : xxx     : GLOBAL : global    ← 全局维度：身份固定是 "global"
```

**这段 Lua 做了什么**（`lua/sliding_window.lua`，一共三步）：

| # | 命令 | 干什么 | 为什么 |
| --- | --- | --- | --- |
| ① | `ZREMRANGEBYSCORE key 0 now-windowMillis` | 把**窗口外的老成员全部删掉** | 这就是"滑动"：窗口跟着当前时间往前走，老请求自动出局 |
| ② | `ZCARD key` → `count >= maxRequests` | 数一数窗口内还有几个请求 | 超了就 `return 0`（**被限流**，注意这一步**不写入**） |
| ③ | `ZADD key now member` + `PEXPIRE key windowMillis` | 记录本次请求 + 给 key 设过期 | 成员唯一标识是 **traceId + 随机 UUID**，所以**同一毫秒内的并发请求也不会互相覆盖** |

返回 **1 = 放行，0 = 被限流**；Java 侧 `tryAcquire` 返回 boolean。

**切面的三段身份取值**（`SlidingWindowAspect`）：

| 维度 | 身份从哪来 | 关键点 |
| --- | --- | --- |
| `USER` | `UserContext.userId()` | 取不到（未登录）就用字符串 `anonymous`；**绝不用请求参数**——否则攻击者传别人的 ID 就能把别人的额度耗光 |
| `IP` | 先看 `UserContext` 里拦截器写进去的 `clientIp`；没有（未登录接口走不到拦截器）就**从当前 HTTP 请求取**：`X-Forwarded-For` 第一段，取不到用 `getRemoteAddr()` | ⚠️ **这个坑踩过**：不这样做的话，所有未登录的登录请求会挤进同一个桶，变成"全局限流"，一个人刷就能把别人挡住 |
| `GLOBAL` | 固定字符串 `global` | 保护整个接口或下游资源 |

## 维度② 为什么这么选

**四种限流算法对比**：

| 算法 | 怎么算 | 特点 | 问题 |
| --- | --- | --- | --- |
| **固定窗口** | 每自然秒一个计数器，满了拒绝、下一秒清零 | 实现最简单 | ❌ **边界处能过 2 倍流量**：卡在窗口交界处，前一秒末尾 + 后一秒开头，各放满一次 |
| **滑动窗口** | 统计"最近 N 秒内"的请求数（存时间戳） | 统计精确、**不预支突发额度** | 要存时间戳，内存开销比计数器大（本项目用 ZSet + PEXPIRE 自动回收） |
| **漏桶** | 请求进桶，按固定速率流出 | 流量最平滑 | ❌ **一点突发都不允许**：用户手滑连点两下就被拒 |
| **令牌桶** | 按固定速率发令牌，请求来领令牌 | **允许突发**（桶里攒着额度） | 参数要按业务调；对"精确限次"不友好 |

**为什么本项目要滑动窗口**：

> 抢购的诉求是"**精确限次、不预支突发额度**"。令牌桶允许突发——桶里攒了 5 个令牌，用户连点 5 下全放行；但抢购每放行一次就消耗一份库存，**我不希望把之前攒的额度一次性兑出来**。固定窗口又有边界双倍漏洞（2 秒内最多能放 2 × 5 = 10 次），所以用滑动窗口按"最近 1 秒内的请求数"精确统计。

（这也是和上一个项目的刻意区分：**上个项目的 AI 接口用令牌桶**——那里"允许突发"是优点；**这里用滑动窗口**——这里"允许突发"是风险。）

**为什么必须用 Lua**：

| 如果在 Java 里写三步 | 会发生什么 |
| --- | --- |
| `ZCARD` 统计 → Java 判断 → `ZADD` 写入 | 两个并发请求**都统计到"没超"** → **双双写入、双双放行** → 限流器在最需要它的时候（并发突发）失效 |

**为什么不用 Nginx / 网关限流**：

| 网关 | 本项目 |
| --- | --- |
| 只能按 IP、路径、Header 限 | 我要按**登录用户**限（得先解析 JWT 拿到 userId），还要按**注解配置**限 |
| 拿不到方法级配置 | 注解贴在 Controller 方法上，切面读注解 → 阈值和维度**跟业务代码放在一起**，改起来直观 |

**续一层：黑名单站在哪儿**（接着上面的表往下排）：

| 层 | 谁来做 | 本项目 |
| --- | --- | --- |
| 最外层（网关 / Nginx） | 粗粒度 IP 封禁、剥离外部 `X-Forwarded-For` | **空缺**（外层没做，边界见下文「限流自身的保护：IP 黑名单」） |
| 应用层入口（过滤器） | 反复触发限流的 IP 直接在过滤器层 429，不再往下走 | `BlacklistFilter`（本轮新增） |
| 应用层业务（切面 + Lua） | 按 GLOBAL / IP / USER 维度精确限次 | `SlidingWindowAspect` + `lua/sliding_window.lua` |

所以黑名单不是"替代限流"，而是**站在限流前面的准入层**：网关那一层空着，代价是每次被拒的请求仍然要走一次应用层 Redis 查询；只有真正进了黑名单的 IP 才是"连 Lua 都不跑"。

这两处不冲突：前者回答『业务限流为什么放在应用层』（网关只有 IP、拿不到登录身份与方法注解），后者回答『更外层的粗粒度入口为什么是空缺』。两层本可叠加——外层做 IP 粗封禁、应用层做业务维度限流。

**代价与收益**：

| 收益 | 代价 |
| --- | --- |
| 精确限次、没有边界双倍漏洞 | 每个受保护接口多一次 Redis 往返（ZSet 操作比计数器重） |
| 注解式：业务代码零侵入，加一个接口只需贴一个标签 | 阈值硬编码在注解上，**改阈值要改代码重新发版**（卡片里说的"配置表可热调"本项目**没做**，只有注解上的默认值） |
| 三维度覆盖：账号挡脚本、IP 挡单机 | ZSet 会存下窗口内的每个请求（本项目窗口只有 1 秒，量可控；窗口开大要评估内存） |

## 维度③ 流程（能画出来）

```
请求进来
  ↓
AOP 切面拦到带 @SlidingWindowLimit 的方法
  ↓
读注解：key / windowSeconds / maxRequests / dimension / message
  ↓
按维度取身份（全部取自服务端上下文）
  ├─ USER   → UserContext.userId()  （null → "anonymous"）
  ├─ IP     → UserContext.clientIp()，没有就从当前 HTTP 请求取真实 IP
  └─ GLOBAL → "global"
  ↓
拼 key：rate:seckill:USER:9003
  ↓
EVALSHA lua/sliding_window.lua
  KEYS = [key]
  ARGV = [当前毫秒时间戳, 窗口秒数, 最大请求数, traceId-UUID]
      ① ZREMRANGEBYSCORE  清掉窗口外的老请求
      ② ZCARD             数窗口内的请求数 → count >= max → return 0
      ③ ZADD + PEXPIRE    记下本次请求，并给 key 设过期
  ↓
  1 → 放行，继续执行方法体
  0 → 抛 429 业务异常（方法体一行都不会执行）
        └─ 全局异常处理器 → HTTP 429 + {code:429, message:"手速太快啦，歇一秒再抢"}

【Redis 异常时】
  redis.execute 抛异常 → catch → log.warn → return true（放行）  ← 降级放行
```

**分步说明**：

| 步骤 | 细节 | 为什么 |
| --- | --- | --- |
| 切面入口 | @Around("@annotation(com.flashmart.common.limiter.SlidingWindowLimit)") | 只拦贴了注解的方法，**没有任何业务代码被侵入** |
| 取身份 | 见上表 | **绝不信请求参数里的 userId** |
| 拼 key | `rate:{key}:{dimension}:{identity}` | 维度写在 key 里，同一个接口的不同维度互不干扰 |
| 生成成员 | `TraceUtil.current() + "-" + UUID.randomUUID()` | traceId 便于排查，UUID 保证**同毫秒并发不覆盖** |
| 执行脚本 | 三步原子完成 | 不原子就会"集体超发" |
| 结果处理 | 0 → `BizException.tooManyRequests(message)` | 429 是**真的 HTTP 429**（其他业务异常是 200 + code=400），前端能明确区分"被限流" |

## 维度④ 兜底

| 如果…… | 会怎样 | 靠什么兜住 |
| --- | --- | --- |
| **① Redis 不可用** | **放行**（注意日志里会打 warn） | `tryAcquire` 的 catch 返回 true。**理由**：限流是保护手段，**不能因为限流组件自己挂了把业务熔断**——宁可短暂超发 |
| **② 未登录接口（登录、注册）取不到用户身份** | 从当前 HTTP 请求取真实 IP：`X-Forwarded-For` 第一段 → `getRemoteAddr()` | ⚠️ 这个坑**踩过**：早期 `UserContext` 为空就落到 `unknown-ip`，结果是"**所有客户端的登录请求共用一个 20 次/秒的桶**"（等价于全局维度），**一个人刷就能把所有人挡住**。修复后实测：并发 30 次登录 → 通过 20 + 限流 10 |
| **③ 攻击者伪造身份** | 不可能：身份只从服务端上下文取 | 切面里没有任何一处读请求参数当身份 |
| **④ 同一毫秒内多个并发请求** | 不会互相覆盖 | ZSet 成员 = traceId + UUID，天然唯一 |
| **⑤ key 一直堆积、占内存** | 不会：`PEXPIRE` 把 key 的生命周期设成窗口长度，**没人访问就自动回收** | 不需要额外的清理任务 |
| **⑥ 阈值配错了** | 只能改代码 | ⚠️ **边界**：注解上的 `maxRequests` 是硬编码的，没有配置中心、没有热更新。运营想调阈值必须发版 |
| **⑦ 用户被限流了但不知道原因** | 429 带明确业务提示 `message`（"手速太快啦，歇一秒再抢"） | 前端 `api.js` 把后端原文抛出来显示成人话，不是白屏 |

## 限流自身的保护：IP 黑名单

> 限流保护的是**业务**，谁保护限流？被限流的请求每次仍要跑一遍 Lua + Redis，攻击者可以无限刷——所以限流之上加了一层按客户端 IP 的准入。

**怎么触发、怎么判定**：

| 环节 | 实现 | 为什么这么设计 |
| --- | --- | --- |
| 记违规 | 限流（滑动窗口）**拒绝一次 = 记一次违规**，`INCR black:violation:{ip}` | 口径是**客户端 IP**，不是分桶身份（这一点第一版写错过，见下面「钉住它的测试」） |
| 违规窗口 | **只在计数为 1 时 `EXPIRE` 60 秒** | 窗口从"第一次违规"起算，不会因为一直有流量被无限顺延 |
| 封禁 | 计数达到 **20** 次 → `SETEX black:list:{ip}` 300 秒，并 `DEL` 违规计数 | 到期自动解封、无人工干预；解封后重新计数 |
| 判定 | `isBanned(ip)`：Redis 里存在 `black:list:{ip}` 即封禁（fail-open） | 状态放 Redis 而不是本地内存——本地黑名单在多实例下只封得住自己那台 |
| 取 IP | `ClientIpResolver`：`X-Forwarded-For` 第一段 → `getRemoteAddr()` → 兜底 `unknown-ip` | **全项目唯一一份**取 IP 的实现，拦截器 / 限流切面 / 黑名单过滤器共用；三处各写一份就会出现"限流按 A 的 IP 判、黑名单按 B 的 IP 封" |

**为什么放在过滤器层**（不是切面、也不是塞进 Lua）：

| 理由 | 说明 |
| --- | --- |
| 越靠前拒绝越省 | `BlacklistFilter` 命中后写 429 响应并 `return`（不调 `chain`），所以**限流切面不执行、一次 Lua 都不跑** |
| 覆盖面不依赖注解 | 切面只拦贴了 `@SlidingWindowLimit` 的方法，过滤器拦的是整个 `/api/**` |
| 顺序有讲究 | `@Order(Ordered.HIGHEST_PRECEDENCE + 1)`，排在 `TraceIdFilter` 之后 → 拒绝日志**带得上 traceId** |
| 响应体刻意与限流一致 | HTTP 429 + `application/json;charset=UTF-8` + `{"code":429,"message":"访问过于频繁，已被临时限制，请稍后再试"}`，前端不用写第二套分支 |

**降级（fail-open）**：`BlacklistService` 与 `BlacklistFilter` 的判断整体 try/catch，异常只打 `log.warn` 然后放行——判断标准和限流那条完全一致（**放行错 vs 拒绝错，哪个更严重**）：黑名单是业务保护类，误拒正常用户的代价更大；换成支付风控、登录锁定这类安全场景，才应该 fail-close。如实说的后果：**Redis 不可用时黑名单与限流同时失效**，那段时间等于两层都没有。

**代价与边界**（主动说，不美化）：

| 边界 | 后果 | 根治方向 |
| --- | --- | --- |
| `X-Forwarded-For` 是客户端可伪造的请求头，而解析又优先读它 | 攻击者每次换一个伪造 IP，就绕开按 IP 的封禁与 IP 维度限流 | 最外层网关剥离外部 XFF 并写入可信头，应用只读可信头（部署层改动，本项目刻意未做） |
| 阈值 20 次 / 窗口 60 秒 / 封禁 300 秒是**策略值** | 没有任何真实流量调参依据，不是实测最优值 | 先"只观测不拦截"跑一段，按真实违规分布定阈值 |
| 惩罚落在 **IP** 上，不落在账号上 | USER 维度被限流时，同一 NAT 出口下的其它账号会被一起挡住 | 把检查点放到鉴权之后按 userId 封；账号维度的处置本项目由 Redis 会话失效承担 |
| 更外一层（网关限流 / 网关自动黑名单）没做 | 每次被拒的请求仍要跑一次 Redis 查询；只有真被封的 IP 才免掉 Lua | 网关做粗粒度 IP 封禁，应用层只做业务维度限流 |
| Redis 不可用 | 两个 key 都没了 → 黑名单与限流一起 fail-open | 与限流同一个取舍，不单独处理 |

**钉住它的测试与取证口子**：单元测试 `BlacklistServiceTest`（11 条：未达阈值不封且只在计数为 1 时设过期、达阈值即封并清计数、无效 IP 不碰 Redis、Redis 抛异常必须被吞掉、总开关关闭时零 Redis 访问）、`BlacklistFilterTest`（7 条：被封的 IP 直接 429 + 不调 chain、放行口径、客户端 IP 解析优先级）；端到端取证靠 `bench` profile 才注册的 `GET /api/bench/blacklist-stats?ip=`（返回 `limiterCalls` / `blacklistRejected` / `banned`）与 `POST /api/bench/blacklist/reset?ip=`。**实验已跑通**：封禁后同 IP 再打 10 次全部是黑名单 429，`limiterCalls` 增量为 0（一次限流 Lua 都没跑）；换对照 IP 打 3 次黑名单拒绝数为 0（按 IP 隔离）—— 数字见 `README.md` 实测数据表。

## 维度⑤ 实测产出

| 实验 | 配置 | 结果 |
| --- | --- | --- |
| **抢购接口突发** | 窗口 1 秒、每人最多 5 次（注解真实配置） | 同一用户 **1 秒内 10 并发 → 通过 5 次 + 429 共 5 次**（正好等于阈值） |
| **抢购接口匀速** | 同上 | 改成**每 1.2 秒 1 次**匀速请求 → **全部通过**（说明只拦突发、不拦正常用户） |
| **登录接口 IP 维度** | 窗口 1 秒、每 IP 最多 20 次 | 并发 **30 次登录 → 通过 20 + 限流 10** |

**这三组数在证明三件不同的事**：

| 实验 | 证明什么 |
| --- | --- |
| 10 并发 → 5 + 5 | **阈值精确生效**：正好卡在 5，没有多放一个（如果 Lua 不原子，很可能 10 个全过） |
| 1.2 秒匀速 → 全过 | **没有误伤正常用户**：限流限的是"突变"，不是"频率" |
| 登录 30 → 20 + 10 | **修复了"退化成全局限流"之后**才有的数字：IP 维度真的按 IP 分桶了（修复前所有人的登录请求共用一个桶） |

**必须主动说的边界**：同一批压测都在本机 Windows + Docker、客户端与服务同机；限流阈值是**注解里写死的**（1 秒 5 次 / 1 秒 20 次），不是从配置中心读的。

## 维度⑥ 方法论

**限流四要素，按顺序问清楚**：

| # | 要素 | 要问的问题 | 本项目的答案 |
| --- | --- | --- | --- |
| ① | **维度** | 限谁？用户 / IP / 接口 / 租户？ | 抢购按 **USER**（防单账号脚本刷）、登录按 **IP**（防撞库）；注解支持 **GLOBAL** |
| ② | **算法** | 允不允许突发？ | 抢购**不允许**预支突发额度 → 滑动窗口；如果是"允许用户手滑连点"的场景（比如 AI 对话），令牌桶更合适 |
| ③ | **阈值** | 定多少？ | 先看**正常用户的行为分布**，别拍脑袋：抢购 1 秒 5 次远高于真人手速，却能挡住脚本 |
| ④ | **降级** | 组件自己挂了怎么办、用户看到什么？ | **放行**（宁可能超发）+ 明确的人话提示 + 429 |

**再加两条工程习惯**：

| 习惯 | 为什么 |
| --- | --- |
| **身份必须来自服务端上下文** | 一旦从参数取身份，"限流"就变成了"给攻击者一个消耗别人额度的工具" |
| **未登录接口也要能定位到人（IP）** | 否则所有匿名请求挤进一个桶 → 限流退化成"第一个刷的人把所有人挡住" |

## 40 秒口述版

> "限流我用 **ZSet + Lua + AOP 注解**做滑动窗口：ZSet 的成员是请求时间戳，Lua 一次完成三步——先 `ZREMRANGEBYSCORE` 把窗口外的老请求清掉、再 `ZCARD` 数窗口内的数量、没超就 `ZADD` 记下本次请求并 `PEXPIRE` 设过期。**必须用 Lua**，不然两个并发请求会都统计到'没超'、双双放行。
> 为什么选滑动窗口而不是令牌桶：抢购要的是'**精确限次、不预支突发额度**'；令牌桶允许突发，而固定窗口有边界双倍流量的漏洞。这和我上一个项目正好相反——那个项目的 AI 接口要的恰恰是'允许突发'，所以用令牌桶。
> 用法上就是一个注解：抢购接口标 1 秒 5 次、用户维度；登录接口标 1 秒 20 次、IP 维度。
> 两个关键点：**身份一律取自服务端上下文**，绝不用请求参数，否则攻击者传别人的 ID 就能把别人的额度耗光；**未登录接口必须从当前 HTTP 请求取真实 IP**——这个坑我踩过，取不到 IP 就会退化成全局限流，一个人刷能把所有人挡住。
> 兜底是 **Redis 挂了就放行**：限流是保护手段，不能变成新的故障点。实测：1 秒内 10 并发 → 通过 5 + 429 共 5；改成 1.2 秒匀速 → 全部通过；登录并发 30 次 → 通过 20 + 限流 10。"

# 亮点⑥ RocketMQ 延迟消息超时关单

## 卡片原文（对照用）

> ① **是什么/怎么用**：下单成功后投一条**延迟消息**，到点仍未支付就关单并回滚库存。RocketMQ 只支持固定档位（1s/5s/10s/30s/1m…），按业务秒数取"最接近且不小于它"的档位
> ② **为什么这么选**：定时任务扫表要处理"扫哪些、扫多少、漏扫"，订单量大时扫描本身就很重；延迟消息到期自己回来，服务重启也不丢
> ③ **具体流程**：下单消费者写订单成功 → 投延迟消息（30 秒档）→ 到点消费者：查订单 → 条件更新 `PENDING_PAY → TIMEOUT` → 回滚数据库库存 + Redis 库存
> ④ **兜底**：关单只允许从"待支付"出发（已支付的不会被关）；关闭失败会走 MQ 重试；回滚带上限（不能超过活动总库存）
> ⑤ **实测产出**：订单 PENDING_PAY → TIMEOUT（轮询 22ms 内已关单），数据库与 Redis 库存**各回滚 1 件**；**该用户再抢会被"一人一单"拦下**（名额不退，库存退给池子）
> ⑥ **方法论**：时序任务四原则：**预约优于轮询、必须有兜底、兜底复用幂等主逻辑、执行前校验状态前置条件**

## 维度① 是什么 · 怎么用

| 卡片里的词 | 大白话 |
| --- | --- |
| **延迟消息** | 发出去之后**不会立刻被消费**，而是等到指定时间才投递给消费者的消息。"30 秒后叫我"——发的人不用等着 |
| **延迟档位** | RocketMQ **只支持固定的几档延迟**，不能指定任意秒数。本项目用的是 `1s / 5s / 10s / 30s / 1m / 2m / 3m / 4m / 5m / 6m / 7m / 8m / 9m / 10m / 20m / 30m / 1h / 2h` 共 18 档 |
| **nearestDelayLevel** | "**最接近且不小于**业务秒数"的档位换算方法。**举例**：业务要 30 秒 → 正好命中 30 秒档；业务要 7 秒 → 取 10 秒档（**宁晚不早**） |
| **超时关单** | 下单后不付款，到点把订单从"**待支付**"改成"**超时关闭**"，并把库存**退回池子** |
| **定时任务扫表** | 另一种常见做法：起一个定时任务，每隔几秒 `SELECT ... WHERE status='PENDING_PAY' AND create_time < NOW() - 30s` 捞一批出来关掉 |
| **预约 vs 轮询** | **预约** = "到点叫我"（延迟消息）；**轮询** = "我每隔一会儿去问一遍有没有要处理的"（扫表）。前者只在有订单时才有开销，后者是**恒定开销 + 空转** |
| **PENDING_PAY / TIMEOUT** | 订单状态机里的两个状态：待支付 → 超时关闭。（完整状态还有 `PAID` 已支付、`CANCELLED` 已取消） |
| **条件更新** | `UPDATE ... WHERE order_no=? AND status='PENDING_PAY'` ——**只有当前状态确实是"待支付"时才更新**，这一条同时保证了"不误关已支付的订单" |
| **回滚（库存）** | 关单成功之后，把这一件库存**还给池子**：数据库 `available_stock + 1`、Redis `seckill:stock:{id} + 1` |
| **回滚上限** | 回滚不能把库存加超总量：数据库侧带 `available_stock < total_stock` 条件，Redis 侧由 `rollback_stock.lua` 比对 `seckill:total:{id}` |
| **不再退还"机会"** | 关单**只退库存，不退这个用户的已购记录**——名额已经用掉，不付款就作废 |
| **force-timeout（压测接口）** | bench profile 下的调试接口：**按 1 秒档**投一条关单消息，用来快速验证关单与回滚（不然每验一次都要等 30 秒） |

**延迟档位换算的真实代码**（`MqProducer`）：

| 输入的业务秒数 | 换算结果 | 实际延迟 |
| --- | --- | --- |
| 订单超时 `flashmart.seckill.order-timeout-seconds: 30` | `nearestDelayLevel(30) = 4`（第 4 档） | **30 秒** |
| 延迟双删 `double-delete-delay-seconds: 5` | `nearestDelayLevel(5) = 2`（第 2 档） | **5 秒** |
| bench 的 `force-timeout` | 直接写死 level = 1 | **1 秒** |

**"最接近且不小于"是什么意思**：`DELAY_LEVEL_SECONDS = {1, 5, 10, 30, 60, 120, ...}`，方法从头扫到尾，**第一个 ≥ 目标秒数的档位**就是它。所以业务说 7 秒会拿到 10 秒档——**宁可晚一点关单，也不能早关**（早关会把还在支付的用户订单关掉，那是事故）。

**关单这条链路做了什么**（`OrderTimeoutConsumer` → `OrderService.timeoutOrder`）：

| # | 动作 | 代码 | 关键点 |
| --- | --- | --- | --- |
| ① | 幂等判重 | `idempotentRepository.tryAcquire(msgId, topic, keys)` | 和下单消费者用同一套幂等表 |
| ② | 查订单 | `findByOrderNo(orderNo)` | 订单不存在 → 记 warn 直接返回 false（**不抛异常**，因为"这单不存在"不是故障） |
| ③ | **条件更新** | `timeoutIfPending(orderNo)`：`UPDATE seckill_order SET status='TIMEOUT', cancel_time=NOW(), cancel_reason='TIMEOUT', version=version+1 WHERE order_no=? AND status='PENDING_PAY'` | 影响 **0 行** = 这单已经不是待支付（已支付 / 已取消）→ **跳过，且不回滚库存** |
| ④ | 回滚数据库库存 | `activityMapper.increaseStock(activityId)`：带 `WHERE available_stock < total_stock` | 上限保护 |
| ⑤ | 回滚 Redis 库存 | `stockService.rollbackStock(activityId)` | 走 `rollback_stock.lua`，比对 `seckill:total:{id}` 上限 |
| ⑥ | 标记成功 | `markSuccess(msgId)` | 失败则 `markFailed` + 抛异常 → MQ 阶梯重试 |

**注意 ③ 和 ④⑤ 的顺序**：**先确认关单成功，再回滚库存**。反过来的话，"已经支付了的订单"也会被退库存——那就是"扣了款还把货还回池子"的事故。

## 维度② 为什么这么选

**四种"到点做事"的方案对比**：

| 方案 | 怎么做 | 问题 |
| --- | --- | --- |
| **定时任务扫表** | `Scheduled` 每几秒扫一遍"待支付且已超时"的订单 | ❌ 要处理三件事：**扫哪些**（没索引就是全表扫）、**扫多少**（一次捞太多会打满内存/连接）、**漏扫**（扫描间隔与分页会漏）；而且**空转开销恒定**：没有超时订单时它照样在扫 |
| **Redis 过期 key 通知** | 监听 `__keyevent@0__:expired` | ❌ 过期通知是 **"尽力而为"** 的，Redis 不保证一定投递，丢了也不知道；而且只给 key 名，不给业务上下文 |
| **时间轮 / Quartz** | 自己实现调度 | ❌ 要自己做持久化与重启恢复；**为了一个"30 秒后关单"引入一套调度系统不划算** |
| **RocketMQ 延迟消息** ✅ | 下单成功时投一条，到点自己回来 | ✅ 消息**可持久化**、服务重启不丢、自带重试与死信；用的是**已经在用的中间件**，零新增组件 |

**"预约"和"轮询"的成本对比（面试可以直接这么讲）**：

| | 定时任务扫表 | 延迟消息 |
| --- | --- | --- |
| 待支付订单很多时 | **每一轮都要把它们全部扫一遍** | 每条消息各自在档位上等着，**不占业务资源**（没有消息就没有消费） |
| 没有待支付订单时 | **照样空转**（每 N 秒一次查询） | **零开销**（没有消息就没有消费） |
| 服务重启 | 重启期间没扫到的会延迟处理 | Broker 里的消息**还在**，消费者起来继续消费 |
| 提前/延后 | 精度取决于扫描间隔（通常秒级到分钟级） | 精度取决于**档位**（本项目 30 秒档，实际就是 30 秒左右） |

**代价与收益**：

| 收益 | 代价 |
| --- | --- |
| 零新增组件：复用 RocketMQ 的持久化、重试、死信 | **延迟时间只能取固定档位**：所以配置项直接写成"秒"（`order-timeout-seconds: 30`、`double-delete-delay-seconds: 5`），并明确"实际生效值 = 命中档位的值" |
| 服务重启不丢、可重试 | 延迟消息如果在发送时丢了，**这一单永远不会被自动关掉**（本项目没有"定时补关单"的对账兜底——明确边界） |
| 关单逻辑就是普通消费者，复用幂等表 | 关单精度受档位限制（要 7 秒只能拿 10 秒档） |

## 维度③ 流程（能画出来）

```
【下单成功后，顺手预约一次"30 秒后检查"】
OrderCreateConsumer
  ↓ 写订单成功（状态 PENDING_PAY）
  ↓ sendAsync(topic_order_timeout, key = order:{orderNo},
              payload = OrderTimeoutEvent(orderNo),
              delayLevel = nearestDelayLevel(orderService.timeoutSeconds()) = 4 → 30 秒)
  ↓ markSuccess
返回（消费者这一轮就结束了，不阻塞、不占线程）

        …… 30 秒 ……（消息睡在 Broker 的档位里）

【到点回来】
topic_order_timeout（消费组 cg_order_timeout，32 线程）
  ↓ ① 幂等表 tryAcquire(msgId)
  ↓ ② 查订单 findOrderByNo
  │      不存在 → log.warn + return false（不抛异常）
  ↓ ③ 条件更新 timeoutIfPending：
  │      UPDATE seckill_order SET status='TIMEOUT', cancel_time=NOW(),
  │             cancel_reason='TIMEOUT', version=version+1
  │      WHERE order_no=? AND status='PENDING_PAY'
  │        影响 0 行 → 已经支付/已取消 → 跳过，不回滚库存（log.info）
  │        影响 1 行 → 继续
  ↓ ④ 回滚数据库库存 increaseStock（WHERE available_stock < total_stock）
  ↓ ⑤ 回滚 Redis 库存 rollbackStock（rollback_stock.lua，比对 seckill:total:{id}）
  ↓ ⑥ markSuccess
  │
  └─ ★ 注意：这里【没有】回滚 seckill:bought:{activityId} 里这个用户的已购记录
            名额已经用掉，不付款就作废；库存退回池子给其他人抢

【前端看到什么】
轮询 /api/seckill/result/{orderNo} → state 从 PENDING_PAY 变成 TIMEOUT
```

**分步说明**：

| 步骤 | 为什么这么做 | 出问题会怎样 |
| --- | --- | --- |
| 投递时机 | **必须在下单成功之后投**——订单都没落库，关单消息无从下手 | 发送失败 → 同步重发一次；再失败只有日志（边界） |
| 档位换算 | 用"最接近且不小于"，**宁晚不早** | 早关单会关掉正在支付的订单，是事故 |
| ② 查订单 | 订单不存在说明消息对应的订单没了（比如压测重置删了） | 直接跳过，**不抛异常**（不是故障，别让它进重试/死信） |
| ③ 条件更新 | **只允许从 `PENDING_PAY` 出发** | 影响 0 行 → 说明支付赢了这一局，跳过 |
| ④⑤ 回滚库存 | 只有在 ③ 成功后才执行 | 顺序反了 → 已支付的订单也会被退库存 |
| ④ 的上限 | 数据库侧带 `available_stock < total_stock` | 在途消息重复回滚不会把库存加超 |
| ⑤ 的上限 | Redis 侧 `rollback_stock.lua` 比对 `seckill:total:{id}` | 两边口径一致（这是踩过坑之后补的） |
| ⑥ 幂等 | 关单消息重复投递也没关系 | 第二次进来时 ③ 影响 0 行（已经是 TIMEOUT），**天然幂等** |

## 维度④ 兜底

| 如果…… | 会怎样 | 靠什么兜住 |
| --- | --- | --- |
| **① 用户在关单前一刻支付成功了** | 订单**不会被关掉** | 关单是条件更新（`WHERE status='PENDING_PAY'`），影响 0 行 → 跳过，**库存也不会被回滚** |
| **② 关单消息重复投递** | 第二次什么也不做 | 幂等表拦一遍；即使漏过去，条件更新也影响 0 行（已经是 TIMEOUT）——**双层幂等** |
| **③ 关单时数据库抖了一下** | 抛异常 | `markFailed` + 抛出去 → **MQ 阶梯重试**；重试时幂等表把 FAILED 的消息放行 |
| **④ 在途的关单消息比压测重置还晚到** | 库存不会被加超 | 数据库 `available_stock < total_stock` + Redis `rollback_stock.lua` 上限 |
| **⑤ 关单消息本身丢了** | ⚠️ **这一单会一直停在待支付** | **没有兜住**——本项目**没有"定时补关单"的对账任务**。这是明确边界：延迟消息丢失是低概率事件，但一旦发生，只能靠人工或后续补一个扫表兜底 |
| **⑥ 用户问"我的名额还在吗"** | **不在了**（再抢会被"每人限购 1 件"拦下） | 这是**设计如此**：名额是一次性机会，不付款就作废。否则用户可以"抢了不付 → 等关单 → 再抢"，**零成本锁库存** |
| **⑦ 订单在关单前被用户主动取消** | `status = CANCELLED` | ⚠️ **未实现**：`STATUS_CANCELLED` 和 `cancel_reason='CANCELLED'` 在表结构里预留了，但**没有取消接口**，也没有取消后回滚库存的路径 |

## 维度⑤ 实测产出

| 实验 | 做法 | 结果 |
| --- | --- | --- |
| **超时关单 + 库存回滚** | 走真实 `/api/seckill` 链路抢 1 次 → 轮询到 `PENDING_PAY` → **不支付** → 延迟消息到点 → 查订单状态与两侧库存 | 订单 `PENDING_PAY → TIMEOUT`（**轮询 22ms 内已看到 TIMEOUT**）；**数据库与 Redis 库存各回滚 1 件** |
| **名额不退（关键补充验证）** | 关单之后，**同一个用户再抢一次** | 被「**每人限购 1 件，你已经抢到啦**」拦下 → 证明"**库存退回了池子、但这个人的名额已经用掉**" |
| **已支付的不会被误关**（验收清单里的手工验证项，不是压测数字） | 抢购后**立刻支付**，再用 bench 的 `force-timeout` 触发关单 | 订单仍是 `PAID`，条件更新影响 0 行，**库存不回滚** |

**口径说明（这句话必须自己说清楚，别让面试官问出来）**：

> "**30 秒**是生产配置的档位（`order-timeout-seconds: 30` → `nearestDelayLevel(30)` = 第 4 档 = 30 秒），手工验收就是"抢一单、不支付、**等 30 秒**看状态变 TIMEOUT"。
> 而**压测工具里的 timeout 实验走的是 bench 的 `force-timeout` 接口，它按 1 秒档投递关单消息**——不然每验证一次都要等 30 秒。所以"**轮询 22ms 内看到 TIMEOUT**"这个观察值，出自**关单消息到点之后、下一次轮询的响应时间**这个口径；**30 秒档只是把"到点"这件事推迟了，关单本身还是同一条 OrderService.timeoutOrder 代码路径**。"

**必须主动说的环境边界**：本机 Windows + Docker、客户端与服务同机；两条数（各回滚 1 件）是用压测工具的断言语句**直接校验增量等于 1** 的，不是肉眼看的。

## 维度⑥ 方法论

**时序任务四原则**：

| # | 原则 | 为什么 | 本项目怎么落 |
| --- | --- | --- | --- |
| ① | **预约优于轮询** | 轮询有恒定空转成本，还要处理"扫哪些、扫多少、漏扫"；预约只在有事时才有开销 | RocketMQ 延迟消息（30 秒档） |
| ② | **必须有兜底** | 消息会丢、"到点"可能没到 | ⚠️ 本项目**只有重试（MQ 阶梯）+ 幂等，没有"定时补关单"的对账兜底**——正解是再加一个低频扫表任务，只扫"逾期很久还在待支付"的订单当安全网 |
| ③ | **兜底要复用幂等的主逻辑** | 兜底路径与主路径用两套代码，就会出现"两条路径行为不一致"的新 bug | 如果以后补扫表，应该**直接调同一个 `timeoutOrder(orderNo)`**，而不是另写一段 UPDATE |
| ④ | **执行前校验状态前置条件** | 到点执行的那一刻，前提可能已经不成立了（用户已经支付） | `WHERE status='PENDING_PAY'` —— **让数据库来判决**，而不是在代码里 if 一下 |

**再加一条本项目特有的原则**：

| 原则 | 说明 |
| --- | --- |
| **⑤ 回滚前先确认"这次变更真的发生了"** | 关单影响 0 行就**不许回滚库存**。顺序错一步，就是"钱收了、货退回池子"的事故 |

## 40 秒口述版

> "超时关单我没用定时任务扫表，而是用 **RocketMQ 延迟消息**：下单成功之后立刻投一条延迟消息，到点自己回来触发关单。
> 为什么不用扫表：扫表要处理'扫哪些、扫多少、漏扫'三个问题，订单量大时扫描本身就很重，而且没订单的时候它照样在空转；延迟消息到期自己回来，服务重启也不丢。
> 有个细节：**RocketMQ 只支持固定档位**（1s/5s/10s/30s/1m…），所以我写了一个'取最接近且不小于业务秒数'的档位换算——业务配 30 秒就命中 30 秒档。**宁可晚关，不能早关**。
> 关单本身是**条件更新**：`WHERE status='PENDING_PAY'`，所以**已经支付的订单不会被误关、更不会被误回滚库存**；影响 0 行就跳过。关单成功之后才回滚库存，数据库和 Redis 两边**各带一个不能超过总库存的上限**。
> 还有一个语义我特意设计的：**关单只退库存、不退这个用户的抢购机会**——名额用掉就作废，库存退回池子给别人。否则用户可以'抢了不付、关单后再抢'，零成本锁库存。实测关单后两侧库存各 +1，**该用户再抢会被'每人限购 1 件'拦下**。"

# 亮点⑦ 乐观锁解决支付回调与关单并发

## 卡片原文（对照用）

> ① **是什么/怎么用**：`UPDATE ... SET status='PAID', version=version+1 WHERE order_no=? AND status='PENDING_PAY' AND version=?` ——只允许从"待支付"出发，且校验版本号；返回 0 行说明状态已被别人改过
> ② **为什么这么选**：冲突概率极低（只有支付回调与关单会同时碰同一单），临界区只改一行，用悲观锁/分布式锁成本过高；**条件更新本身就能表达业务规则**：不是待支付就不许改
> ③ **具体流程**：支付：查订单 → 校验归属与状态 → 条件更新（返 0 行就提示"订单状态已变化，请刷新"）；关单：同样条件更新，返 0 行说明已支付/已取消，直接跳过
> ④ **兜底**：支付幂等（已支付直接返回成功，不重复扣款）；关单成功才回滚库存，避免"已支付却被退款"
> ⑤ **实测产出**：两次支付都返回 PAID，第二次提示"订单已支付，无需重复支付"；关单后再支付会被拒绝（订单已关闭）
> ⑥ **方法论**：状态机四原则：**先定状态与允许的流转 → 每次更新都带前置条件 → 幂等设计 → 并发冲突交给数据库的条件更新判决**

## 维度① 是什么 · 怎么用

| 卡片里的词 | 大白话 |
| --- | --- |
| **乐观锁** | **假设冲突很少发生**，所以不加锁；只在**更新的时候**检查"我读到的东西有没有被别人改过"，改过就放弃这一次更新 |
| **version（版本号）** | 订单表上的一个整数列，**每次更新 +1**。读取时连着 version 一起读出来，写回时拿它当"凭据" |
| **条件更新** | 把"**允许在什么状态下更新**"直接写进 SQL 的 `WHERE` 里。数据库来判决，而不是应用层先用 `if` 判断 |
| **返回 0 行** | `UPDATE` 的影响行数是 0 = **条件不满足 = 这个世界在我读完之后变了**。这就是乐观锁的"失败信号" |
| **支付回调** | 支付网关在用户付款成功后回调我的接口（本项目是**模拟**的：直接调 `/api/order/pay` 触发同一段状态流转逻辑） |
| **状态机** | 订单的状态以及"允许怎么流转"：`PENDING_PAY → PAID`（支付成功）、`PENDING_PAY → TIMEOUT`（超时关单） |
| **前置条件** | 每一次更新都必须写清的"我允许从哪个状态出发" |
| **幂等** | 同一个操作执行多次，结果和执行一次一样。这里的表现是：**重复支付不重复扣款** |
| **悲观锁** | 先锁住这一行（`SELECT ... FOR UPDATE` 或分布式锁），别人等着，我改完再放开 |

**两条 SQL（真实代码，`SeckillOrderMapper`）**：

```sql
-- 支付：只允许从"待支付"出发，并且校验我读到的版本号
UPDATE seckill_order
   SET status = 'PAID', pay_trade_no = ?, pay_time = NOW(),
       version = version + 1, update_time = NOW()
 WHERE order_no = ? AND status = 'PENDING_PAY' AND version = ?

-- 超时关单：同样只允许从"待支付"出发（不带 version，靠 status 的原子性判定）
UPDATE seckill_order
   SET status = 'TIMEOUT', cancel_time = NOW(), cancel_reason = 'TIMEOUT',
       version = version + 1, update_time = NOW()
 WHERE order_no = ? AND status = 'PENDING_PAY'
```

**支付接口的完整分支**（`OrderService.pay`）：

| # | 判断 | 结果 |
| --- | --- | --- |
| ① | 订单不存在 | 抛"订单不存在或还在生成中，请稍后重试" |
| ② | 订单不是本人的 | 403「无权操作该订单」 |
| ③ | **状态已经是 `PAID`** | **直接返回成功**，message = "订单已支付，无需重复支付"（**幂等，不重复扣款**） |
| ④ | 状态不是 `PENDING_PAY`（比如已 TIMEOUT） | 抛"订单已关闭（TIMEOUT），无法支付" |
| ⑤ | 条件更新影响 0 行 | 抛"**订单状态已变化，请刷新后查看**"——说明读完订单到写这一瞬间，状态被别人改了（多半是关单抢先了） |
| ⑥ | 影响 1 行 | 返回 `status = PAID`，message = "支付成功"，并记下 `tradeNo` |

**③ 和 ⑤ 的关系要讲清楚**（这是最容易被追问的点）：

> ③ 是"**我读的时候就已经是已支付**"——这是**重复支付**，直接幂等返回；
> ⑤ 是"**我读的时候还是待支付，写的时候已经不是了**"——这是**并发对撞**，乐观锁把它挡住了。
> **两者提示语不同、处理方式也不同**，前者是正常业务（用户手滑点了两次），后者是并发冲突（要么刷新重试、要么就已经被关单了）。

## 维度② 为什么这么选

**三种并发控制方案对比**：

| 方案 | 怎么做 | 本项目的判断 |
| --- | --- | --- |
| **悲观锁**（`SELECT ... FOR UPDATE`） | 读的时候就把行锁住，别人等着 | ❌ **成本过高**：持锁期间占着数据库连接（连接池只有 20 个），而这个临界区其实**只改一行、冲突概率极低** |
| **分布式锁**（Redis `SETNX` / Redisson） | 用 Redis 锁把"查订单 → 改状态"串行化 | ❌ 为一个"极低概率的冲突"引入一次 Redis 往返 + 锁失效风险 + 要处理续期，不划算 |
| **乐观锁 + 条件更新** ✅ | 不加锁，更新时用 `WHERE` 判定 | ✅ **代价只有 SQL 里的两个条件**；冲突时返回 0 行，业务代码把它翻译成一句人话 |

**为什么"条件更新"比"先 if 判断再 update"更好**：

| 写法 | 问题 |
| --- | --- |
| `if (order.getStatus().equals(PENDING_PAY)) { update(...); }` | 判断和写入之间**有缝隙**：判断完之后、写入之前，状态可能被关单改了 → **两个线程都通过判断**，一个改成 PAID、一个改成 TIMEOUT，最后谁赢看运气 |
| `UPDATE ... WHERE status='PENDING_PAY'` ✅ | 判断和写入**是同一条 SQL**，由数据库在行锁保护下原子完成 → **只有一方能成功** |

**卡片里那句"条件更新本身就能表达业务规则"**是本条亮点的核心：

> "`WHERE status='PENDING_PAY'` 这半句，本身就是业务规则——**不是待支付就不许改**。它不需要在应用层再写一遍 if，也不会因为哪条路径忘了判断而出错。**把业务规则下沉到数据层，是最不容易被绕过的一种写法。**"

**代价与收益**：

| 收益 | 代价 |
| --- | --- |
| 无锁、无等待、不占连接；一行 SQL 搞定 | 冲突时**要重试或提示用户**（本项目选择提示"请刷新"，因为这是真实的状态变化，不是瞬时抖动） |
| 业务规则（只允许从待支付出发）由数据库强制执行 | 条件写错就静默失败（返回 0 行但没抛异常）——所以**每次都必须检查影响行数** |
| 和"关单"用的是同一种模式，两条路径对称、好理解 | 需要应用层把"0 行"翻译成人话，否则用户看到的是"什么都没发生" |

## 维度③ 流程（能画出来）

```
        t0             t1                        t2
用户A   │ 支付请求 ──→ 读订单（PENDING_PAY, version=0）
用户B   │                      关单消息到点 ──→ 读订单（PENDING_PAY, version=0）
        │
        │  ┌─────────── 同一毫秒，两条 UPDATE 同时发出 ───────────┐
        │  │                                                     │
        │  ▼                                                     ▼
        │  UPDATE ... SET PAID   version=version+1        UPDATE ... SET TIMEOUT   version=version+1
        │  WHERE order_no=? AND status='PENDING_PAY'      WHERE order_no=? AND status='PENDING_PAY'
        │        AND version=0
        │  │                                                     │
        │  └──────────────► 数据库行锁串行执行 ◄─────────────────┘
        │                          │
        │              ┌───────────┴───────────┐
        │              ▼                       ▼
        │        先执行的那条            后执行的那条
        │        影响 1 行 ✅            影响 0 行 ❌（status 已不是 PENDING_PAY，
        │        状态真的变了             或者 version 对不上了）
        │              │                       │
        │              ▼                       ▼
        │        支付成功 → PAID          支付：抛「订单状态已变化，请刷新后查看」
        │        或 关单成功 → TIMEOUT     关单：log.info 跳过，【不回滚库存】
        │                                                        │
        └────────────────────────────────────────────────────────┘
                结果：只有一方生效，库存不会被错误回滚
```

**分步说明**：

| 阶段 | 支付链路 | 关单链路 |
| --- | --- | --- |
| 读 | 查订单、校验归属、判断当前状态 | 查订单（不存在就 warn 返回） |
| 写 | `payWithVersion(orderNo, tradeNo, version)`（status + version 双条件） | `timeoutIfPending(orderNo)`（status 单条件） |
| 影响 0 行 | 抛"订单状态已变化，请刷新后查看" | log.info 跳过，**不回滚库存** |
| 影响 1 行 | 写 `pay_trade_no` / `pay_time`，version + 1 | 写 `cancel_time` / `cancel_reason='TIMEOUT'`，version + 1，**然后才**回滚两侧库存 |

**为什么关单那条不带 version**：关单的语义是"**到点了，如果还没付就关掉**"——它不关心自己读到的是哪个版本（那个 version 可能已经是很久以前读的），它只关心"**此刻是不是还没付**"。而 `status='PENDING_PAY'` 是一个**原子的条件判断**，已经足够。支付那条带 version 是因为支付是"**基于我看到的那份订单**"做的动作，带上版本更严格（既防状态变化、也防同一订单的两次并发支付）。

## 维度④ 兜底

| 如果…… | 会怎样 | 靠什么兜住 |
| --- | --- | --- |
| **① 用户重复点支付** | 第二次不重复扣款 | `pay` 读到状态已经是 `PAID` → **直接返回成功** + message "订单已支付，无需重复支付" |
| **② 两个支付请求真的同时到达** | 只有一方能改 | `WHERE ... AND version=?` 双条件；第二个影响 0 行 → "订单状态已变化，请刷新后查看" |
| **③ 支付与关单同时到达** | 只有一方生效 | 两条 SQL 都带 `status='PENDING_PAY'`，数据库行锁串行执行 |
| **④ 关单抢在支付前面成功了** | 支付被拒（"订单已关闭（TIMEOUT），无法支付"），**而且库存已经被正确回滚了** | 关单成功后回滚库存；支付影响 0 行 → 不会出现"付了钱却被退库存" |
| **⑤ 支付抢在关单前面成功了** | 关单**跳过，且不回滚库存** | `timeoutIfPending` 影响 0 行 → `timeoutOrder` 直接 return false，**根本不执行回滚那两行** |
| **⑥ 别人拿我的订单号来支付 / 查询** | 403 | 两个入口都校验 `userId.equals(order.getUserId())`（`OrderService.detailOfMine` 与 `pay`） |
| **⑦ 订单状态卡在奇怪的值** | 明确报错，不会静默 | `pay` 里"既不是 PAID 也不是 PENDING_PAY"→ 抛"订单已关闭（状态），无法支付" |
| **⑧ 支付与关单"同一毫秒对撞"** | ⚠️ **未实测** | 已经验证的是"两条路径各自走到正确终态、且互不干扰"（支付后订单保住 PAID 且库存不动；不支付的订单超时并回滚库存）。**要精确压这个对撞，需要在服务端加可控的时序开关、在客户端用栅栏让两个动作尽量同时发出——这个实验我没做**，如实说 |

**主动说的边界**（这段背下来，比被问出来好）：

> "**我没有构造'支付与关单在同一毫秒对撞'的实验，这是未实测的**。我验证过的是两条路径各自的终态正确、并且互不污染：支付之后订单保住 PAID、库存不回滚；不支付则超时关单、库存回滚。另外我还**手工验证过一条**：抢购后立刻支付、再用 bench 的 `force-timeout` 触发关单，订单仍然是 PAID、条件更新影响 0 行、库存不回滚——**这就是'已支付不会被误关'的直接证据**。"

## 维度⑤ 实测产出

| 实验 | 做法 | 结果 |
| --- | --- | --- |
| **支付 + 重复支付幂等** | 抢购 → 轮询到 `PENDING_PAY` → 支付 → **再支付一次** | **两次都返回 `PAID`**；第二次 message = "**订单已支付，无需重复支付**"（不重复扣款） |
| **关单后再支付** | 抢购后不支付 → 等关单 → 再调支付 | **被拒绝**（订单已关闭），说明状态机的前置条件真的在拦 |
| **已支付不会被误关**（验收清单里的手工验证项，不是压测数字） | 抢购后立刻支付 → 用 `force-timeout` 触发关单 | 订单仍是 `PAID`，条件更新影响 0 行，**库存不回滚** |
| **支付与关单同一毫秒对撞** | —— | ❌ **未实测**（见维度④ 边界） |

**这三个数/结论在证明什么**：

| 观察 | 证明 |
| --- | --- |
| 两次支付都 `PAID`、第二次带明确提示 | **幂等生效**：这是"重复支付不会重复扣款"的直接证据（真实项目里对接的是钱，这一条最重要） |
| 关单后再支付被拒 | **状态前置条件生效**：不是"待支付"就改不了 |
| 已支付 + 关单消息 → 仍是 PAID 且库存不动 | **顺序与判定正确**：条件更新影响 0 行时**没有执行回滚**，所以不存在"收了钱还把货退回池子" |

## 维度⑥ 方法论

**状态机四原则**：

| # | 原则 | 一句话理由 | 本项目怎么落 |
| --- | --- | --- | --- |
| ① | **先定状态与允许的流转** | 状态机的价值在于"**没有定义过的流转就是不允许的**" | `PENDING_PAY` / `PAID` / `TIMEOUT`（+ 预留的 `CANCELLED`）；允许 `PENDING_PAY→PAID`、`PENDING_PAY→TIMEOUT` |
| ② | **每次更新都带前置条件** | 判断与写入之间有缝隙，条件必须和写入在同一条 SQL 里 | 两条 SQL 都带 `WHERE status='PENDING_PAY'` |
| ③ | **幂等设计** | 支付回调会重复送达，用户也会重复点 | 已是 `PAID` 就直接返回成功，不重复扣款 |
| ④ | **并发冲突交给数据库的条件更新判决** | 应用层的 if 会被并发绕过；数据库的行锁不会 | 影响行数 0 / 1 就是判决结果，业务代码只负责翻译成人话 |

**再加两条工程习惯**：

| 习惯 | 为什么 |
| --- | --- |
| **每次条件更新都必须检查影响行数** | 条件不满足时数据库**不会报错**，只会静默返回 0 行；不检查就等于"改了但没生效，而且没人知道" |
| **"先确认变更成功，再做副作用"** | 关单先确认更新成功、再回滚库存；反了就是"没有关单却退了库存" |

## 40 秒口述版

> "支付回调和超时关单可能同时改同一张订单，我用**乐观锁加状态前置条件**解决：支付那条 SQL 是 `UPDATE ... SET status='PAID', version=version+1 WHERE order_no=? AND status='PENDING_PAY' AND version=?`，**返回 0 行就说明这一瞬间状态已经被别人改过了**——多半是关单抢先了，这时我提示'订单状态已变化，请刷新后查看'。关单用的是同样的条件更新，只允许从'待支付'出发，**影响 0 行就直接跳过，而且不回滚库存**，所以不可能出现'已经支付了却被关单退回库存'。
> 为什么不用悲观锁或分布式锁：这里的**冲突概率极低**（只有支付回调和关单会同时碰同一单），临界区**只改一行**，加锁的成本远大于收益；更重要的是——**条件更新这半句 `WHERE status='PENDING_PAY'` 本身就在表达业务规则**：不是待支付就不许改。判断和写入在同一条 SQL 里，应用层的并发绕不过数据库的行锁。
> 另外支付做了幂等：**已经支付过就直接返回成功**、不重复扣款。实测两次支付都返回 `PAID`，第二次的提示是'订单已支付，无需重复支付'；关单之后再支付会被拒绝。
> 一个边界我会主动说：**支付与关单在同一毫秒对撞的实验我没有做，这是未实测的**；我验证的是两条路径各自的终态正确、而且互不污染。"

# 术语速查

> 用法：看正文时碰到不认识的词，回到这里查一行。**一行看不懂就再往下翻，下面按主题分了组。**

## Redis 与 Lua

| 词 | 一句话解释 |
| --- | --- |
| **Lua** | Redis 内置支持的一门小脚本语言；本项目用它把"多条 Redis 命令"打包成"一次调用" |
| **原子执行 / 原子性** | 这段操作**中间不会被别的请求插进来**。Redis 处理命令是单线程的，一整段脚本会被当成一条命令跑完 |
| **EVALSHA** | 按脚本的 SHA1 摘要执行**已经缓存过的脚本**。脚本第一次执行后 Redis 会缓存起来，之后不用每次传体 |
| **KEYS / ARGV** | 脚本的两个入参通道：`KEYS` 传"要操作哪些 key"，`ARGV` 传普通参数 |
| **DECR / INCR** | 把 key 的值当整数 **-1 / +1**，是 Redis 的原子命令 |
| **Hash** | 一个 key 下面挂很多"字段 → 值"。本项目用来存 `userId → 已购数量` |
| **HGET / HINCRBY** | Hash 的"读一个字段" / "把某个字段加 N"。`HINCRBY` 是原子的 |
| **ZSet（有序集合）** | 每个成员带一个分数、**自动按分数排序**的集合。本项目把**请求时间戳当分数**，用来做滑动窗口 |
| **ZADD / ZCARD / ZREMRANGEBYSCORE** | 加成员 / 数成员个数 / **按分数范围批量删成员**（限流里 = 清掉窗口外的老请求） |
| **SETNX** | `SET key value NX`，"**不存在才设置**"。本项目用它当"简易互斥锁"（缓存重建、库存预热、回滚去重） |
| **TTL / PEXPIRE** | key 的存活时间（秒 / 毫秒）。到点 Redis 自动删掉它 |
| **预热** | 把数据库里的数据**提前抄一份到 Redis**，让后面的读/扣减发生在 Redis 里 |
| **回源** | 缓存没命中 → **回到数据库查一次**。所有缓存指标看的都是"回源次数" |

## 缓存

| 词 | 一句话解释 |
| --- | --- |
| **Cache Aside** | 缓存一致性的经典写法：读未命中就回源并写回缓存；写的时候**先更新数据库、再删缓存** |
| **逻辑过期** | 缓存值里**额外存一个过期时间**（`expireAt`），到点**不删 key**，只是请求发现"逻辑过期了"就先返回旧值、再让后台去重建 |
| **物理 TTL** | Redis 里那个 key **真正**的过期时间。本项目设成逻辑 TTL 的 **3 倍**，保证逻辑过期后旧值还在 |
| **空值缓存 / `__NULL__`** | 回源发现"数据库里确实没有"时写进缓存的**空值标记**（TTL 30 秒），用来挡住反复穿透 |
| **缓存穿透** | 查的东西**数据库里也不存在**，缓存永远不命中 → 每次请求都白跑一趟库 |
| **缓存击穿** | 某个**热点 key 在一瞬间失效** → N 个并发同时扑向数据库 |
| **缓存雪崩** | **大量 key 在同一时刻集体过期** → 数据库被全量回源砸中 |
| **回填** | 读路径把数据库查出来的值**写进缓存**这个动作 |
| **延迟双删** | 更新库后删一次缓存，**延迟 5 秒再删一次**，专门清掉"并发读在第一次删之后才回填的旧值" |
| **补偿任务** | 删缓存失败时落到 `cache_sync_task` 表里的**持久化待办记录**（PENDING → SUCCESS/FAILED，`retry_count` 累加） |
| **最终一致** | 允许中间有一小段时间不一致，但**最终会一致**。本项目接受的就是这个语义 |
| **对账** | 定时把两份数据拉出来比对、修正不一致。**本项目没做**（明确边界） |

## 消息队列

| 词 | 一句话解释 |
| --- | --- |
| **削峰** | 把某一瞬间涌进来的请求**摊平成队列**，让数据库只面对"消费速度"而不是"点击速度" |
| **尖峰 / 平稳** | **尖峰** = 某一刻流量是平时的几十倍（开抢那一秒）；**平稳** = 长期稳定。削峰只对尖峰有意义 |
| **Topic** | 消息的**频道名**，按业务分类：下单 / 超时关单 / 缓存补偿各一条 |
| **消费组（consumerGroup）** | 干同一件事的一群实例；**同一条消息在同一个组里只会被一个实例处理** → 加实例就能提速 |
| **ACK** | "签收"：告诉 MQ 这条消息我处理完了。不签收（抛异常）MQ 就会重投 |
| **阶梯重试** | 消费失败后 MQ 按**越来越长的间隔**自动重投（不是立刻重试、也不是无限重试） |
| **DLQ / 死信队列** | 重试到上限还失败的消息进"问题件仓库"。本项目会进 RocketMQ 按消费组自动建的 `%DLQ%cg_order_create`，**但没有消费者和重放接口，只能去 Dashboard 人工看**（边界） |
| **延迟消息** | 发出去之后**等到指定时间才被消费**的消息。超时关单用它 |
| **延迟档位** | RocketMQ **只支持固定几档延迟**（1s/5s/10s/30s/1m…共 18 档），不能指定任意秒数 |
| **traceId** | 一次请求的跟踪号。入口生成、塞进消息属性带到消费者，**三段日志能被同一个 ID 串起来** |
| **幂等** | 同一个操作执行多次，结果和执行一次一样（重复支付不重复扣款、重复消息不重复落单） |
| **幂等表** | `mq_consume_log`：`msg_id` 唯一索引，**插入成功 = 第一次消费** |
| **本地消息表** | "把业务数据和待发消息写进同一个事务，再定时补发"的做法。**本项目没有做**（明确边界） |
| **顺序消息** | 让同一业务键的消息固定进同一个队列、串行消费。本项目**不需要顺序**（消息只带业务主键，消费端回查数据库） |

## 限流

| 词 | 一句话解释 |
| --- | --- |
| **固定窗口** | 每个自然秒一个计数器，满了拒绝、下一秒清零。**缺点：边界处能过 2 倍流量** |
| **滑动窗口** | 统计"**最近 N 秒内**有多少请求"（存时间戳）。本项目用的就是它 |
| **令牌桶** | 按固定速率往桶里发令牌，请求来领券。**允许突发**（桶里攒着额度）。上一个项目的 AI 接口用的就是它 |
| **漏桶** | 请求进桶、按固定速率流出，流量最平滑，但**一点突发都不允许** |
| **限流维度** | 按什么限：`GLOBAL`（整个接口）/ `IP`（客户端）/ `USER`（登录用户） |
| **429** | HTTP 的 "Too Many Requests"。本项目对限流**真的返回 HTTP 429**（其他业务异常是 HTTP 200 + code=400） |
| **降级放行** | 限流组件（Redis）自己挂了的时候**选择放行**——宁可能超发，也不能把业务全部熔断 |
| **AOP / 切面 / 注解** | 在方法上贴一个标签（@`SlidingWindowLimit`），切面在方法执行前自动做限流，**业务代码零侵入** |

## 并发与数据

| 词 | 一句话解释 |
| --- | --- |
| **临界区** | 多个线程/进程都会去改的那一段代码或那几行数据 |
| **乐观锁** | **假设冲突很少**，不加锁；只在更新时检查"我读到的版本有没有被改过" |
| **悲观锁** | 先锁住这一行（`SELECT ... FOR UPDATE` 或分布式锁），别人等着 |
| **条件更新** | 把"允许在什么状态下更新"写进 SQL 的 `WHERE` 里，**由数据库判决**而不是应用层 if |
| **version（版本号）** | 订单表上的整数列，每次更新 +1；写回时拿它当"凭据" |
| **返回 0 行** | `UPDATE` 影响行数为 0 = 条件不满足 = **这个世界在我读完之后变了**（乐观锁的失败信号） |
| **唯一索引** | 数据库层的"不允许出现重复行"。`uk_user_activity(user_id, activity_id)` 是"一人一单"的最后一道防线 |
| **`available_stock` / `total_stock`** | 活动的**剩余库存** / **总库存**。预热读的是前者，回滚上限看的是后者 |
| **`limit_per_user`** | 每人限购件数（默认 1 = 一人一单） |
| **状态机 / 前置条件** | 订单状态（`PENDING_PAY / PAID / TIMEOUT / CANCELLED`）以及"允许怎么流转"；每次更新都要写清"从哪个状态出发" |

## 压测与指标

| 词 | 一句话解释 |
| --- | --- |
| **并发数** | 同时有多少个"虚拟用户"在打请求 |
| **闭环压测** | 固定 N 个线程，每个线程**发一个请求、等响应、再发下一个**，直到打完总数——模拟真实客户端。**不是**一次性把 2000 个请求全丢出去 |
| **栅栏** | 让所有线程**等在同一个点上**，然后一起放行，制造"真正的同时"（超卖实验用的就是它） |
| **吞吐（req/s）** | 每秒能处理完多少请求 |
| **平均耗时** | 所有请求耗时的平均值，**容易被少数极慢请求带偏**，只作参考 |
| **P50 / P90 / P95 / P99** | **99% 的请求都比这个数快**。P99 最接近"用户遇到的最差体验"，削峰的效果在 P99 上体现得最明显（1462ms → 329ms） |
| **对照组** | 同一套业务的另一条实现路径（这里是同步写库版），用来证明"差异真的来自异步本身" |
| **MQ 排空** | 跑下一组实验之前，先等上一组的消息被消费完、统计不再增长，否则两组数字会互相污染 |
