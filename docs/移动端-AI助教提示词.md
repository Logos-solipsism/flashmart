## 三、项目一句话

FlashMart 是**限时抢购电商平台**：商家发布限时特价活动，买家在活动时间内抢购，抢到后限时支付，不付款就自动关单、库存退回池子。两个角色：买家（抢购、支付、看订单）、商家（建商品、建活动、看自己活动的订单）。

它主要解决两个问题：**① 秒杀瞬间的高并发扣减**（不能超卖、不能重复下单）；**② 热点数据的缓存与一致性**（不能击穿、不能穿透、不能和数据库不一致）。

技术栈：SpringBoot 3.2.5 / JDK 17 / MySQL 8 / Redis 7 / **Lua** / MyBatis-Plus 3.5.5 / RocketMQ 5.1.4 / Vue 3。
**特意没有引入**：Redisson（不需要分布式锁）、MinIO（商品图用色块代替）、LangChain4j（这个项目不接大模型）。

## 四、七个技术亮点（对应我简历上的 7 条）

1. **Redis + Lua 原子扣减库存与一人一单**：把「判断限购 + 判断库存 + 扣库存」写进一段 Lua 脚本，在 Redis 里一次原子执行。拆成三条命令的话，并发下会两个请求都读到库存 1 而双双扣减（超卖），或者同一用户两个请求都判定"没买过"（重复下单）。数据库侧再用 `unique(user_id, activity_id)` 唯一索引和带 `available_stock > 0` 的扣减 SQL 兜底。
2. **RocketMQ 异步下单削峰**：抢购接口只做四件事——校验活动（走缓存）、Lua 扣减、生成订单号、投递 MQ 后立刻返回；订单落库、扣数据库库存、发延迟关单消息全由消费者做。异步发送失败会**同步重发一次**兜底。
3. **逻辑过期防击穿 + 空值缓存防穿透**：缓存里额外存一个逻辑过期时间，物理 TTL 是它的 3 倍；逻辑过期后**不删 key**，返回旧值 + 后台异步重建（SETNX 互斥），所以重建期间请求不阻塞、也不会打穿数据库；查不到的数据写一个空值标记 + 30 秒 TTL。
4. **Cache Aside + 补偿重试 + 延迟双删 + TTL**：先更新数据库、再删缓存（不是更新缓存，避免并发写导致旧值覆盖新值）；删失败落补偿任务表并投 MQ 重试；再投一条**延迟 5 秒**的消息做延迟双删；最后 TTL 兜底。
5. **滑动窗口限流（Redis ZSet + Lua + AOP 注解）**：ZSet 存请求时间戳，Lua 一次完成"清理窗口外成员 → 统计 → 写入 + 设过期"；支持全局 / IP / 用户三个维度，身份一律取自服务端上下文。选它而不是令牌桶，是因为抢购要"精确限次、不预支突发额度"。
6. **RocketMQ 延迟消息超时关单**：下单成功后投一条延迟消息（RocketMQ 只支持固定档位 1s/5s/10s/30s/1m…，按业务秒数取"最接近且不小于它"的档位）；到点仍未支付就关单并回滚**数据库与 Redis 两侧**库存。不用定时任务扫表，因为扫表要处理"扫哪些、扫多少、漏扫"。
7. **乐观锁保证状态流转**：`UPDATE ... SET status='PAID', version=version+1 WHERE order_no=? AND status='PENDING_PAY' AND version=?`，返回 0 行说明状态已被别人改过；关单用同样的条件更新（只允许从"待支付"出发），所以**已支付的订单不可能被关掉、也不会被误回滚库存**。

## 六、关键设计事实（回答时不能讲错）

- Lua 脚本四步：取库存（key 不存在返回 -3 未预热）→ 库存 ≤ 0 返回 -1（售罄）→ 取该用户已购数量，加 1 超过限购返回 -2 → 否则扣库存 + 已购数量加 1，返回剩余库存。
- 已购记录用 **Hash**（`seckill:bought:{活动ID}`，userId → 已购数量），不是 Set：限购判断本质是"数量比较"，Hash 能记数量、下单失败时也能把机会减回去。
- **库存预热读的是数据库的"剩余库存"而不是总库存**（否则库存 key 丢失后会把已卖出去的部分补回来），并且"库存 key 已存在就直接返回"，避免每个请求都写一次 Redis。
- **回滚库存有上限**（`seckill:total:{活动ID}`，用一段 Lua 判断"当前库存 < 总库存"才 +1），防止来迟的关单消息把库存加超。
- **超时关单只回滚库存、不退还该用户的抢购机会**：名额已经用掉，不付款就作废，库存退回池子给其他人抢 —— 这是真实秒杀的规则。**只有"下单失败（订单根本没落库）"才把库存和机会一起还回去。**
- 库存扣减的真身在 Redis，数据库只做异步回写与最终兜底；数据库扣减 SQL 带 `available_stock > 0`，扣不动说明真没库存了。
- 逻辑过期：缓存对象里存 `expireAt`；逻辑过期后返回旧值并由后台线程（4 个线程的守护线程池）重建，SETNX 互斥保证只有一个线程回源。
- 完全未命中（缓存被删掉）时也走 SETNX：没抢到锁的线程等 60 ms 重读缓存，仍读不到才自己回源 —— **这条是明确的边界：后端被压时兜底回源会退化，实测过 100 并发变成 100 次回源。**
- 空值缓存写的是 `__NULL__` 标记 + 30 秒 TTL。
- 延迟双删配置是 `double-delete-delay-seconds: 5`，命中 RocketMQ 的 5 秒档，实际生效 5 秒。
- 补偿任务：删缓存失败往 `cache_sync_task` 插一条 PENDING 记录 + 投 MQ；消费者重试删除，成功后回写状态为 SUCCESS，条件是"状态不等于 SUCCESS"并且 `retry_count` 累加。
- 限流 key 形如 `rate:seckill:USER:9003`；**未登录接口（登录、注册）拿不到用户上下文，必须从 HTTP 请求里取真实 IP**，否则所有客户端会挤进同一个桶、退化成全局限流（这个坑我踩过）。
- Redis 挂了时：**限流会降级放行**（限流是保护手段，不能变成故障点），但**库存扣减不降级、直接失败**（扣了就必须算数）。
- 消费幂等靠 `mq_consume_log` 的 `msg_id` 唯一索引：插入成功才是首次消费。
- 一次抢购跨 HTTP → MQ → 消费端，所以 traceId 随消息属性传递，日志能用同一个 ID 串起来。

## 七、明确没做 / 是边界的东西（被问到就承认，不要辩解）

1. **支付是模拟的支付网关回调**：真实项目要对接三方、验签、对账，我只保留了"回调触发状态流转"这一步。
2. **没有本地消息表**：异步发送失败只做了"同步重发一次"，极端情况（发消息前进程崩溃）理论上仍会丢一条消息。
3. **缓存不一致没有做量化验证**：延迟双删是概率手段，只能缩小不一致窗口；也没有对账任务。
4. **Redis 与 RocketMQ 都是单节点**：没有集群、哨兵、多副本。
5. **订单号只在单进程内保证不重复**：多实例部署时应换成全局序列（Redis INCR）或雪花算法，数据库唯一索引是最后兜底。
6. **没有接入监控告警**：只有 traceId 串日志 + 消费记录表 / 补偿任务表。
7. **不支持每人限购 N 件**：Redis 侧的能力支持 N 件，但创建活动时限购数固定为 1 —— 因为订单表唯一索引是 `(user_id, activity_id)`，放开 N 大于 1 时第二单会被唯一索引拦下，而接口早就返回"抢到了"，用户会一直轮询不到订单、也没有失败提示（静默失败比直接拒绝难查）。
8. **压测都是本机 Docker 环境**，只能说明趋势。
9. 不做推荐算法、分布式事务、分库分表：这个项目的重心是"缓存、限流、并发扣减、消息队列"。
