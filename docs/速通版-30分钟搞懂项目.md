## 第 1 章 · 业务闭环（3 分钟）

### 一句话
**面向买家与商家的限时抢购电商平台**：商家发限时特价活动，买家在活动时间内抢购，抢到后限时支付，不付款就自动关单、库存退回池子。

### 两个角色
| 角色 | 能做什么 |
| --- | --- |
| 买家 BUYER | 浏览抢购活动、抢购、支付、查看我的订单 |
| 商家 MERCHANT | 创建商品、创建/修改抢购活动、查看自己活动的订单 |

### 七步闭环（画图就画这个）
    ① 商家创建商品 → ② 创建抢购活动（同步预热 Redis 库存）
    → ③ 买家在抢购专区看到倒计时与库存进度 → ④ 点"立即抢购"
    → ⑤ 服务端 Redis + Lua 原子扣减成功 → 返回 orderNo（用户只等几十毫秒）
    → ⑥ RocketMQ 异步落单 → 买家拿到待支付订单 → 支付（乐观锁）
    → ⑦ 不支付 → 延迟消息 30 秒后到点 → 自动关单 + 库存回滚

### 我做了什么（一句话）
把"**瞬时高并发扣减**"和"**热点数据缓存一致性**"这两件事，做成了一条能跑、能压、能用数字验收的主链路。

## 第 2 章 · 七条亮点（六维速查）★核心

> 每条按六个维度压缩成一张表。**面试时按行说，一行一句就行。**

### 亮点① Redis + Lua 原子扣减库存与一人一单

| 维度 | 内容 |
| --- | --- |
| ① 是什么/怎么用 | 把「判断限购 + 判断库存 + 扣库存」写进**一段 Lua 脚本**，在 Redis 里**一次原子执行** |
| ② 为什么这么选 | 拆成三条命令的话，并发下会出现两个请求都读到库存 1 → **双双扣减（超卖）**；同一用户两个请求都读到"没买过" → **落下两单**。分布式锁能解决，但多了加锁/释放/续期的开销，而这条链路只有"读-判断-写"三步，Lua 更直接 |
| ③ 具体流程 | 抢购请求 → 限流 → 读活动（缓存）→ 预热库存 → Lua（库存没了返回 -1、超限购返回 -2）→ 成功则生成订单号 + 投 MQ → 立刻返回 |
| ④ 兜底 | 数据库侧 `unique(user_id, activity_id)` 唯一索引 + 扣减 SQL 带 `available_stock > 0`；Redis 判断失效也落不下第二单、也扣不成负数 |
| ⑤ 实测产出 | 30 件库存 / 60 个用户并发 → **成功 30、落库 30、数据库与 Redis 剩余库存都是 0**（成功数 = 落库数 = 总库存，无超卖） |
| ⑥ 方法论 | 高并发扣减 = **把"判断+扣减"压成一次原子操作 + 数据库唯一约束兜底 + 数量永远不为负** |

### 亮点② RocketMQ 异步下单削峰

| 维度 | 内容 |
| --- | --- |
| ① 是什么/怎么用 | 抢购接口**不写数据库**：只校验、扣 Redis、发一条消息就返回；订单落库、扣数据库库存、发延迟关单消息全在消费者做 |
| ② 为什么这么选 | 开抢瞬间是**尖峰**：几千个请求同时写库会打满连接池、响应雪崩。异步把尖峰**摊平成队列**，数据库只面对消费速度 |
| ③ 具体流程 | 抢购接口 → 发消息（带 traceId）→ 返回 orderNo → 前端轮询结果 → 消费者：幂等表 → 扣库库存 → 写订单 → 投延迟关单消息 |
| ④ 兜底 | 消费幂等表 `mq_consume_log`（msg_id 唯一索引）；异步发送失败**同步重发一次**兜底；失败抛异常交给 MQ 阶梯重试 |
| ⑤ 实测产出 | 接口 **28ms** 返回、订单 **157ms** 后落库；50 并发 2000 请求：**异步 176 req/s（P99 329ms）vs 同步 39 req/s（P99 1462ms）→ 吞吐 4.5 倍、P99 降 77%** |
| ⑥ 方法论 | 该不该异步：**用户是否必须马上拿到结果？动作是否不可逆？失败能否用重试/补偿兜住？** 三条都满足才异步 |

### 亮点③ 逻辑过期防击穿 + 空值缓存防穿透

| 维度 | 内容 |
| --- | --- |
| ① 是什么/怎么用 | **逻辑过期**：缓存里额外存一个过期时间，物理 key 不删；逻辑过期后**返回旧值** + 后台异步重建（SETNX 互斥）。**空值缓存**：查不到的数据写一个空值标记 + 短 TTL |
| ② 为什么这么选 | **击穿**：热点 key 一失效，全量请求同时打库。用互斥锁重建会让请求排队等；逻辑过期让请求立刻拿到旧值，重建在后台做。**穿透**：查不存在的 id 会每次打库，写空值标记就能挡住 |
| ③ 具体流程 | 读缓存 → 命中空值标记直接返回 null → 未命中则 SETNX 只放一个线程回源（其余等 60ms 重读）→ 命中后判断逻辑过期，过期就异步重建 |
| ④ 兜底 | 重建失败继续用旧值；空值 TTL 只有 30 秒，真有数据了不会被长期挡住；物理 TTL 是逻辑 TTL 的 3 倍，保证逻辑过期后旧值还在 |
| ⑤ 实测产出 | 缓存被删后 **100 并发只回源 1 次**（114ms）；逻辑过期瞬间 **100 并发全部成功、只重建 1 次**（119ms）；查不存在的活动 **200 次只回源 1 次** |
| ⑥ 方法论 | 缓存三问：**数据存不存在（穿透）？热点会不会同时失效（击穿）？大量 key 同时过期（雪崩）？** 三问各有各的解法 |

### 亮点④ Cache Aside + 补偿重试 + 延迟双删 + TTL

| 维度 | 内容 |
| --- | --- |
| ① 是什么/怎么用 | 更新数据时：**先更新数据库 → 再删缓存**（不是更新缓存）；删失败落补偿任务 + 投 MQ 重试；再投一条**延迟 5 秒**的消息做"延迟双删"；最后还有 TTL 兜底 |
| ② 为什么这么选 | 并发更新时"更新缓存"会出现后写的旧值覆盖先写的新值，而且不自愈；"删除"天然幂等、下次读自然回源。延迟双删是为了清掉"并发读在删除之后才回填的旧值" |
| ③ 具体流程 | 商家改活动 → 更新数据库 → 删缓存（失败则落 `cache_sync_task` + 投 MQ）→ 投延迟 5 秒消息再删一次 → TTL 兜底 |
| ④ 兜底 | 三层：**补偿重试**（删失败重试）、**延迟双删**（清回填）、**TTL**（最终一定过期）。删缓存失败也不影响主流程 |
| ⑤ 实测产出 | 补偿与双删链路都跑通（补偿任务状态 PENDING → SUCCESS、retry_count 会累加）；**一致性没有做量化验证，如实说** |
| ⑥ 方法论 | 缓存一致性四步：**先库后删 → 删除失败要能重试 → 并发回填要能补一刀 → 最后一定有 TTL** |

### 亮点⑤ Redis ZSet + Lua + AOP 注解滑动窗口限流

| 维度 | 内容 |
| --- | --- |
| ① 是什么/怎么用 | ZSet 存请求时间戳，Lua 一次完成"清理窗口外的成员 → 统计 → 写入"；注解 `SlidingWindowLimit` + AOP 切面，支持**全局 / IP / 用户**三个维度 |
| ② 为什么这么选 | 抢购要"**精确限次、不预支突发额度**"：令牌桶允许突发（第一个项目用的就是它），固定窗口有边界双倍流量的漏洞，滑动窗口按"最近 N 秒内的请求数"精确统计 |
| ③ 具体流程 | 切面读注解 → 拼 key `rate:seckill:USER:9003` → 执行 Lua（清理 → 统计 → 写入 + 设过期）→ 超阈值抛 429 |
| ④ 兜底 | Redis 不可用时**放行**（限流是保护手段，不能变成故障点）；身份一律取自服务端上下文（未登录接口从 HTTP 请求取真实 IP，否则会退化成全局限流——这个坑我踩过）|
| ⑤ 实测产出 | 同一用户 1 秒内 10 并发 → **5 通过 + 5 × 429**；改成每 1.2 秒 1 次匀速 → **全部通过**；登录接口并发 30 次 → 通过 20 + 限流 10 |
| ⑥ 方法论 | 限流四要素：**维度（限谁）、算法（允不允许突发）、阈值（按正常行为分布定）、降级（组件挂了怎么办）** |

### 亮点⑥ RocketMQ 延迟消息超时关单

| 维度 | 内容 |
| --- | --- |
| ① 是什么/怎么用 | 下单成功后投一条**延迟消息**，到点仍未支付就关单并回滚库存。RocketMQ 只支持固定档位（1s/5s/10s/30s/1m…），按业务秒数取"最接近且不小于它"的档位 |
| ② 为什么这么选 | 定时任务扫表要处理"扫哪些、扫多少、漏扫"，订单量大时扫描本身很重；延迟消息到期自己回来，服务重启也不丢 |
| ③ 具体流程 | 下单消费者写订单成功 → 投延迟消息（30 秒档）→ 到点消费者：查订单 → 条件更新 `PENDING_PAY → TIMEOUT` → 回滚数据库库存 + Redis 库存 |
| ④ 兜底 | 关单只允许从"待支付"出发（已支付的不会被关）；关闭失败会走 MQ 重试；回滚带上限（不能超过活动总库存） |
| ⑤ 实测产出 | 订单 PENDING_PAY → TIMEOUT（轮询 22ms 内已关单），数据库与 Redis 库存**各回滚 1 件**；**该用户再抢会被"一人一单"拦下**（名额不退，库存退给池子） |
| ⑥ 方法论 | 时序任务四原则：**预约优于轮询、必须有兜底、兜底复用幂等主逻辑、执行前校验状态前置条件** |

### 亮点⑦ 乐观锁解决支付回调与关单并发

| 维度 | 内容 |
| --- | --- |
| ① 是什么/怎么用 | `UPDATE ... SET status='PAID', version=version+1 WHERE order_no=? AND status='PENDING_PAY' AND version=?`——只允许从"待支付"出发，且校验版本号；返回 0 行说明状态已被别人改过 |
| ② 为什么这么选 | 冲突概率极低（只有支付回调与关单会同时碰同一单），临界区只改一行，用悲观锁/分布式锁成本过高；**条件更新本身就能表达业务规则**：不是待支付就不许改 |
| ③ 具体流程 | 支付：查订单 → 校验归属与状态 → 条件更新（返 0 行就提示"订单状态已变化，请刷新"）；关单：同样条件更新，返 0 行说明已支付/已取消，直接跳过 |
| ④ 兜底 | 支付幂等（已支付直接返回成功，不重复扣款）；关单成功才回滚库存，避免"已支付却被退款" |
| ⑤ 实测产出 | 两次支付都返回 PAID，第二次提示"订单已支付，无需重复支付"；关单后再支付会被拒绝（订单已关闭） |
| ⑥ 方法论 | 状态机四原则：**先定状态与允许的流转 → 每次更新都带前置条件 → 幂等设计 → 并发冲突交给数据库的条件更新判决** |

## 第 3 章 · 选型速查（为什么用这个、不用那个）★面试高频

| # | 我选的 | 没选的 | 一句话理由 |
| --- | --- | --- | --- |
| 1 | Redis + Lua 扣减 | Redisson 分布式锁 | 三步读改写用原子脚本更直接，少一次加锁/释放/续期开销；数据库唯一索引与条件更新兜底 |
| 2 | RocketMQ 异步下单 | 同步写库 | 开抢是尖峰，异步把尖峰摊平成队列（实测吞吐 4.5 倍） |
| 3 | 逻辑过期重建 | 互斥锁重建 | 互斥锁让请求排队等；逻辑过期返回旧值继续服务 |
| 4 | 滑动窗口限流 | 令牌桶 / 固定窗口 | 抢购要精确限次不预支突发；固定窗口有边界双倍流量漏洞 |
| 5 | 乐观锁 | 悲观锁 / 分布式锁 | 冲突概率低、只改一行；条件更新本身表达业务规则 |
| 6 | 延迟消息关单 | 定时任务扫表 | 扫表要处理扫描范围与漏扫；延迟消息到期自己回来 |
| 7 | 先更库再删缓存 | 先删缓存 / 更新缓存 | 先删有并发漏洞；更新会有旧值覆盖新值且不自愈 |
| 8 | 空值缓存 | 布隆过滤器 | 数据量级不支撑布隆（还要维护位图与误判处理），空值标记几行代码就够 |
| 9 | Hash 存已购记录 | Set / String | Hash 能记"已购数量"，天然支持"每人限购 N 件" |
| 10 | 延迟消息做双删 | 应用内定时任务 | 应用重启就丢；消息可持久化 |
| 11 | 数据库库存异步回写 | 数据库做强一致 | 数据库只做最终兜底，扣减真身在 Redis，避免每次扣减都写库 |
| 12 | 订单号进程内自增 | 纯随机数 | 随机数在两万次生成时撞了 207 次，而订单号有唯一索引（撞号=下单失败） |
| 13 | 不引入 MinIO / LangChain4j / Redisson | —— | 商品图用色块代替对象存储；不需要大模型；加锁需求已被 Lua + 乐观锁 + 唯一索引覆盖 |

### 三条选型"万能句"（被问任何选型都能接）
- **"先看约束"**：可靠性 / 延迟 / 成本 / 团队熟悉度 / 运维能力——**选型的答案在业务约束里，不在技术本身的优劣里**。
- **"看并发形态"**：是"尖峰"还是"平稳"？尖峰要削峰（队列），平稳只要够用（同步）。
- **"看一致性要求"**：能不能容忍短暂不一致？能容忍就用"缓存 + 补偿 + TTL"，不能容忍才上强一致方案（代价很大）。

## 第 4 章 · 难点在哪（面试官爱问的"难在哪"）

| 难点 | 一句话 |
| --- | --- |
| **把"判断 + 扣减"变成原子的** | 不是"加锁"，而是让这三步在 Redis 里一次执行完；否则并发下必然出现超卖或重复下单 |
| **尖峰 vs 平稳** | 抢购的并发是尖峰，不是平均值——**削峰的目标是让数据库只面对队列的速度** |
| **缓存的三种"死法"** | 击穿（热点失效）、穿透（查不存在）、雪崩（同时过期）——三种解法完全不同 |
| **缓存的"最后一公里"** | 删缓存失败、并发读回填旧值：**补偿 + 延迟双删 + TTL，三层缺一不可** |
| **并发下的状态流转** | 支付回调与关单可能同时到达：**用条件更新让数据库来判决**，而不是靠代码判断 |
| **库存回滚的两种语义** | "下单失败"要连机会一起还（用户什么都没拿到）；"超时关单"只退库存不退机会（名额已用掉）——**判错一种，用户就会凭空多出一次抢购机会** |
| **观察线上** | 一次抢购跨 HTTP → MQ → 消费端，所以我把 traceId 贯穿日志与消息 |

## 第 5 章 · 数字口径表（必背，含环境边界）

| 简历上的数字 | 怎么来的 | 环境/边界 |
| --- | --- | --- |
| 抢购接口 **28ms** 返回 | 异步版：只做校验 + Redis 扣减 + 发消息 | 本机 Windows + Docker 中间件，压测客户端与服务同机 |
| 订单 **157ms** 后落库 | 接口返回后轮询到订单可查 | 同上；是"通常值"，不是 P99 |
| **异步 176 req/s（P99 329ms）vs 同步 39 req/s（P99 1462ms）** | 同一套业务逻辑两个入口：异步走 MQ、同步直接写库；闭环压测、50 并发、各 2000 请求 | 两组必须在**同样背景噪音**下测：先等 MQ 排空、把订单超时调长、每次重置起点 |
| **超卖验证：30 件库存 / 60 个用户并发** | 成功数、落库订单数、数据库与 Redis 剩余库存四个数一起看 | 结果：30 / 30 / 0 / 0，无超卖；用压测接口（合成用户，跳过限购） |
| 一人一单：**并发 20 次只成功 1 次** | 同一用户 1 秒内并发 20 次抢购 | 结果 1 成功 + 4 限购 + 15 个 429（限流在限购之前，所以不是 19 个限购）|
| 限流：**10 并发 → 5 通过 + 5 × 429** | 阈值是每人 1 秒 5 次 | 匀速 1.2 秒 1 次则全部通过 |
| 击穿：**100 并发回源 1 次** | 缓存被删后并发请求详情，看回源计数 | 后端空载时成立；被压时兜底回源会退化，如实说 |
| 逻辑过期：**100 并发只重建 1 次** | 逻辑 TTL 调成 3 秒后并发请求 | 全部成功，耗时 119ms |
| 穿透：**200 次只回源 1 次** | 查不存在的活动，看回源计数 | 真实接口 |
| 超时关单：**库存各回滚 1 件** | 抢购后不支付，延迟消息到点关单 | 关单后该用户再抢被拦（名额不退） |
| 登录 IP 限流：**30 并发 → 20 通过 + 10 限流** | 阈值 20 次/秒/IP | 修复"退化成全局限流"之后测的 |

**一句话原则**：**能随实验设置任意变化的数字不写进简历；要写就写"不随设置变化的规律"**。

## 第 6 章 · 我主动说的不足（必背 5 条）

1. **支付是模拟的支付网关回调**：真实项目要对接三方、验签、对账，我只保留了"回调触发状态流转"这一步。
2. **没有本地消息表**：异步发送失败会同步重发一次兜底，但极端情况（发消息前进程崩溃）理论上仍会丢一条消息。
3. **缓存不一致没有量化验证**：延迟双删是概率手段，只能缩小窗口，无法证明绝对一致；也没做对账任务。
4. **存储与中间件都是单节点**：Redis、RocketMQ 都没有集群与多副本；订单号在多实例下需要换全局序列（Redis INCR 或雪花）。
5. **没有接入监控告警**：目前靠 traceId 串日志 + 消费记录表 / 补偿任务表排查，P99、重试率、死信量都没做面板。

外加一条边界：**压测都是本机 Docker 环境，只能说明趋势，不代表线上。**

## 第 7 章 · 90 秒项目介绍（逐字稿）

> "FlashMart 是一个**限时抢购电商平台**，买家在活动时间内抢购，商家发布活动并查看订单。
>
> 它主要解决两个问题：
> **第一是瞬时高并发扣减**。开抢那一瞬间会有几千个请求同时打过来，如果直接写数据库，连接池马上就满了。我的做法是：抢购接口只用 **Redis + Lua** 做一次原子操作——把'判断限购、判断库存、扣库存'合成一次执行，然后投一条 **RocketMQ** 消息就立刻返回；订单落库、扣数据库库存、发超时关单消息全交给消费者。实测接口 **28 毫秒**返回、订单 157 毫秒后落库；50 并发下异步版 **176 req/s**，同步对照组只有 **39 req/s**，P99 从 1462 毫秒降到 329 毫秒。
>
> 为了保证数据不出问题，我在三层都做了兜底：Redis 的 Lua 保证不超卖和一人一单，数据库用唯一索引和条件扣减兜底，压测里 30 件库存 60 个人同时抢，最后正好卖出 30 单、库存为 0。
>
> **第二个是热点数据的缓存问题**。活动详情是典型热点，我用**逻辑过期 + 异步重建**防击穿——逻辑过期后返回旧值、后台重建，请求不用排队等；用**空值缓存**防穿透；改数据时用 **Cache Aside**，删缓存失败会投消息补偿重试，再加一条延迟双删，最后还有 TTL 兜底。实测缓存被删后 100 个并发请求只回源数据库 1 次。
>
> 另外还有两个细节：关单我没用定时任务扫表，而是用 **RocketMQ 延迟消息**，到点自己回来；支付回调和关单可能同时改同一张订单，我用**乐观锁加状态前置条件**，让数据库来判决，只允许一方成功。"
